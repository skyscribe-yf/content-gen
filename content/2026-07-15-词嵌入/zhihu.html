词嵌入（embedding） 解决一件事：token 的整数编号没有远近，模型却需要「意思近的挨在一起」。做法是把每个 ID 查成一串坐标——这就是嵌入矩阵在干的活。

上一篇《BPE分词：AI为什么把文字切成碎片？》把文字切成了 token，每个 token 拿到一个整数编号。但编号只是编号——5237 和 16652 之间没有远近关系，"猫"的 ID 和"猫咪"的 ID 也挨不到一起。

怎么办？把编号变成一串坐标。意思近的坐标挨得近，意思远的各站一角。

先从一个小实验开始。

你搜"苹果手机"，结果里跳出了"iPhone 16 Pro"。一个中文字都没匹配上，搜索引擎怎么知道它们是一回事？

反过来，传统 Ctrl+F 搜"苹果"，会把"吃苹果""苹果发布会""苹果醋"全给你——它只看字形，不懂意思。

AI 不是这样。它把每个词（严格说是每个 token）装进一个高维空间里，变成一串坐标。意思近的词，坐标挨得近。意思远的，各站一角。搜索不再是匹配字形，而是在这个空间里找邻居。

但这串坐标怎么来的？不是人填的。是训练时，反向传播根据损失函数的梯度，一步步把这 9.27 亿个数字调到让模型预测最准的位置。

① 第一步：把词变成编号

大模型看文本的第一步是分词。它不像你想象的那样按"词"切——同一个字在不同的搭配下，可能被切成不同的 token。

以 DeepSeek-V4-Pro 的分词器为例（AutoTokenizer.from_pretrained("deepseek-ai/DeepSeek-V4-Pro")）：

输入: "今天天气真好，适合出去玩"

分词结果 (6 个 token):
  ID  5237 → "今天"
  ID 16652 → "天气"
  ID 67261 → "真好"
  ID   303 → "，"
  ID 10447 → "适合"
  ID 122377 → "出去玩"

每个片段叫一个 token。分词器手里有一本 词表（vocabulary），2026 年 DeepSeek-V4-Pro 的 config.json 里 vocab_size = 129,280，也就是约 13 万个 token，每个 token 被分配了一个整数编号。

分词器把文本切成 token，每个 token 拿到一个整数编号

看仔细："今天"是一个 token，"出去玩"也是一个 token——常见的词组会被打包成单个 token。但英文就惨了，看看这个：

输入: "DeepSeek-V4使用了7168维的词嵌入"

分词结果 (11 个 token):
  ID 53091 → "Deep"
  ID  4374 → "Se"
  ID  1465 → "ek"
  ID 13582 → "-V"
  ID    22 → "4"
  ID 44596 → "使用了"
  ID 27853 → "716"
  ID    26 → "8"
  ID  3013 → "维"
  ID 106543 → "的词"
  ID 52421 → "嵌入"

"DeepSeek" 被拆成了三块：Deep + Se + ek。因为英文大写在词表里没有现成的"DeepSeek"这个 token，分词器只能用更小的子词碎片拼出来。

到这里，文字已经变成了数字。但问题来了：ID 只是个编号，没有任何语义。

5237 和 16652 之间没有大小关系、没有远近关系。如果直接把这些 ID 喂给神经网络，它在模型眼里只是一串无序的整数。

更糟的是——"猫"的 ID 是 11440，"猫咪"的 ID 是 54420。两个数字之间没有任何联系，但模型需要知道它们意思相近。

怎么办？

② One-hot：最直觉的方案，也是最失败的

最直接的想法：给每个 token 一个独立向量。词表有多大，向量就有多长。每个向量只有一位是 1，其余全是 0。

比如一个只有 3 个词的微型词表 {猫, 狗, 汽车}：

"猫"  → [1, 0, 0]
"狗"  → [0, 1, 0]
"汽车" → [0, 0, 1]

这叫 one-hot 编码。干净、准确、不会搞混。

但问题也出在这里。怎么判断两个向量表示的意思是不是相近？直觉上，看它们的夹角就行——夹角越小，方向越一致，意思越近。 量化这个角度的指标叫余弦相似度：1 表示完全同方向，0 表示垂直无关，−1 表示完全相反。

回到 one-hot——这三个向量互相垂直：

cos(猫, 狗) = 0，cos(猫, 汽车) = 0

——猫和狗的距离 = 猫和汽车的距离。 没有任何语义信息。

题目里的「5 万个 0」只是入门量级：词表有 5 万个 token，one-hot 就接近 5 万维。放到 2026 年 DeepSeek-V4-Pro 上，词表是 129,280 个 token，one-hot 会膨胀到约 13 万维，几乎全是 0，只有一个位置是 1。

One-hot 编码：所有向量互相垂直，距离全等——没有任何语义信息

这个方案有两个致命伤：

  • • 维度灾难：动辄几万到十几万维，太稀疏、太浪费
  • • 语义为零：所有 token 之间距离一模一样，无法区分语义近远

我们需要的，是一个既紧凑又包含语义的表示。

③ 嵌入矩阵：5 万个 0 变成一串坐标

答案藏在嵌入矩阵（embedding matrix）里。

嵌入矩阵是一个巨大的表格——行数 = 词表大小，列数 = 嵌入维度。以 2026 年 DeepSeek-V4-Pro 为例（数据来自 Hugging Face config.json）：

vocab_size = 129,280（约 13 万个 token） hidden_size = 7,168（每个 token 用 7168 个数字表示）

一张 129,280 × 7,168 的大表，每行是一个 token 的"坐标"。总参数量：129,280 × 7,168 ≈ 9.27 亿，光嵌入矩阵就占了一个中等模型的体量。

但这 9.27 亿个数字不是人填的。它们一开始是随机的（V4-Pro 的 config.json 写着 initializer_range = 0.02），然后在训练中被反向传播一步步调整。

嵌入矩阵是一张 vocab × dim 的大表，one-hot 乘矩阵 = 抽出那一行

怎么查表？一行代码的事。但拆开看，这里面有一个漂亮的数学操作——

one-hot 向量 × 嵌入矩阵 = 抽出那一行。

用 NumPy 拆解一下：

import numpy as np

np.random.seed(42)  # 让你本地运行时输出一致

# 模拟：5个词的小词表，嵌入维度=4
vocab_size, dim = 5, 4

# 嵌入矩阵——训练前是随机的，训练后才有语义
W_embed = np.random.randn(vocab_size, dim) * 0.02

# "猫"的 token id = 2，用 one-hot 编码
one_hot_cat = np.zeros(vocab_size)
one_hot_cat[2] = 1.0

# one-hot × 嵌入矩阵 → 抽出 ID=2 的那一行
vec_cat = one_hot_cat @ W_embed
print(f"'猫'的向量: {np.round(vec_cat, 3)}")
# 输出: '猫'的向量: [-0.009  0.011 -0.009 -0.009]

# 同理，"狗"的 token id = 3
one_hot_dog = np.zeros(vocab_size)
one_hot_dog[3] = 1.0
vec_dog = one_hot_dog @ W_embed

# 余弦相似度
def cosine(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

print(f"随机初始化下猫和狗的相似度: {cosine(vec_cat, vec_dog):.3f}")
# 输出: 随机初始化下猫和狗的相似度: -0.035

用 PyTorch（工业实现）：

import torch
import torch.nn as nn

# 先用小词表演示 nn.Embedding 的查表动作
vocab_size, dim = 5, 4
embedding = nn.Embedding(vocab_size, dim)

# 输入 token id → 查表出向量
token_ids = torch.tensor([2, 3, 4])
vectors = embedding(token_ids)

# DeepSeek-V4-Pro 的真实规模只做参数量计算，避免本地直接分配 927M 参数
deepseek_vocab, deepseek_dim = 129280, 7168
print(f"演示输出形状: {vectors.shape}")  # torch.Size([3, 4])
print(f"DeepSeek-V4-Pro 嵌入矩阵总参数: {deepseek_vocab * deepseek_dim / 1e6:.0f}M")  # 927M

nn.Embedding 把 one-hot 与矩阵乘法这件事封装成了查表。token_ids[2] 进去，拿出第 2 行的 4 个小数；换成 DeepSeek-V4-Pro 的真表，就是拿出对应行的 7168 个小数。

④ 中药柜隐喻：为什么这 7168 个数字能"懂"语义

最难的来了：这张表里的数字，凭什么就带上了语义？

我给你讲一个比喻。

想象一个老药铺的中药柜。约 13 万个抽屉，每个抽屉上贴着一个 token 名。拉开"当归"的抽屉，里面是一包粉末——其实是一个装满 7168 个数字的向量。拉开"川芎"，也是一包粉末，差不多的颜色、差不多的气味、差不多的配方。这两种药材老被开在同一张方子里，所以它们的粉末越来越像。

但光有方子不够。这个药柜不是普通的柜子，它是一台机器。每次大夫开方子，机器拉开对应抽屉，倒出一包粉末（这是前向传播）。更关键的是，每次倒完之后，机器会根据"这包粉末配得好不好"的反馈，悄悄调整抽屉里的配方（这是反向传播）。

  • • 当归和川芎老被一起用来活血，几百万次之后，它们的粉末越来越像——近义词在空间里挤在一起。
  • • 用法差很远的药材，很少出现在相似方子里，机器会把它们拉开——不相关的词会站得更远。
  • • 反义词不一定站成正负两端；"好"和"坏"常出现在同一类句式里，可能反而离得不远。嵌入学的是用法，不是字典规则。
  • • 同一个药材查表时拿到同一包基础粉末，但进了后面的 Transformer 层，会被整张方子的上下文重新调味——上下文层让向量动态偏移。

矩阵乘法（one_hot @ W_embed）= 拉开抽屉、倒药。
梯度更新（W_embed -= lr * grad）= 根据反馈调整抽屉里的配方。
语义空间 = 不是老中医设计的，是几百万张方子"用"出来的。

这个比喻抓住了一个关键直觉：嵌入矩阵的参数不是人设计的——是训练中反向传播自动调出来的。 这就是「AI 的语义不是规则，而是统计规律」的数学本质。

中药柜隐喻：拉开抽屉倒药 = 前向传播，调整配方 = 反向传播

进度小结：走到这里，三步已经走完两步——①分词给每个 token 一个编号，②one-hot 因为维度灾难和语义为零被否掉，③嵌入矩阵把编号查成一串坐标，④解释了这串坐标凭什么带语义。还剩一个问题：怎么量化两个向量「意思有多近」？ ⑤余弦相似度登场。

⑤ 余弦相似度：在坐标空间里量"意思有多近"

有了向量，怎么量两个词的意思有多近？

用余弦相似度。你不用记公式，记住三个场景就够：

方向完全一致 → cos = 1（"猫"和"猫咪"——几乎同义词） 方向互相垂直 → cos = 0（"猫"和"汽车"——不相关） 方向完全相反 → cos = −1（数学上的相反方向，不等于所有反义词都会这样）

为什么用余弦而不是欧式距离？一个关键原因：高频词（比如"的""了"）出现次数多，训练中梯度累积多，向量的模长天然偏大。如果比欧式距离，"的"和什么都远。余弦只看方向，消掉了频率偏差，让语义本身说话。

训练成熟的嵌入矩阵里，真正重要的不是某个固定分数，而是相对顺序：

cos("开心", "高兴") 会明显高于 cos("开心", "汽车") cos("苹果手机", "iPhone") 会被训练拉高，成为跨语种语义搜索的基础

这就是为什么搜"苹果手机"能找到"iPhone"——它们在嵌入空间里是邻居。

余弦相似度：看方向不看距离，同义词方向一致，不相关互相垂直

⑥ 延伸：2013 年的 Word2Vec 和那个著名的算术彩蛋

你听到这里可能会问——这个思想最早是谁提出的？

2013 年，Google 的研究员 Tomas Mikolov 发表了 Word2Vec。核心思想跟前面讲的一模一样：一个词的意思，由它周围的词决定。 让模型做"完形填空"——遮掉中间一个词，用上下文猜它是什么。猜着猜着，嵌入矩阵就学会了语义。

Word2Vec 发布时最轰动的结果，是一个语义算术：

vec("国王") − vec("男人") + vec("女人") ≈ vec("女王")

不是人工规则。是模型从海量文本中自动学到的——国王和女王的区别（在很多语境下）= 男和女的区别。这个向量方向被编码在了嵌入空间里。

但这里有一个关键的升级要说清楚。

Word2Vec 是一词一向量。 "苹果"不管在"吃苹果"还是"苹果发布会"里，拿到的都是同一个向量。这在 2013 年读新闻分类够用了，放到今天的大模型里就露馅了——"苹果"在水果语境下应该靠近"香蕉"，在科技语境下应该靠近"安卓"。

现代大模型（包括 DeepSeek-V4-Pro）用的是上下文相关的 token 级嵌入：同一个字在不同上下文里，经过 Transformer 层加工后，向量会动态偏移。Word2Vec 是"一个词一张固定身份证"，Transformer 的嵌入是"同一个词在不同场合穿不同衣服"。

也就是说，今天大模型的嵌入矩阵，本质还是 Word2Vec 那套"查表→训练→近义词挤在一起"的逻辑——但多了"看上下文动态调整向量"这个维度。下一篇讲位置编码和注意力的时候，我们会展开这个。

语义算术：国王−男人+女人≈女王；Word2Vec 固定向量 vs Transformer 上下文嵌入

⑦ 结尾

回到开头的问题：AI 怎么把「苹果」变成它能懂的数字？

三步——

  1. 1. 分词器把文本切成 token，每个 token 拿到一个整数编号。
  2. 2. 嵌入矩阵是一张巨大的查表——13 万行、7168 列，每行是一串坐标。
  3. 3. 训练时，反向传播不断调整这串坐标，让意思近、用法相似的 token 在空间里靠近，让无关 token 被拉远。这不是人设计的，是"用"出来的。
