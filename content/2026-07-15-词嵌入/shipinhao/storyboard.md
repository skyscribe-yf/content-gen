# 《词嵌入为什么让AI懂"苹果"？5万个0变坐标》视频号分镜脚本

基于 content/2026-07-15-词嵌入/weixin.md
规格：竖屏 1080×1920 · Manim 动画 · MiniMax 克隆音色配音（speed 1.15 pitch +2）+ 烧录字幕 · 目标 2-3 分钟

## 段落设计（8 段）

| # | 场景 | 动画要点 | 配音稿 |
|---|------|---------|--------|
| S1 | 开场钩子 | 搜索框"苹果手机"→ 命中"iPhone 16 Pro"（0 字匹配）；Ctrl+F 对比三结果；散点空间两簇（意思近的挨一起） | 你搜"苹果手机"，结果跳出"iPhone 16 Pro"——一个中文字都没匹配上，搜索引擎凭什么知道它们是一回事？反过来，Ctrl+F 搜"苹果"：吃苹果、苹果发布会、苹果醋，全给你——它只看字形，不懂意思。AI 不是这样。它把每个词装进一个高维空间，变成一串坐标：意思近的，坐标挨得近；意思远的，各站一角。搜索不再是匹配字形，而是在这个空间里找邻居。 |
| S2 | 分词给编号 | "今天天气真好，适合出去玩"→ 6 个 token 块逐个点亮；ID 与词对照；词表 129,280；"猫"11440 vs "猫咪"54420 无联系 | 大模型看文本的第一步，是分词。以 DeepSeek-V4-Pro 的分词器为例："今天天气真好，适合出去玩"，被切成 6 个 token——"今天"是一个，"出去玩"也是一个。常见的词组，会被打包成单个 token。分词器手里有一本词表：2026 年，DeepSeek-V4-Pro 的 vocab_size 是 129,280——约 13 万个 token，每个都拿一个整数编号。但问题来了：ID 只是个编号，没有任何语义。5237 和 16652，没有远近、没有大小。"猫"的 ID 是 11440，"猫咪"是 54420——两个数字之间，没有任何联系。怎么办？ |
| S3 | One-hot 失败 | 微型词表 3 词 → 三个互相垂直的向量箭头；cos(猫,狗)=0；13 万 token → 13 万维膨胀示意；两个致命伤 | 最直觉的方案，是 one-hot：给每个 token 一个独立向量，词表多大，向量就多长。一个只有 3 个词的微型词表——猫、狗、汽车："猫"是 [1,0,0]，"狗"是 [0,1,0]，"汽车"是 [0,0,1]。干净、准确、不会搞混。但问题出在这里：这三个向量，互相垂直。cos(猫,狗) 等于 0，cos(猫,汽车) 也等于 0——猫和狗的距离，等于猫和汽车的距离。语义？为零。放到 2026 年的 DeepSeek-V4-Pro 上：13 万 token，one-hot 直接膨胀到约 13 万维，几乎全是 0。维度灾难，加上语义为零——one-hot，判死刑。 |
| S4 | 嵌入矩阵 | 129,280 × 7,168 大表网格；总参数 9.27 亿；one-hot × 矩阵 = 抽行（高亮一行） | 答案藏在嵌入矩阵里。它是一张巨大的表格：行数等于词表大小，列数等于嵌入维度。以 DeepSeek-V4-Pro 为例：vocab_size 129,280，hidden_size 7,168——每个 token，用 7168 个数字表示。总参数量：129,280 乘 7,168，约 9.27 亿——光嵌入矩阵，就占了一个中等模型的体量。但这 9.27 亿个数字不是人填的：一开始是随机的，训练中被反向传播一步步调出来。怎么查表？一行代码的事。拆开看，是一个漂亮的数学操作：one-hot 向量乘嵌入矩阵，等于抽出那一行。 |
| S5 | 中药柜隐喻 | 中药柜抽屉网格（当归/川芎）；粉末向量；前向=倒药、反向=调配方；近义词挤在一起 | 最难的来了：这张表里的数字，凭什么带上了语义？想象一个老药铺的中药柜——约 13 万个抽屉，每个贴着 token 名。拉开"当归"，是一包粉末，一个装满 7168 个数字的向量。拉开"川芎"，也是差不多的粉末。这两种药材老被开在同一张方子里，几百万次之后，粉末越来越像——近义词，在空间里挤在一起。而用法差很远的药材，会被慢慢拉开。注意。这个药柜不是普通的柜子，它是一台机器：每次倒完药，机器会根据"这包药配得好不好"的反馈，悄悄调整抽屉里的配方——这就是反向传播。AI 的语义不是规则，是几百万张方子，"用"出来的。 |
| S6 | 余弦相似度 | cos=1（同向）/0（垂直）/−1（反向）三场景箭头；高频词模长偏大 vs 余弦只看方向；"开心-高兴"高亮 > "开心-汽车"；苹果手机→iPhone 邻居 | 有了向量，怎么量"意思有多近"？用余弦相似度。记住三个场景就够：方向完全一致，cos 等于 1——"猫"和"猫咪"；方向互相垂直，cos 等于 0——"猫"和"汽车"；方向完全相反，cos 等于负 1。为什么不用欧式距离？因为高频词，"的""了"，出现次数多，向量模长天然偏大——比欧式距离，"的"和什么都远。余弦只看方向，消掉了频率偏差。所以训练成熟之后：cos("开心","高兴")，会明显高于 cos("开心","汽车")。这就是为什么搜"苹果手机"，能找到"iPhone"——它们在嵌入空间里，是邻居。 |
| S7 | Word2Vec 与上下文嵌入 | 2013 Mikolov 卡片；完形填空（遮中间词）；语义算术 国王−男人+女人≈女王；固定身份证 vs 换衣服 | 这个思想，最早是谁提出的？2013 年，Google 的研究员 Tomas Mikolov 发表了 Word2Vec——核心思想一句话：一个词的意思，由它周围的词决定。让模型做"完形填空"：遮掉中间一个词，用上下文猜。猜着猜着，嵌入矩阵就学会了语义。当时最轰动的，是一个语义算术：vec("国王") 减 vec("男人")，加 vec("女人")，约等于 vec("女王")。不是人工规则，是模型从海量文本里自动学到的。但注意。Word2Vec，是一词一向量："苹果"在"吃苹果"和"苹果发布会"里，拿的是同一个向量。放到今天的大模型，就露馅了。现代大模型用的是上下文相关的嵌入——同一个词，在不同场合，穿不同的衣服。本质还是查表加训练，但多了"看上下文、动态调整"这个维度。 |
| S8 | 三步总结 + 品牌尾卡 | ①分词 ②嵌入矩阵 ③反向传播调坐标（近的靠拢/远的拉远）；尾卡：avatar 圆角图 + 图下黄色「关注「数解AI」」+ 当期文章标题 + 「查看公众号文章」绿色引导 + 下一篇预告 | 回到开头的问题：AI 怎么把"苹果"变成它能懂的数字？三步。第一步，分词器把文本切成 token，每个 token 拿到一个整数编号。第二步，嵌入矩阵——一张 13 万行、7168 列的大查表，每行是一串坐标。第三步，训练时，反向传播不断调整坐标：意思近的，靠拢；无关的，拉远。这不是人设计的，是"用"出来的。关注数解AI，下一篇讲位置编码：词序一错，意思全变。 |

## 制作流程

1. 配音：`scripts/minimax_tts.py` 逐段生成 S1-S8（克隆音色 `branding/my-voice-denoised.wav`，speed 1.15 pitch +2），拟声标签见 `tts-tagged/sN.txt`（标签只进 TTS 输入，tts.txt 保持纯净作字幕基准），ffprobe 记录各段真实时长
2. 动画：每段一个 Manim Scene（S1..S8），`construct` 末尾 `pad_to_voice()` 补齐；动画节点按台词时间轴铺满
3. 构建：`scripts/manim_video_build.py` mux 配音 + 无缝拼接 + 黄色字幕烧录（MarginV=210, 75 号）+ 打字机字幕 + 品牌尾卡
4. 封面：Cover 场景单帧渲染（底部放公众号 logo 圆角图 avatar-sjai-round.png）→ `<标题>-封面.png`（1080×1920）
5. 归档：`content/2026-07-15-词嵌入/shipinhao/`
