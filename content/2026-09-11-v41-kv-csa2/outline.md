## 悬念链（小标题连起来是完整故事）

1. **读仓库的时候，先爆的不是模型，是账本**
   - 人话：每看一个词记一笔「跟谁有关 / 留下什么」——这就是 KV 缓存，本篇统一叫记账
   - 不重讲 1bit / 落盘 / 稀疏选位置；一句回扣已发三层：格子多薄、账本放哪、看多少个位置。今天问的是第四层——**层和层之间要不要各记一份**
   - 埋钩：四十层听起来应该有四十本账。V4.1 的全局账却薄成 890 字节

2. **890 字节到底有多离谱**
   - 官方口径（Hugging Face 模型卡 + 2026-09-10 发布稿）：全局 KV **890 字节 / token**；相对 V4-Flash 约 **1/4**（HBM）；持久化 KV 约 **1/8**（SSD）；相对 V1 约 **437 倍**
   - 对照用「上一代 Flash」，不编「四十层四十本账」
   - 预告：890 不是一刀砍出来的，是三刀合计。主刀是跨层复用，另外两刀后文交代
   - 图 1：890 vs 上一代 Flash 4 倍（脚本图，数字只在脚本里）

3. **第一层筛短名单，后面的层只在短名单里找**
   - 交付句：第一层已经把「可能相关」筛过一遍，后面的层只在这张短名单里找，不再对着整本仓库重新建账
   - 人话讲完，再点一次标签：这套静态分工叫 CSA2（全文只出现这一次）。三档各出现一次——**Full** 自己建账并筛 Top-512；**Reindex** 抄账本、自己再打分；**Reuse** 连短名单一起抄、索引器都不跑
   - Reindex 与 Reuse 的差别一句带过：有的层连短名单都抄，有的层只抄账本、自己再挑。不进小标题、不配对照图
   - 解码器里还有一层人话：第一层 Full 先给出最多 16,384 个候选位置（2,048 块 × 8），后面的层只在这个池子里打分——候选池有上限，不跟上下文长度一起疯长
   - 图 2：仓库全文 → 第一层短名单 → 后面的层只在短名单里找（脚本图，结构不写数字公式）

4. **短名单会漏人，这是代价**
   - 反常识必须配诚实边界：复用不是免费的。短名单漏了关键文件，后面的层再认真也看不到
   - 不写成「四十层看的是同一份账」——三档并不一样，每层仍保留自己的主查询 Q 和窗口账
   - 读者能带走的判断：敢抄，是因为第一层已经付过筛选的算力；看错人的风险，用短名单长度和分档来管

5. **另外两刀：格子改成 4 位，窗口账不落盘**
   - 主 KV 用 FP4（E2M1，每 16 通道一个 E4M3 缩放）。这是「格子多薄」，跟 09-01 的 1bit/1.25bit 不是同一篇：那篇讲 K 精 V 糙；这里是主账 FP4，几乎相对 V4 的 FP8 再砍一半
   - 滑动窗口那截（窗口 128）**不写入持久化账本**。需要时只把最近 128 个词重放一遍——Bounded Replay。开场的 890 **不含**这截持久化；漏写会被懂的人喷
   - 官方：SWA 不落 SSD，是持久化 KV 收到约 1/8 的关键一刀
   - 图 3：三刀叠成 890（跨层复用 / FP4 / Replay），脚本图，数字白名单：890、1/4、1/8、128、437

6. **回扣开头：四十层，不是四十本账**
   - 回答标题：不给每层都记账，因为第一层筛短名单，后面的层在短名单里找；890 是三刀合计，不是单靠复用
   - 回到仓库：词再多，全局账按 890 字节/词长，显存先爆的那一幕被往后推
   - 社区速度体感最多一句「有人测到输出飞到几百 token 每秒」，**不写 500、不当机制、不写成官方**
   - 文末问题（30 秒可答）：你跑过长仓库的 coding agent 吗？最后爆掉的是显存、上下文，还是模型开始看错文件？
