# 《大模型 API 为什么这么慢？首字延迟揭秘》视频号分镜脚本

基于 content/2026-08-03-推理加速/weixin.md
规格：竖屏 1080×1920 · Manim 动画 · MiMo 配音 + 烧录字幕 · 目标 2-3 分钟

## 段落设计（8 段）

| # | 场景 | 动画要点 | 配音稿 |
|---|------|---------|--------|
| S1 | 开场钩子 | 请求图标 → 假想"直通 GPU"直线被打断 | 你给大模型 API 发出一个请求，以为它会直接抵达 GPU。可十几秒过去，屏幕上连第一个字都没有。到底慢在哪？ |
| S2 | TTFT 定义 | 公式 T_TTFT = t_first − t_request 逐项亮起 | 首字延迟，工程上叫 TTFT，Time To First Token。从你按下发送，到收到第一个流式 token，中间这段等待，就是首字延迟。 |
| S3 | 服务链路 | 链式方块逐个点亮：客户端→网关→路由→排队→prefill→decode→流式返回 | 请求并不是直通 GPU 的电线。它要过网关鉴权、模型路由，可能还要排队等批处理；真正进入模型后，先 prefill 读完整段输入，再逐 token decode，最后流式返回。 |
| S4 | prefill 平方 | 2×2 网格 → 4×4 网格，配对连线爆炸，C ∝ T_in² | prefill 要建立输入位置之间的两两关系，工作量随输入长度近似平方增长。输入翻一倍，注意力配对的工作量，可能接近四倍。 |
| S5 | decode + KV Cache | token 序列逐个生成，KV 缓存条随历史增长，M ∝ T_in | decode 阶段，KV Cache 把历史的 Key 和 Value 存下来，避免每次重算。但缓存占用随上下文线性增长：历史越长，显存压力越大。 |
| S6 | 真实日志数据 | 柱状图：0-16K→96-128K TTFT P50 4.7s→14.0s；TPS 平线 25-30 | 作者的真实请求日志：输入从 16K 涨到 128K，TTFT 中位数从 4.7 秒升到 14 秒，将近三倍；但首字之后的生成速度，稳定在每秒 25 到 30 个 token。长输入，主要撞上的是 prefill 和排队。 |
| S7 | 四把扳手 | 四格图标：减输入 / KV Cache / 推测解码 / 量化 | 想提速，先看慢在哪一段：输入太长，就压缩提示词和历史；decode 慢，用 KV Cache 和推测解码；显存吃紧，可以量化。四种扳手，各管一段。 |
| S8 | 结尾引导 | 总结卡：记录 TTFT/TPS，看 P50/P90；关注「数解AI」 | 给每次请求记下输入、输出、TTFT 和 TPS，看 P50 和 P90，再决定优化方向。关注数解AI，继续拆大模型推理链路。 |

## 制作流程

1. 配音：`scripts/xiaomi_mimo_tts.py` 逐段生成 S1-S8，记录各段真实时长
2. 动画：每段一个 Manim Scene，时长 ≥ 配音时长 + 1s 缓冲
3. 拼接：ffmpeg concat 各段视频 + 音频
4. 字幕：按段落时间轴生成 SRT（黄色字幕）
5. 烧录：`scripts/burn_shipinhao.py` 烧录字幕（无 logo 场景，跳过 auto-logo）
6. 归档：`content/2026-08-03-推理加速/shipinhao/成品.mp4`
