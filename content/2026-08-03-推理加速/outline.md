## 文章设计

### 读者读完要得到的答案

1. 为什么 API 请求不是“直接和 GPU 对话”。
2. TTFT、TPS 和总耗时分别在测什么。
3. 输入长度、输出长度、排队和流式传输如何共同决定等待体验。
4. KV Cache、推测解码、量化和采样策略分别能解决哪一段问题，哪些不能解决。
5. 如何用自己的 TTFT/P90 和输入长度分布选择接口。

### 驱动问题：你等的不是模型回答，而是整条服务链路

- 从代码助手发出一次 API 请求写起：读者以为“请求 → GPU → 答案”。
- 反转：真实路径是客户端、网关、鉴权/限流、路由、排队/批处理、prefill、decode、流式返回。
- 抛出主问题：调用大模型 API 时，时间到底花在了哪一段？

### 一、先别急着怪 GPU：首字之前发生了什么

- 解释 API 服务不是单卡直连：请求先进入服务层，再决定去哪一组模型实例。
- 区分连接等待、排队等待、prefill、首 token 编排和网络返回。
- 说明连续批处理的取舍：提高整体吞吐，却可能让某个请求等待下一轮调度。

### 二、TTFT 是用户真正感受到的第一堵墙

- 定义 TTFT：发起请求到收到首个流式 token。
- 对比 TTFT、TPS 和总耗时：首字慢会让用户觉得“模型没反应”，首字快但 TPS 低则是“开始说了却说得慢”。
- 给出 Pi 日志采集说明：`before_provider_request` 到第一个 `message_update`；`providerResponseMs` 没有写入最终记录，因此不拆成不可观测的服务端阶段。

### 三、四个简单公式，把“慢”翻译成数学

1. 用户侧首字延迟：

   $$T_{\mathrm{TTFT}} \approx T_{\mathrm{queue}}+T_{\mathrm{prefill}}+T_{\mathrm{network}}$$

2. 总耗时：

   $$T_{\mathrm{total}} \approx T_{\mathrm{TTFT}}+\frac{N_{\mathrm{out}}-1}{r_{\mathrm{decode}}}$$

3. 全注意力 prefill 的注意力计算项：

   $$C_{\mathrm{prefill}}\propto T_{\mathrm{in}}^2$$

4. KV Cache 的长度趋势：

   $$M_{\mathrm{KV}}\propto T_{\mathrm{in}}$$

- 每条公式先讲人话，再说明它没有覆盖哪些服务层变量。

### 四、真实日志：讯飞为什么最像“我正在等”

- 先声明：这是作者 Pi 日志，不是厂商官方 benchmark，也不是不同供应商的速度排名。
- 讯飞主表（最近窗口，输入 0–128K）：

  | 输入 token | 样本数 | TTFT P50 | TTFT P90 | TPS P50 |
  |---|---:|---:|---:|---:|
  | 0–16K | 191 | 4.7s | 19.3s | 26.94 |
  | 16–32K | 449 | 6.6s | 19.6s | 26.79 |
  | 32–64K | 2,430 | 7.9s | 22.5s | 25.73 |
  | 64–96K | 1,868 | 11.8s | 26.1s | 26.53 |
  | 96–128K | 851 | 14.0s | 24.1s | 30.56 |

- 读表结论：输入变长时，首字等待明显变长；首字后的 TPS 并没有同步变快，说明“等首字”和“生成速度”是两堵不同的墙。
- 长尾说明：P90/P99 会受到路由、重试和服务负载影响；不能把每一次异常慢归因给上下文长度。
- 超过 128K 的讯飞样本不并入趋势结论：该组工作负载组成发生变化，TTFT 反而下降，正好提醒读者不要把分桶数据硬说成单变量因果。

### 五、2026 DeepSeek-V4 Pro 对照：更清楚的输入长度趋势

- `commandcode / deepseek/deepseek-v4-pro` 最近窗口 3,539 条请求。
- 4K–16K 输入的 TTFT P50 约 4.2 秒；64K–128K 约 6.9 秒；超过 128K 约 8.8 秒。
- 这组数据用来帮助读者看懂输入长度的影响，不和讯飞做“谁更快”的结论。
- 说明数据仍是用户侧观测：它混合了接口路由和服务负载，不能还原 GPU 内部每一步耗时。

### 六、四种加速手段，各自只解决一段

- 减少输入：直接降低 prefill 工作量和 KV Cache 压力；长系统提示词、工具说明和历史上下文是首字延迟的现实来源。
- KV Cache：避免 decode 阶段重复重算历史 token，但不等于历史查询免费；本文只讲长度关系，不声称讯飞日志测到了命中收益。
- 推测解码：小模型先猜多个 token，大模型并行验证；主要改善首字之后的 decode 速度，不能自动消除排队和长 prefill。
- 量化：减少权重/激活的存储和搬运压力，效果取决于硬件、kernel 和模型，不承诺固定倍数。
- 采样：Temperature、Top-k、Top-p 决定候选如何被选出，通常不是解决 TTFT 的第一工具；不要把“采样更快”与“服务链路更快”混为一谈。

### 七、读者如何判断一个 API 是否真的快

- 连续记录 TTFT 的 P50/P90，而不是只看一次成功请求。
- 把输入 token、输出 token、TTFT、TPS 分开记录。
- 按工作负载分组：短 prompt、长上下文、工具调用、长回答不能混成一个平均数。
- 根据真实延迟分布选择接口；模型能力、价格和首字体验是三个维度。

- 回答开头：API 慢不只因为 GPU 算得慢，用户等待的是连接、服务调度、prefill、decode 和流式传输叠加出来的结果。
