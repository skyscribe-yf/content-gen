你给大模型 API 发出一个请求。

你以为接下来发生的是：请求穿过网络，抵达 GPU，GPU 开始计算，然后把答案吐回来。

可现实常常是：十几秒过去了，屏幕上连第一个字都没有。

这时最容易怪模型太大，或者怪 GPU 太慢。但 API 调用和 GPU 之间，隔着一整条服务链路：网关要鉴权，路由要挑实例，请求可能要排队，还可能要等下一轮批处理；真正进入模型后，输入要先做一次 prefill，算出第一个 token，之后才进入逐 token 的 decode。

所以，调用大模型 API 时，时间到底花在了哪一段？

这篇先不拿实验室里的理想数字说服你。我们直接看作者自己日常使用 Pi 客户端时留下的真实请求日志，看看“首个 token 到底多久才来”。

## API 请求不是一根直通 GPU 的电线

把 API 想成一根电线，很容易漏掉真正决定等待时间的部分。

更接近现实的路径是：

```text
客户端
  ↓
网关、鉴权与限流
  ↓
模型路由与实例选择
  ↓
排队、批处理与调度
  ↓
prefill：读完整段输入
  ↓
decode：逐个生成 token
  ↓
流式返回到客户端
```

![大模型 API 请求经过服务链路和模型推理](01-api-request-route.png)

前面几步属于服务层，后面几步才是模型推理。

你发出的请求可能已经抵达服务商，但并不代表某一张 GPU 已经开始替你计算。它可能正在等待一个合适的实例，也可能在等调度器把更多请求拼进同一个 batch。

批处理有一个很现实的取舍：一批请求越大，GPU 越不容易空转，整体吞吐越高；但对其中某一个请求来说，它可能需要多等一会儿，才能进入下一轮计算。

这也是为什么“这家模型理论上更快”不一定等于“我今天调用它更快”。模型结构只是链路中的一段，服务负载、路由和网络也会进入用户的等待体验。

前面的文章一直在拆模型内部：预训练让模型学会预测下一个 token，[RLHF](https://mp.weixin.qq.com/s/NJDuCLAEfDpILf2J9D6qLQ) 和 [PPO](https://mp.weixin.qq.com/s/OEZtUhm8MT_En7enJo_8dw?token=2031108942&lang=zh_CN) 改变它如何根据反馈调整行为，[GRPO](https://mp.weixin.qq.com/s/t4sO-zC5v1_jq8hJT_YTGA) 和 [RLVR](https://mp.weixin.qq.com/s/NvemnDdtkinRKEbmtcckzA) 继续把训练推向可验证任务。

今天我们把视线移到推理现场：模型已经训练好了，为什么你还是要等？

## 先看首字：TTFT 才是用户遇到的第一堵墙

“首字延迟”是一个方便读者理解的说法，工程上更准确的名字是 TTFT，Time To First Token。

它测量的是：从客户端发起请求，到客户端收到第一个流式 token，经过了多久。

标题里的“首字”不一定真的是一个完整汉字。中文里的一个汉字可能被拆成多个 token，但读者感受到的现象是一样的：屏幕什么时候终于开始动了。

把时间写成公式：

$$
T_{\mathrm{TTFT}}=t_{\mathrm{first\ token}}-t_{\mathrm{request}}
$$

翻译成人话：从“我按下发送”到“我看到第一点结果”，这段时间就是首字延迟。

TTFT 和生成速度不是同一个指标。

- **TTFT 高**：请求像没有反应，用户不知道它究竟有没有收到。
- **TTFT 低、TPS 低**：很快冒出第一个字，但后面一个字一个字地挤出来。
- **TTFT 和 TPS 都高**：才是完整意义上的“快”。

我的 Pi 埋点会在第一次发起 provider 请求时记下开始时间，在第一次收到 assistant 的流式更新时记下首 token 时间。两者相减，就是日志里的 `ttftMs`。

这一定义很重要。它不是服务商机房里的纯 prefill 计时，而是用户真正经历的等待。DNS、TCP、TLS、网络往返、连接重试、服务端排队和模型计算，都可能落在这段时间里。

这也意味着它不能回答“GPU 纯计算用了几秒”。但它能回答另一个更有用的问题：**我调用这个 API 时，多久能看到第一点可用结果？**

首字之后，才进入逐 token 生成。假设模型一共生成 $N_{\mathrm{out}}$ 个 token，首字后的平均生成速度是 $r_{\mathrm{decode}}$，那么总耗时可以粗略写成：

$$
T_{\mathrm{total}}\approx T_{\mathrm{TTFT}}+\frac{N_{\mathrm{out}}-1}{r_{\mathrm{decode}}}
$$

这不是服务商的精确性能模型，只是一个很有用的拆账方法：先等首字，再等剩下的 token。

![首字延迟与首字后生成速度的区别](02-ttft-vs-tps.png)

## 第一个 token 为什么要等这么久？

模型生成第一个 token 时，不能只看最后一句话。

它要先把本次请求里的系统提示词、对话历史、工具描述和用户问题全部读进去。这一轮叫 prefill，可以把它理解成“开口前先把整份材料过一遍”。

在自回归模型里，输入长度记作 $T_{\mathrm{in}}$。如果注意力需要在输入位置之间建立两两关系，注意力部分的工作量会近似呈平方增长：

$$
C_{\mathrm{prefill}}\propto T_{\mathrm{in}}^2
$$

翻译成人话：输入长度翻一倍，注意力配对的工作量可能接近四倍。这里说的是 prefill 中注意力的主要增长项，不是说整个模型的每一项计算都严格等于平方增长；前馈网络、硬件 kernel 和批处理都会改变最终墙钟时间。

prefill 结束后，模型拿到最后一层的 logits，经过采样，才得到第一个 token。这个 token 送回客户端，用户才看到屏幕开始变化。

之后的 decode 看起来更像流水线：模型根据已有上下文生成下一个 token，再生成下一个 token。

为了避免每次都把历史重新算一遍，推理系统会把历史 token 的 Key 和 Value 存起来，这就是 KV Cache。它省掉了重复计算，但这份缓存并不是免费的。历史越长，缓存里要保留的内容越多：

$$
M_{\mathrm{KV}}\propto T_{\mathrm{in}}
$$

翻译成人话：KV Cache 的存储压力随上下文长度线性增长；它解决的是“不要重复重算旧历史”，不是“历史长度不再影响成本”。

所以，长上下文会同时把两笔账推高：prefill 要读更长的输入，decode 要面对更长的历史缓存。

## 真实日志：讯飞线路为什么最像“我正在等”

下面的数字来自作者实际使用 Pi 时记录的请求日志，不是厂商官方 benchmark，也不是把不同供应商混在一起做速度排名。

截至写作快照，完整日志覆盖 2026 年 5 月 4 日到 8 月 2 日，共解析出 262,796 条有效记录，另有 1 行解析失败，不纳入统计。正文主统计窗口取最近两周，也就是 2026 年 7 月 20 日到 8 月 2 日，共 25,090 条有明确 provider 和 model 标识的请求。

讯飞线路是这批数据里最能代表“用户感觉很慢”的案例。`xunfei / xopglm51` 在主窗口里有 6,261 条请求。我们按输入 token 数分桶，只看 128K 以内的主要工作负载：

| 输入长度 | 样本数 | TTFT P50 | TTFT P90 | TPS P50 |
|---|---:|---:|---:|---:|
| 0–16K | 191 | 4.7 秒 | 19.3 秒 | 26.94 |
| 16–32K | 449 | 6.6 秒 | 19.6 秒 | 26.79 |
| 32–64K | 2,430 | 7.9 秒 | 22.5 秒 | 25.73 |
| 64–96K | 1,868 | 11.8 秒 | 26.1 秒 | 26.53 |
| 96–128K | 851 | 14.0 秒 | 24.1 秒 | 30.56 |

![讯飞线路不同输入长度下的 TTFT P50 与 P90](03-xunfei-ttft-buckets.png)

先看中位数。

输入从 0–16K 增长到 96–128K，TTFT 中位数从 4.7 秒升到 14.0 秒。首字等待变长了将近 3 倍，但首字之后的 TPS 仍大多在每秒 25–30 个 token 左右。

这正好把两堵墙分开：长输入主要先撞上 prefill 和服务调度，首字之后的生成速度是另一件事。

再看 P90。

0–16K 输入的 P90 已经是 19.3 秒，64–96K 输入的 P90 达到 26.1 秒。也就是说，即使输入不算最长，仍然有一部分请求会让用户等很久。

这部分不能简单归因给上下文长度。连接重试、路由变化、服务负载和批处理等待，都可能制造长尾。日志能真实记录用户经历了多久，却不能从一个 TTFT 数字里把每个服务端阶段准确切开。

还有一个容易被误读的地方：超过 128K 的讯飞样本，TTFT 反而下降了。它不是“上下文越长越快”的反例，而是提醒我们，这一组请求的工作负载组成、路由或服务状态已经发生变化，不能把分桶结果硬说成单变量因果。

真实数据的价值，恰恰在这里。它没有替我们制造一个漂亮的单调曲线，而是把 API 服务的复杂性原样露了出来。

## 2026 DeepSeek-V4 Pro 对照：输入长度的影响更清楚

为了让输入长度这条线更容易看清，再看一组 2026 DeepSeek-V4 Pro 的真实请求记录。

在 `commandcode / deepseek/deepseek-v4-pro` 这条线路上，最近两周有 3,539 条请求。4K–16K 输入的 TTFT 中位数约为 4.2 秒；64K–128K 输入约为 6.9 秒；超过 128K 输入约为 8.8 秒。

这组数据比讯飞主案例更接近我们想观察的趋势：同一模型线路里，输入越长，首个 token 通常越晚出现。

但它仍然是用户侧观测，不是 GPU 内核剖析。它混合了路由、排队、连接和服务负载，所以我们可以说“这个工作负载里看到了输入长度与 TTFT 的相关趋势”，不能说“8.8 秒全部由 prefill 贡献”。

用一个案例讲真实体验，用另一个案例看清输入长度，是比做供应商速度排行榜更诚实的方式。

## 四种加速手段，各自只解决一段

知道慢在哪里，才能知道该用哪把扳手。

![四种推理加速手段各自作用的阶段](04-inference-acceleration-map.png)

### 第一把扳手：先减少送进去的东西

如果首字延迟里有一部分来自 prefill，那么最直接的办法就是减少输入 token。

长系统提示词、重复的工具说明、已经不再重要的历史对话，都会在每次请求里重新占用输入长度。把历史压缩成摘要、只保留相关文件、把稳定前缀放到可复用的位置，都可能降低 prefill 的负担。

代价也很直接：删掉上下文可能损失信息。压缩不是把 token 越砍越好，而是判断哪些信息值得继续占用这笔延迟预算。

### 第二把扳手：KV Cache 让模型别反复重算历史

在 decode 阶段，KV Cache 让模型保留已经算过的 Key 和 Value。

它像把会议纪要放在桌上，后面继续讨论时不必从头听录音。可是纪要越写越厚，查找和存储仍然有成本；上下文很长时，KV Cache 会吃掉显存，也会影响每一步的访存压力。

这就是为什么 KV Cache 能降低重复计算，却不能把长上下文变成零成本。它解决的是“重复算”，不是“历史不存在”。

需要特别说明：这篇的讯飞日志几乎没有接口报告的缓存命中数据。`xunfei / xopglm51` 的 6,261 条记录里，只有 1 条出现正的 `cacheReadTokens`；`xunfei-ex / xopglm51` 的 3,657 条记录里没有命中记录。

而且，接口里的 `cacheReadTokens` 也不等于 GPU 内部的 KV Cache 命中。因此本文不从这批日志推导缓存带来了多少提速。

### 第三把扳手：推测解码减少串行等待

普通 decode 一次生成一个 token。大模型每生成一个 token，都要等上一步的结果出来，再继续下一步。

推测解码换了一种分工：让一个更小的草稿模型先猜一小段 token，再让目标模型一次性检查这段猜测。猜对的部分可以一起接受，目标模型就少走几轮串行生成。

它主要改善的是首字之后的 decode 阶段，不会自动消除请求排队，也不会让一段很长的输入凭空跳过 prefill。草稿模型的质量、接受率、额外开销和硬件 kernel 都会影响最终结果，所以没有一个脱离场景的固定提速倍数。

### 第四把扳手：量化减少搬运压力

模型权重和中间数据如果用更低的数值精度表示，需要存储和搬运的字节更少。在受支持的硬件和 kernel 上，这可能减轻显存带宽压力，让 decode 更快，也可能让更大的模型装进同一张卡。

但量化不是一个“位宽减半，延迟也减半”的开关。实际收益取决于模型结构、量化方案、硬件、算子实现和 batch 形状。没有同一模型、同一硬件和同一工作负载的对照数据，就不该把某个倍数写成普遍结论。

### 采样参数不是首字延迟的万能药

Temperature、Top-k 和 Top-p 决定模型从候选 token 中怎么选。

它们主要影响的是输出分布和回答风格，不是网关排队，也不是输入 prefill。把 Temperature 调低，可能让回答更稳定，却不会让一个正在排队的请求立刻拿到 GPU。

这也是推理优化里容易混淆的地方：采样策略属于“选哪个 token”，KV Cache、推测解码和量化属于“怎样更快地算出 token”，而服务调度属于“什么时候轮到这个请求”。三者不能互相替代。

## API 用户真正能做什么？

如果你只记录一次总耗时，很多问题会混在一起。更有用的做法是给每次请求记录四个字段：输入 token、输出 token、TTFT 和 TPS。

然后按工作负载分组。

短 prompt 和长上下文不要混在一个平均数里；普通问答和连续工具调用不要混在一起；短回答和长代码生成也不要用同一个“快慢”结论。

接着看 P50 和 P90。

P50 告诉你典型请求的体验，P90 告诉你十次里最慢的那一两次大概会有多难受。只看平均数，很容易把长尾藏掉；只看一次最快响应，又会把偶然情况当成能力。

最后再决定优化方向：

- TTFT 高：先查输入长度、接口路由和排队体验。
- TTFT 还可以、TPS 低：再看 decode、KV Cache、量化或推测解码。
- P90 特别高：不要急着怪模型，先排查重试、服务负载和工作负载混合。

这套方法不要求你知道服务商用了几张 GPU。你只需要记录自己真正经历的时间。

## 大模型原理主线走完，下一站回到国产模型

现在回头看，API 的一次回答并不是孤立发生的。

分词决定输入有多少 token，嵌入和位置编码把它们送进 Transformer，注意力和 FFN 处理上下文，预训练让模型学会预测，SFT 和 RLHF 让它更听懂指令，PPO、GRPO 和 [RLVR](https://mp.weixin.qq.com/s/NvemnDdtkinRKEbmtcckzA) 再用反馈改变行为。

到了推理现场，这些训练成果要面对另一笔账：输入要多久读完，历史要怎么缓存，token 要多快生成，结果要经过多少层服务才能回到你的屏幕。

所以，调用大模型 API 不是直接和 GPU 对话。你等待的，是一整条链路共同交付的第一个 token。
