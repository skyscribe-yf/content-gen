# MTP：一次猜两个词，推理快1.8倍

## 文章定位

- 本篇是 DeepSeek 技术解密系列的新一篇，主线是 **MTP（Multi-Token Prediction，多 Token 预测）——训练时为每个位置多配一个「侧头」预测下一个词，推理时这个侧头变成投机解码的草稿机，让 DeepSeek-V3 的生成速度提升 1.8×**（V3 Technical Report §2.2 + §5.4.3 + ISCA'25 论文 2505.09343）。
- 兑现 Indexer 篇（08-11）文末预告：「Indexer 省的是推理时翻档案的时间，MTP 省的是猜词的时间」——时间账线收尾：上一站省 prefill 时间，这一站省 decode 时间。
- 主线冲突：**串行生成的死结**——大模型一次只能猜一个词，猜完才知道下一个词是什么，每一步都浪费在等待上；解码阶段 GPU 算力闲置，瓶颈在「一步一词」的节奏本身。
- 啊哈时刻（点破式）：**训练时答案就在手里**（语料里全是真实词），所以模型能用真实词当条件，一次前向并行猜一串；推理时没有真实词，只能让侧头先猜一串、主头一次验一串——猜和验互为镜像。
- **同题不同解对照（GLM-5.2，系列惯例第 8 节）**：DeepSeek 保守路线（depth=1，只多猜一个）vs GLM-5.2 激进路线（5 个 draft tokens + IndexShare 复用第一步索引/KV + 拒绝采样 + 端到端 TV loss，接受长度 4.56→5.47、+20%）。对照焦点：**训练-推理一致性**——GLM-5.1 推理时草稿步的 KV 是目标模型和草稿模型的混合体（训练时从未见过这种输入），GLM-5.2 用 IndexShare 让草稿步只看到目标模型的 KV，消除不一致。
- **归属校准（系列惯例）**：MTP 不是 V3 发明——Gloeckle et al. 2024（Meta，独立输出头并行预测 D 个额外 token）是源头；V3 的增量是「串行模块保因果链」的改造（每深度一个共享 embedding/输出头 + 一个 Transformer block），并把 MTP 用于大规模 MoE 训练（信号加倍 + 消融性能白赚）。V4 原样继承（depth=1，HF config `num_nextn_predict_layers: 1`）。GLM-5.2 走的是另一条进化线（从 EAGLE/多步草稿出发，不是 DeepSeek 的 depth-1 设计）。
- **防炒冷饭边界**：08-03 推理加速篇没碰投机解码（已核查），投机解码机制本篇首次展开；预训练篇（07-27）只提 next-token 概念，teacher forcing 细节未讲过。与 Indexer 篇边界：Indexer 省的是「翻档案」（KV 检索）时间，本篇省的是「猜词」（自回归步数）时间，机制完全不同。
- 数学深度：B- 级。不推公式，只讲三个关键结构（侧头拼接条件、接受率账、草稿步 KV 复用），每个都配具体数字例子（如 85-90% 接受率 → 每步平均 1.85 词 → 1.8× TPS）。
- **不做实验（作者决定，2026-08-09）**：experiment.py 方案已放弃——CPU 训练不动、AutoDL 上玩具模型侧头与主头 top-1 一致性上不来（接受率≈0，小模型侧头单 block 拟合不足）。正文直接引用论文数字（V3 §5.4.3 接受率 85-90%/1.8× TPS；GLM-5.2 消融 4.56→5.47）。「接受率→每步推进→加速比」的账用解析方式在正文呈现（几何分布：p 接受率时每步平均 1/(1-p) 词）。
- 下一篇预告：08-13 并行策略（训练系统线入口）——过渡线：单卡再快也有极限，下一站讲 1000 块 GPU 怎么分活。
- **开源可核验声明**：V3 2024-12 开源（MIT），V4 2026-04 开源（MIT，HF transformers 2026-05-02 支持，config 里 `num_nextn_predict_layers: 1`）；GLM-5.2 2026-06-16 开源（MIT，config 里 `index_share_for_mtp_iteration`）。正文数字全部来自技术报告与 config.json，可自查。

## 核心结论

1. **死结**：自回归生成一次只能猜一个词——第 k+1 个词的预测依赖第 k 个词的结果，推理时只能一步一步来；解码阶段每步只有一次前向，大模型算力大部分闲置（memory-bound），瓶颈是步数本身。
2. **训练时答案在手**：训练语料里每个位置的真实词都是已知的，所以模型可以「用真实词当条件」一次前向并行预测一串——这是 teacher forcing 的延伸，MTP 在训练时就是这么干的（每个位置多配一个侧头，条件 = 上一深度表示 + 真实目标词 embedding，拼接后过一个 Transformer block）。
3. **推理时的镜像**：推理时没有真实词，侧头只好自己猜——猜出一串候选，主模型一次前向把它们全部验证（投机解码）。接受率 85-90%（V3 §5.4.3），每步平均推进 1.85 个词，TPS 提升 1.8×。
4. **侧头从哪来（训练侧白赚）**：MTP 本是为训练设计的——一次前向两个交叉熵（主头+侧头），信号密度加倍、数据效率提升；15.7B/228.7B 两档消融普遍提升 benchmark（V3 §4.5.1 Table 4）。推理时本来可以直接丢弃 MTP 模块（推理成本为零），但 DeepSeek 选择把它翻出来当草稿机——「训练时白赚的信号，推理时白赚的速度」。
5. **为什么敢只猜一个（depth=1）**：V3 选择保守——每深度一个串行模块保持因果链（与 Gloeckle'24 的独立并行头不同），多猜一个词的边际收益大、边际成本小（侧头只有 1 个 block）；更深的多步预测收益递减（GLM-5.2 用 5 步换来 +20% 接受长度，但那是建立在 IndexShare 消除了训练-推理不一致的前提下）。
6. **GLM-5.2 的激进路线（对照）**：5 个 draft tokens + IndexShare（第一步跑 indexer，后续步骤复用 topk 索引）+ KVShare（草稿步 KV 全部来自目标模型，消除 GLM-5.1 的混合 KV 不一致）+ 拒绝采样 + 端到端 TV loss；接受长度 4.56→5.47（+20%，coding 场景）。代价：草稿步多了，每步验证的计算也多了；收益：接受率更高、加速更猛。
7. **进化链归属**：Gloeckle'24（Meta，并行独立头）→ DeepSeek-V3（串行模块保因果链，depth=1，训练信号加倍）→ V4（原样继承）；另一边：EAGLE（草稿模型思路）→ GLM-5.1（多步 MTP，训练-推理不一致）→ GLM-5.2（IndexShare/KVShare 消除不一致）。两条线在「投机解码」汇合。

## 文章结构（预计 3000-3200 字）

### 开头（150 字）
承接 Indexer 预告的「时间账」线：上次讲了翻档案的时间（Indexer），这次讲猜词的时间（MTP）。悬念：为什么模型生成时一次只能猜一个词，而训练时却能一次猜一串？

### 一、死结：一步一词，GPU 在等词（400 字）
- 自回归的串行本质：猜完第 1 个词才知道第 2 个词的条件。
- 解码阶段的真实瓶颈：不是算力（每步只有一次前向，算力大量闲置），是「步数」本身——生成 1000 个词就要 1000 次前向。
- 数字例子：一个 37B 激活的模型每步前向约几十毫秒，但其中大部分时间 GPU 在等内存（memory-bound），算力利用率很低。
- 引入悬念：能不能一次前向猜两个词？

### 二、点破：训练时答案就在手里（500 字）
- 训练时语料里全是真实词——预测第 k+1 个词时，第 k 个词是已知的（teacher forcing）。
- MTP 的结构（V3 §2.2）：主头照常预测下一个词；每个位置额外挂一个侧头（MTP 模块 = 共享 embedding + 共享输出头 + 一个 Transformer block + 拼接投影），输入 = 上一深度表示 + 真实目标词的 embedding，输出预测「下下一个词」。
- depth=1 的含义：主头猜「下」一个，侧头猜「下下」一个 → 一次前向两个交叉熵。
- 与 Gloeckle'24 的区别：不搞独立并行头，用串行模块保因果链（这是 V3 的工程化增量）。

### 三、推理镜像：猜一串，验一串（500 字）
- 推理时没有真实词 → 侧头自己猜：侧头（草稿机）先猜一串候选，主模型一次前向把它们全部验证（投机解码）。
- 接受率账：第二个词预测的接受率 85-90%（V3 §5.4.3）→ 每步平均推进 ≈1.85 个词 → 1.8× TPS。
- 为什么敢信侧头：侧头是主模型自己的「预演」，与主模型共享 embedding 和输出头，猜的风格天然接近——不像外挂小模型（draft model）有风格漂移问题。
- 实验预告位。

### 四、侧头从哪来：训练时白赚的信号（400 字）
- 起源：MTP 本为训练设计——信号加倍（两个交叉熵）、数据效率。
- 消融证据（V3 §4.5.1 Table 4）：15.7B/228.7B 两档，多数 benchmark 提升（BBH 39.0→41.4、HumanEval 20.7→26.8 等），推理时丢弃模块、成本为零。
- 双用设计：训练完不丢，翻出来当草稿机——「训练白赚信号，推理白赚速度」。

### 五、同题不同解：GLM-5.2 的激进版（500 字）
- GLM-5.2 的选择：5 个 draft tokens（vLLM `num_speculative_tokens 5`，EAGLE 驱动），MTP 从 3 步扩到 5 步。
- 激进带来的新问题：多步草稿时，第 2 步起的输入是模型自己猜的 token，KV 缓存变成「目标模型 + 草稿模型」混合体——训练时从未见过（GLM-5.1 的痛点）。
- GLM-5.2 的解法（IndexShare + KVShare）：只在第一步跑 indexer，后续步骤复用第一步的 topk 索引和 KV → 草稿步只见目标模型的 KV，训练-推理一致。
- 配套：拒绝采样 + 端到端 TV loss；接受长度 4.56→5.47（+20%）。
- 对比落点：DeepSeek 保守（depth-1 够用，多步收益递减）；GLM 激进（用 IndexShare 解决多步的坑）。两条路线，同一个目标：让「猜」跟上「验」。

### 六、接受率账：猜得准，才快得起来（350 字）
- 解析账（不跑实验，论文数字直接算）：接受率 p 时每步平均推进 1/(1-p) 词（几何分布）——p=0.85 时 6.7 词/7 步 ≈ 每步 1.85 词 → 加速比 1.8×；p 掉到 0.5 时每步只有 2 词，加速比 2× 上限但草稿成本吃掉大半；p=0 时（草稿全拒）加速比 1.0×，白算。
- 这正是实验放弃的教训：玩具模型侧头没学好（接受率≈0），投机解码白跑——反向验证「接受率决定加速比」的账。
- 官方数字：V3 接受率 85-90%（§5.4.3）→ 1.8× TPS；GLM-5.2 接受长度 4.56→5.47（+20%）。

### 结尾（200 字）
- 收束时间账：Indexer 省 prefill 的翻档案时间，MTP 省 decode 的猜词时间。
- 预告 08-13：单卡再快也有极限——MTP 让每一步走得更远，但下一步要讲 1000 块 GPU 怎么分活（并行策略）。
- 开放式问题：如果你来设计，猜几个词最划算？接受率和草稿成本怎么权衡？

- V3 §5.4.3：接受率 85-90% → 每步平均 ≈1.85 词 → 1.8× TPS
- 解析账：接受率 p → 每步 1/(1-p) 词（几何分布），正文 §六 呈现
- GLM-5.2 消融：接受长度 4.56→5.47（+20%，coding 场景）
- 诚实备注：玩具模型接受率≈0 的实验观察可作为正文一句「为什么小模型演示不出效果」的反向例证（草稿质量决定一切）
