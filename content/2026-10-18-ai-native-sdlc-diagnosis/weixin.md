## 一、营销口号打回原形

我高强多实践 AI coding 已经超过两年了。工具链走了一整轮。

早期的 GitHub Copilot，突然爆火的 Claude Code。

开源社区声名鹊起但又一言难尽的 OpenCode、pi coding agent。

以及当红的 Codex 和更 agent 的控制面板 Paseo。

一个深刻的体会是：

**当你想要按照软件工程的流程要求去开发和交付正儿八经的软件的时候，很多营销宣传的口号都会立马被打回原形。**

AI coding 工具本身的突飞猛进，依然不能解决软件工程最核心的一些挑战。

实际交付依然会有很多困难。

只不过是以前 coding 自身成为占据最多资源的瓶颈。

这个瓶颈被很大程度上解决了之后（尽管也解决的不是很理想），其他新的瓶颈马上就浮现上来了。

从 coding 方面来看。

商业软件所期望的各种非功能约束，领域特定的需求范式，软件需求和测试如何拉通对齐，这些核心挑战其实都远远称不上被完美解决。

有的企业甚至提出很朴素的想法。

尝试将各种文档、材料一股脑丢给 AI，使用各种 RAG、Graph 等技术，尝试让 coding agent 一把梭哈。

然而这种方式很快就会碰上模型本身"锯齿智能"的弱点。

确定性世界里人们积累的大量经验，想无缝照搬到 AI agent 上。

期望用许愿式的方法直接得到期望的产品，基本上都是一厢情愿的过度简化。

## 二、Anthropic 的诊断：瓶颈从代码搬到了流程

2026 年 8 月。

Anthropic Applied AI 团队发布了一份 54 页的《AI-native SDLC Playbook》。。。它的诊断链是这样的：

1. 传统 SDLC 是为"写代码最贵"的时代设计的。PRD、估点仪式、产品安全评审的存在，是为了在"几周~几个季度"的开发周期里强行对齐。
2. 现在写代码的成本断崖下跌，但这些仪式没跟着变。

approval gate、review、handoff、policy 都还在以人的速度运行。
3. 于是**收益被流程吃掉**（这是 Amdahl 定律的形态）。
4. 结论：不是把 Claude 塞进旧流程，而是**重建流程**。

一句话概括他们的取舍：**保留旧的控制目标，更换执行手段。**

 playbook 把整条 SDLC 重建成一个以"提交到版本控制的 artifact"为交接件的 agent 循环。

人的注意力从"逐段干活"上移到"守闸门"。

** committed artifact 链**是贯穿主线：

```
intent.md → spec.md → plan.md → diff + tests → PR + review findings → incident record。
```

每个阶段结束时把一个 artifact 写进版本控制，下一阶段开始时读它。这条 commit 链同时就是审计轨迹。

**知识载体三分法**（我认为是最可迁移的一条）：

- `CLAUDE.md` — 一次性的、每会话都读的**工作知识**（命令、约定、常犯错误），控制在一页以内
- **skill** — 必须**一致执行**的机构知识 / 政策，有具名所有者，中心化更新
- **hook** — **不许有任何例外**的政策的确定性执行层

三者是"建议 → 强制"的梯度，而不是三种风格的偏好。

六阶段对照：

| 阶段 | 传统 | AI-native |
|---|---|---|
| Plan | 委员会收需求、workshop + sign-off | Claude 综合痛点落成 `intent.md` |
| Design | 分析师写 spec，设计师再解析 | 需求与设计压缩成一次 agent 会话，政策以 skills 作约束 |
| Build | 代码与测试手写 | 先有被接受的 plan 才动手；护栏是代码不是习惯 |
| Test | QA 作为阶段边界的闸门 | evals 织进实现过程；每个会话先自查再交人 |
| Deploy | 人逐行 review，治理靠 review 周期 | 多层 agentic review，人工 review 只留给受监管/关键代码 |
| Maintain | 人盯生产 bug | agent 盯线上；控制带被突破即诊断并写成新的 `intent.md` |

## 三、Anthropic 自家的数据与踩坑

作者 Jason Clinton（Deputy CISO）给出的数字来自他们自己跑过的系统：

| 数据 | 值 |
|---|---|
| 工程师人均季度代码产出（2021–2025） | **8×** |
| Claude 撰写并 merge 进 codebase 的代码占比 | 约 **80%** |
| 由内部版 Claude Tag merge 的代码占比 | **超过一半** |
| PR 中获得实质性 review 评论的比例 | **16% → 54%** |
| 过去 claude.ai 事故背后 bugs 里，现有自动化本可抓到的比例 | 约 **1/3** |

**踩坑教训**（价值密度最高）：

- **多条窄 scope 的 review agent > 一个"超级安全 agent"**：它们不共享偏见和盲点（这点后面会修正）。
- **新 agent 一律先跑 shadow mode**，只发评论等人批准；并且要 red team 它们。
- **agent 的身份边界要包含"它对其他 agent 的访问权"**。作者的亲身教训：一次模型升级后，**incident response agent 自己主动在 Slack 上找上另一个能写代码的 Claude 实例，请它推修复**——虽然按设计被人工闸门拦住，但这让他们改为"**把边界画在访问权限和动作上，而不是画在模型的指令或我们以为模型能做什么上**"。现在 Anthropic 内部 Slack 上 agent-to-agent 通信是常态。
- 单用途身份 + 最小权限：那个事故处理 agent 只有三个权限（写新文档、在公司频道发帖、读生产日志），**不能自动部署**。

安全篇的收尾金句：**安全工程师的工作从"监控 bug"变成"监控循环"**。

## 四、生产数据怎么说

Anthropic 的数据来自自己，外部证据呢？

**Google 的生产 C++ 研究**（12 个月）：build 失败 1.3×、revert 0.9×、blocking threads 1.92×；**review 努力度代理指标与低效代码存活没有相关性**。也就是说，"我们 review 得很认真"无法用来证明代码质量被守住了。

**Borg et al. 的 449 人受控实验**：AI 开发者与非 AI 开发者在可维护性上**无系统性差异**。

**GitClear 的 623M 变更**（厂商数据、相关分析，非因果）：函数连通性 −35%、重构行移动 −70%、块重复 +81%。

这两组数据矛盾。

我的解读是：**"可维护性"目前无法被现有指标捕捉**。

Google 那篇也指出"评估 AI 代码的认知摩擦无法被现有指标捕捉"。

Borg 的实验窗口太短（单次任务、小时级），GitClear 是 4 年聚合信号但相关分析。可维护性的真实衰减时间尺度是 3–10 年，所以"AI-native 让软件更好维护了吗"这个问题，目前无法回答。

## 五、MECE 六问：playbook 真正扎实的只有"能"一格

Anthropic playbook 是好的起点，但它的覆盖有盲区。用 MECE（Mutually Exclusive, Collectively Exhaustive）做一次完备性枚举。

把"把 SDLC 改成 AI-native"这一行动的全部合理质疑摊开：

对一项行动能追问的只有六个问题，回答方式互不相同：

| 轴 | 问题 | 回答靠什么 |
|---|---|---|
| **能** | 做得到吗 | 实验、能力实测 |
| **值** | 划算吗 | 算账 |
| **该** | 允许吗 | 法规、伦理、责任 |
| **愿** | 会真的发生吗 | 组织行为、采纳 |
| **撑** | 长期撑得住吗 | 长期观测 |
| **知** | 我怎么知道做对了 | 实证设计 |

playbook 的覆盖度：

| 轴 | 覆盖度 | 空白 |
|---|---|---|
| 能 | **高** | 跨 harness 原语不对称、lock-in、底座模型能力未实测 |
| 值 | **近零** | 成本结构、验证成本、单位口径 |
| 该 | **仅内部治理** | 外部监管、责任、IP、"哪些不该做" |
| 愿 | **近零** | 变更管理、采纳阻力、既得利益 |
| 撑 | **零** | 人、junior、技术债、平台容量 |
| 知 | **给了度量，但未质疑度量** | 相关性失效、时间长尺度、度量扭曲 |

**playbook 本质上是可行性手册**——它只回答了"能"这一格，外加半格"知"。这不是写得差，是定位不同。

**权重排序**（MECE 不提供权重，这是我的判断）：

> 能 < 值 < 该 < 愿 < 撑 < 知

前两格（能、值）一两年内会自然收敛——成本随模型降价下降、harness 原语随标准统一。后三格（愿、撑、知）是这一轮真正的风险所在，而它们的反馈延迟都在 3–10 年。

Anthropic 公司根据自己企业内部实践推出来的 AI 原生 SDLC 方案，推出来已经有挺长时间了。

这些来自于最前沿公司内部的软件工程实践，

是否真的可以推广到很多传统商业软件公司，用于助力其他非 AI 开发公司的业务，我个人一直是持有大大的疑问的。

毕竟软件本身的领域复杂性，就不是千篇一律的，充满了模糊空间，

而 LLM 技术本身，从底层原理上看，就非常容易受到不确定性本身的影响——

你给他的东西越含糊不清，他的困惑度就越大，很容易给你生成出来一大堆看似正确，其实内行看来错的离谱的成品出来。

## 六、【知】的深水区：冗余 ≠ 独立性

Anthropic 在安全篇建议"多条窄 scope 的 review agent > 一个超级 agent"。

论据是"它们不共享偏见和盲点"。

**但这只做到角色分离，没做到误差去相关。** 同一底座模型意味着它们共享更深层的盲点。冗余 ≠ 独立性；多样性才是独立性的来源。

**Kish 有效样本量**：

$$n_{\text{eff}} = \frac{k}{1 + (k-1)\bar{\phi}}$$

Apple 实测 $\bar{\phi}=0.39$、$k=9$ 时：

$n_{\text{eff}} = 9/(1+8\times0.39) = 2.18$。**9 个判官 = 2.2 票。** 全票一致时错误率 9.1%，独立假设下应为 0.02%——差约 455 倍。

**共失败天花板** $\beta = P(\text{池中所有模型都错})$：任何路由、投票、cascade 的精度上限 = $1-\beta$。

**推论**：只能用一个底座模型时，$\bar{\phi} \to 1$，$n_{\text{eff}} \to 1$，$\beta \to$ 单模型的漏检率。在这种情况下增加 agent 是纯浪费——数学上为零，不是效果打折。

Cornell 在 350+ 个模型上测得：两个模型都出错时，有 60% 的概率错在同一处。**越强越相关**——更大更准的模型误差高度相关，即使架构与 provider 完全不同。

## 七、收尾

各种软件千人千面，各种技术上的非技术上的约束混杂期间，是否所有的东西都可以用堆 token 来完成，这是很多做 agent 评测和玩具 coding 项目的人从来都不会关心的事情。

不过毕竟，它山之石可以攻玉，对于 Anthropic 这种工作方式，探讨和研究的价值还是很高的。

反馈延迟决定 agent 行为形态、成本核算决定混合架构有没有最优点。

review 独立性决定"多开几个 agent 互相审"是不是纯浪费。
