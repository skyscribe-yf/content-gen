## 交付句（全文唯一想证明的事）

> **派子代理不是为了跑得快，是为了不让「你已经不再需要的东西」继续参与你之后的每一次判断。**
> 而且：隔离的对象不是垃圾，是注意力预算——Claude 擅长忽略**无关**的内容，但**相关**的内容照样拖垮它。

## 反直觉答案（恢复期 B.2 的交付物）

1. **模型不是塞满才变笨的**：长程搜索实证显示，模型在**远未耗尽上下文窗口之前**就给「放弃」或「不确定的错误答案」——是**先放弃**，不是先超限。
2. **争议双方测的不是同一个东西**：正方测单轮长输入（needle-in-a-haystack），反方测预注册的固定针/增长干草堆因子；而 agent 的真实上下文是**多轮、多源、渐进累积**的。所以即使 Context Rot 被证伪，隔离仍然成立。

## 拿得走的工程结论

**按「参与度」派活，不按长度。** 派子代理之前问一句：**这份内容，我后面还要不要让它参与每一次判断？**
要 → 留在主上下文（哪怕它很长，比如架构决策、未解决的 bug 描述）；不要 → 扔出去（哪怕它很短，比如一段日志）。
与 10-08 的「易分发派出去、要收敛自己干」**不同轴**：那条看任务耦合度，这条看**上下文参与度**。

**先分清症状，再下药。** 撞车（冲突/互相干扰）→ 转舵指令拉回清晰上下文；涣散（太长）→ fork 或压缩。
而且压缩能力**因 agent 而异**：Codex 可压三四次，很多 agent 压一两次就不堪大用。

## 结构（6 节，叙事弧线，零导航开头）

### 开头钩子（零导航，场景对比型，~200 字）

跑了一夜的 agent 停在中途。窗口用了一半不到，工具调用记录正常，没有报错、没有超限——但它的结论已经开始自相矛盾：同一个问题，先给 A，隔十几步又给 B。

> **它没崩，也没满，它是先放弃了。**

*（[本槽留作者原声：作者亲眼见过的一次「窗口没满就先放弃」）](#作者原声槽)*

### 一、它没崩，也没超限——它是先放弃了（~450 字）

- 一手来源：**arXiv 2606.29718《Diagnosing and Mitigating Context Rot in Long-horizon Search》**（上海交大 / SII / GAIR）
- 实测对象是**国产开源模型**：GLM-4.7、GLM-5.0、Qwen3.5-397B-A17B（256K 窗口）、MiniMax-M2.5（约 200K 窗口）；**300 条轨迹**、3 个基准
- 论文核心现象（意译）：*在上下文很长时，模型**远未耗尽上下文窗口**就会放弃，或给出**不确定的错误答案***
- 争议细节爆点：该论文**主动排除闭源模型**（GPT-5.4 / Claude Opus 4.7），理由是它们把推理过程加密，「无法分析它为什么失败」
- 🔗 内链：《每步都靠猜，上百万Token的长任务怎么不跑偏》
- 落点：所以你看到的「变笨」，可能根本不是变笨

### 二、先说正方：一家做向量库的公司，比模型厂更早测出来（~600 字）

- **Chroma**《Context Rot: How Increasing Input Tokens Impacts LLM Performance》（2025）：**18 个模型**（GPT-4.1 / Claude 4 / Gemini 2.5 / Qwen3 等）、**194,480 次 LLM 调用**、69 次拒答（0.035%）
  - 「即使在这些最小条件下，模型性能仍随输入变长而退化，且方式不均匀」
  - **加一个干扰项就掉分，加到四个继续叠加**
  - **针与问题的相似度越低，随长度退化得越快**
- **Anthropic**《Effective context engineering for AI agents》（2025-09-29，官方一手）：上下文是**有限资源**、边际收益递减；模型有 **attention budget**；token 两两关系是 **n²**
- **arXiv 2601.15300**（2026-01，Qwen2.5-7B）：临界阈值 **43.2%**（40–50%，std 1.2%）；越过后 F1 **0.556 → 0.302（−45.5%）**，Cohen's d = **8.2**；RoPE 理论预测 49%
- **Boolean**《Context Rot Quantified》（2026-09-15）：**相关**上下文下 Claude Opus 5 **0.50 → 0.425（0.55MB）→ 0.398（1.05MB）**，GPT-5.6 Sol **0.347 → 0.26**；而**无关**上下文下 Opus 几乎不掉（0.50 平到 1.25MB）
- 🔗 内链：《为什么AI上下文越长越慢？两道数学硬墙一次讲透》+《GLM-5.3-Flash 和 Qwen4 架构：注意力为什么都不够用了？》
- 反直觉子结论：**不是垃圾太多，是内容太相关**
- **落点（作者 2026-10-10 槽 2 升级）**：这些阈值都是**统计意义**上的——论文能告诉你什么时候会掉，**不能告诉你什么时候正在掉**。现场没有任何可观测信号标出「本次会话已越过临界点」，只能凭感觉和经验（进作者原声）

### 三、反方：150k token 以内，受控实验测不出来（~450 字）

- **Zenodo 预印本《Is Context Rot Real? A Controlled, Cross-Provider Null for Length-Driven Degradation in Frontier Models up to 150k Tokens》**（2026-06-18）
- 4 个模型：gpt-5.5 / gpt-5.4 / gpt-5.4-mini / claude-sonnet-4-6
- 预注册的**固定针 / 增长干草堆因子设计**，交叉上下文体量与针位置
- 数字：注册网格 **12,570 次试验**；**7,330** 条有针试验中 **48 次失败**；准确率 **0.9935**；失败率单侧 95% 上界 **0.87%**；最高 **150,000 token**
- 结论（论文原话意译）：在这些探针上**观测不到长度驱动的退化**
- 落点：这一巴掌打得很响——它直接说：你们测出来的，可能不是长度

### 四、两边测的不是同一个东西（~400 字，收口）

- 2606.29718 原话意译：现有 Context Rot 研究多聚焦**单轮长输入**（needle-in-a-haystack），与 agent 任务显著不同——agent 的上下文通常是**多轮、多源、渐进累积**的
- 所以：null 那篇测的是「一根针放在更长的干草堆里还能不能找到」；你的 agent 面对的是「十几轮里，那些工具输出和半成品结论，还会不会继续参与后面每一次判断」
- 落点句：**争议双方都没错，错的是把它当成同一个问题**；而你的现场**两种失败都会出现**，且长得不一样（进作者原声）

### 五、所以子代理省下的不是时间，是「参与权」（~700 字）

- **Claude Code 官方文档**（一手）：当一个子任务会「淹掉你的主对话」（flood your main conversation）时用它——**子代理在它自己的上下文里干这件事，只把摘要交回来**
- **Anthropic**《How we built our multi-agent research system》（2025-06-13）：子代理扮演 **intelligent filters**；主 agent 的上下文超过 **200,000 token** 会被截断，所以它先把计划存进 Memory
- 成本照实说：Anthropic 自己承认多智能体用掉约 **15× token**、agent 本身约 **4×**——**隔离不是免费的**
- **进作者原声（槽 4）**：无脑追逐超长上下文、对执行偏差弃之不顾的人难以理解；配上定价事实（OpenAI 长上下文输入 2 倍 / Anthropic 已取消 / 阿里整单重算），末尾收在「是不是厂商借口推理成本涨价、而给你的是打折的服务」这个反问上
- **本段收口句（结构金句）**：性能有一个看不见的临界阈值（43.2%），计价也有一个看不见的临界阈值——**两个悬崖，一个你测得到，一个要等账单**
- 主轴句：你买到的不是速度，是**后面每一次判断不再被前面那些东西拖累**
- **转折（B 轴降级在此使用）**：代价是子代理只回一段**没有过程的话**，所以它的失败不会报错
- 🔗 内链：《给 Agent 装了记忆，为什么它还是不懂我的项目？》+《同样 1M 上下文，KV 缓存差 15 倍：四家架构差在哪一层》
- **本节结尾进作者原声（槽 5，全文唯一真实案例）**：opencode 对一整天巨额代码变更做一次性审计、按复杂 checklist 审到 GitHub——**diff 还没读完上下文就超了**，自动压缩的结果乏善可陈。该案例同时踩中两种病，自然引出第六节「先分清症状」
- *（[已采：槽 4、槽 5）](#作者原声槽)*

### 六、两种药：先分清是「撞车」还是「涣散」（~800 字，回应开头）

- **处置分叉（作者原声落在本节，槽 3）**：
  - 上下文**冲突 / 撞车**导致模型陷入困顿 → 及时下达**转舵指令**，帮它拿到清晰而无歧义的上下文——比放任它去猜测和胡乱验证好得多
  - 因为**太长**导致注意力涣散 → **fork** 或**压缩上下文**才是正解
  - 前置条件：操作的人得有足够背景知识**先判断是哪一种**——判错就下错药
- **反例制度化**（手册 §9.6，也是作者槽 1 原声的下游）：Anthropic 自己承认 compaction 的难点正是「留什么、丢什么」——**过度压缩会丢掉那些重要性后来才显现的细节**
- **压缩能力因 agent 而异（作者原声，槽 3b）**：Codex 以极强的上下文压缩能力著称（作者一线经验：可放心压三四次而不失太多智能），而很多 agent 压一两次就不堪大用 → 所以「压缩 / fork」**不是通用解**：长活交给谁，本身就是一道**上下文压缩能力的选型题**
- **一手来源（OpenAI 官方，两条）**：OpenAI API 文档《Compaction》——压缩是「为长时间运行交互服务、在**保留后续轮次所需状态**的前提下缩减上下文」的机制，做成了 API 一等的 **server-side compaction**（配 `compact_threshold`，过阈自动在流内压）；OpenAI 博客直接定调：**把压缩当作长跑的默认原语，不是应急兜底**
- **关键细节（本段最强传播点）**：OpenAI 的服务端压缩返回的是**加密的压缩项**——你看得到它还在跑，**看不到它丢掉了什么**。这与第一节「闭源模型因推理过程加密而被长程搜索论文排除」是同一个病根
- **本段收口句**：压缩最大的风险不是压得狠，是**它没有告诉你它丢掉了什么**
- Cognition《Multi-Agents: What's Actually Working》（2026-04-22）：真正跑通的模式是「多个 agent 贡献智能，但**写入保持单线程**」
- **双判据卡**：① **任务侧**——按参与度派活（见「拿得走的工程结论」）；② **故障侧**——先分清撞车还是涣散，再决定**转舵**还是 **fork / 压缩**
- 🔗 内链：《信息熵：压缩1000倍，为什么信息反而少？》+《上下文并行：1M序列为什么切了会坏？》
- 回扣开头：开头那个跑了一夜的 agent，它缺的不是窗口，是一条**把它不需要继续参与的东西挡在外面的边界**（以及一个能分辨「它到底是撞车还是涣散了」的人）
- **收尾前进作者原声（槽 6）**：按实际场景编排、设计合理的分工，用好当下 AI 的推理能力、**做好分治**
