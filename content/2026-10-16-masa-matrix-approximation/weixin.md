同一份预算，两列候选摆在你面前。

第一列的注意力分数是第二列的 **66 倍**。第二列看上去什么都没接住。

现有方法会毫不犹豫地挑第一列，丢掉 **98%** 的输出。

这不是段子，是论文 Figure 1 里一个两列的算例。

这个真的只是通过刻意硬凑，给构造出来的数学玩具吗？

不过从个人的角度来看，LLM 模型发展到今天，其实很多底层逻辑还是有不少缺口需要去补，靠朴素直觉硬玩炼丹术总不是长久之计。

理论解释略微落后于实践是可以的，但是一直跟不上来就不利于长期健康发展。

## 一、注意力不是被「读」的，是被乘掉的

每个 token 都有一个 query 和一个 key 向量，两者做内积，再过一遍 softmax。

得到的，就是这一行上每个位置的分数。

分数大，就意味着这个位置和当前这个 query 最说得上话。

但注意力不是被「读」的，是被**矩阵乘法**消费的：

$$\mathrm{softmax}(QK^\top)V$$

$A$ 不是终点。$A$ 乘上 value 矩阵 $V$ 得到的东西，才是模型的输出。

现有方法都盯着前半截——给每个候选单元（竖线、斜线、块）算一个标量分：

$$s_{\text{entry}}(u)=\sum_{(i,j)\in u}\phi(A_{ij})$$

$\phi$ 通常就是**注意力质量**：一个候选单元里所有分数加起来是多少。

🔗 [DeepSeek 注意力只算 8.6%，为什么 V4 反而不用？](https://mp.weixin.qq.com/s/HIBJliEXWtVyJqvH_Ocbog)

它们答的是「哪些格子分数大」，不是「哪些格子保住了输出」。

看到多家的注意力机制设计，我发现其实大家都还是单纯地按照 token 对应的向量表示之间的内积得分来挑最大这个共性，为什么就没有人尝试用一些不一样的方法来处理呢？

难道这真的是唯一正确的路径吗

## 二、挑最大不是笨办法，它只是答错了题

### 把误差写开，答案就露出来了

输出差多少可以这样写（论文 Eq.5）：

$$\big\|(A-M_{\mathcal S}\odot A)V\big\|_F^2=\mathrm{tr}\big((A-M_{\mathcal S}\odot A)\,VV^\top(A-M_{\mathcal S}\odot A)^\top\big)$$

于是第一件反直觉的事来了：**逐元素挑最大，恰好是「逐元素误差最小」的精确最优解**（论文给了证明）。

它不笨，只是答错了题。

真正的目标是把 $AV$ 逼近好，而两个目标只在 $VV^\top$ 像单位阵时才重合。

### 这个前提永远不成立

$V$ 的形状是 $N\times d$，$N$ 远大于 $d$，所以 $\mathrm{rank}(VV^\top)\le d\ll N$。

一个秩不超过 $d$ 的矩阵，没法在 $N$ 个位置上像单位阵。

**逐元素排序成立的唯一前提，在长上下文里永远不成立。**

那该按什么挑？

**矩阵逼近**：把「挑格子」重定义成「用一小部分格子，把 $AV$ 逼近到多好」（Eq.7）：

$$s(u)=2\langle O_X,C_u\rangle_F-\|C_u\|_F^2$$

逐对写开（Eq.8）：

$$s(i,j)=2A_{ij}\langle O_{X,i},X_j\rangle-A_{ij}^2\|X_j\|_2^2$$

$XX^\top=I$ 时它退化成 $A_{ij}^2$——**逐元素排序只是它的特例。**

这个错位其实来自 value 的方向差异，不是质量本身。

多出来的那个 $\|X_j\|^2$ 和内积项，就是质量排序丢掉的东西。

## 三、66 倍 vs 98%：一个两列的反例

论文 Figure 1 把它推到极端。

同一列预算下，质量排序选中质量大 $66\times$ 的那列，带来 **98%** 的相对矩阵乘积误差。

按矩阵逼近选另一列，误差降到 **3%**。

我们复刻了一遍——质量比 66、value 范数比 2158、方向差 49 度，得到 **98.0% / 3.0%**。

![同一列预算下，质量高 66 倍的那列反而丢掉 98% 的输出](01-66x-98.png)

翻译成人话：它分数高，是因为把每行 softmax 必须分配的质量都接住了。

它的 value 却几乎不往输出里加东西。**分数高是真的，高的原因和「重要」无关。**

看到这个数字，总算有一些不一样的视角能看出来点东西了，原来学习得到的分数高也并不一定就等价于产出就是最好的。

就像按照某个单一KPI计算得分最好的项目，未必实际效果就是最好的一样，任何方法都不应被滥用成为唯一标准，这个世界还是很复杂的。

## 四、把旋钮拧一遍：质量排序什么时候才真的崩

### 怎么测的

为了只看「方向抵消」这一个变量，所有列的 value 范数都设成 1——先剥掉范数因子。

单元换成块：16 块 × 16 列，预算 1/16。

旋钮是块内 value 方向的翻转比例 $f$：0 是一致，0.5 是完全抵消。

### 结果

$f=0$ 时两种排序**完全一样**：37.1% 对 37.1%，相关系数 **1.000**，选对率 100%。

$f=0.5$ 时，质量排序冲到 **92.8%**，矩阵逼近只到 **50.6%**。

相关系数掉到 **0.774**，选对率从 100% 掉到 **42.5%**。

![方向越互相抵消，两种排序分得越开](02-direction-scan.png)

两条线都不到 0，是因为预算只给了一块（1/16）。**看的是两条线分开的那一段，不是绝对值。**

### 三条边界

必须**不对称**才有错位：所有块同等抵消时，两种排序几乎分不开（37.1% 对 30.4%）。

**代价随预算收紧而放大**：预算放宽到 4/16 块，差距被压到约 0。

第一版我们拿单列当单元，跑反了——误差反而从 60.1% 降到 56.2%。单列内部根本不存在抵消。

**「单元内的相互作用」只有在块这类多 entry 单元上才成立。**

错位不是「总在犯错」，是在质量排行和贡献排行**脱钩**的地方犯错。

我倾向于认为，质量排行其实并不是任何时候都是错误的，而仅仅是有些时候显得失真，需要更好的工具来完善它。

## 五、为什么长上下文把这件事放大

一个单元的净贡献，量级约是 **质量 × ‖value‖²**，再加一项方向的内积修正。

质量排序丢掉的，正是整个范数因子和那项修正。而长上下文里这两个因子**同时**走向极端：sink 的质量占比暴涨，高范数的 value outlier 开始支配输出。


增益随上下文长度变大，更可能是质量分布趋向极端（attention sink / 汇聚）导致的污染，而不是方向各向同性化。

实验也对得上：32K 到 128K 四个配置里，**11/12** 个长度级分数提升。

长段的平均增益，超过 4K–16K 那一段。

所以不是「长上下文更容易出错」，是**两个极端同时变尖锐**。

## 六、论文自己怎么证明这不是玩具

### 一份刻意做干净的协议

它把新打分挂到 MInference、SeerAttention、FlexPrefill 三家的官方配置上。

kernel、候选单元、预算全不动，唯一变量是排序分数。

### 两个翻盘时刻

3 个方法 × 3 个基准 × 2 个 backbone，**8 个匹配平均分全部提升**。

SeerAttention 在 RULER 上从 **87.60 涨到 88.09**。全注意力 88.01，它从低于翻到高于。

FlexPrefill-Llama 在 InfiniteBench 上从 **47.14 涨到 47.99**。

全注意力 48.06，它收回原来 92% 的差距。

128K 四个配置加 **1.28 / 0.48 / 1.45 / 2.16** 分，64K 最高加 **3.65**。

附录 E 直接量了目标本身：输出误差全降。

四个配置分别 **+0.41% / +2.10% / +2.34% / +7.17%**，配对置信区间全部大于 0。

### 主动把短板摆出来

最小的那个提升是 **+0.48**。不藏。

更要紧的是：它**只在基线已有的候选单元上重排序**。

候选集本身差，打分再准也救不回来。论文自己把这写成 practical boundary——它是**矫正器，不是新的搜索空间**。

所以「零成本」准确说是**不新增一层计算**。

论文还划了一条线：全注意力是参考，不是严格上界。真正的问法是「同预算下一次修正能回收多少」。

## 七、DeepSeek 的选择器线，值得再问一句

NSA 的选块分数，**直接来自压缩分支的注意力分数**。

V3.2 的 DSA 索引器更直白：监督目标是 **KL 散度对齐主注意力分布**。

每个 query 只留 **2048** 个键值对。

V4 的 CSA 先压后选，再按同一套分数挑 top-k 的压缩块。

🔗 [稀疏注意力怎么挑重点？DeepSeek-V4 只算 1/64](https://mp.weixin.qq.com/s/QcZUcxYZUw27_J2ykESUHA)

这条线格外敏感的地方，在 sink。

稠密 softmax 里像是变相去除了不太影响矩阵相似性的项——sink 承接了 softmax 必须分配出去的质量，但它的 value 贡献趋零，所以对输出无害。

但稀疏化把行内质量截断了，免费出口立刻变成**预算黑洞**。

所以不少实现要特判保 sink（StreamingLLM 就强制保留最初几个 token）。

矩阵逼近的乘积结构自动降权，不用特判。

🔗 [同样 1M 上下文，KV 缓存差 15 倍：四家架构差在哪一层](https://mp.weixin.qq.com/s/7BdQlueJrRJ5f-x3v_2VqA)

不过，**错的是目标函数，不是实现水平**——索引器是训练出来的，参数有补偿空间。

这里写的是「值得再问一句」，不是「做错了」。

回到开头：8 个匹配全升、输出误差全降、长段增益最大。

它不是硬凑的数学玩具。**它是真实系统上一笔可以量出来的账。**
