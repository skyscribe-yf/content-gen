# KV缓存存进SSD：慢50倍的硬盘，为什么反而更快？

## 文章定位

- 本篇是 DeepSeek 技术解密系列的新一篇，主线是 **V4 推理系统的 on-disk KV cache 与共享前缀复用**（DeepSeek-V4 Technical Report §3.5.2 + Obsidian 第 14 课）。
- 兑现 FP4 篇（08-09）文末预告：「下一篇拆 1M 上下文为什么能秒开——KV 缓存直接存进 SSD」——标题与预告同频。
- 承接 K=V 篇（08-05）推理效率线：K=V 讲**显存账**（KV 占显存多少、怎么省），本篇讲**磁盘账**（KV 存进 SSD 后，靠共享前缀复用让 1M 长文秒回）。
- 主线冲突：**秒回之谜**——同一份 1M 长文，为什么第二个人问就秒回？SSD 比显存慢约 50 倍，把 KV 放进硬盘反而更快，凭什么？
- 暗线：**档案 vs 状态**——V4 承认「KV 不是一种东西」：CSA/HCA 压缩 KV 是长期档案（存盘、复用），SWA KV 与未压缩 tail 是滚动状态（固定池、局部重建）。缓存分层是秒回的真正原因。
- **与 K=V 篇（08-05）的边界（防自相矛盾）**：K=V 讲的是 **entry 内部**——一个压缩 entry 同时当 K 和 V（两个角色、一份数据）；本篇暗线讲的是 **entry 之间**——不同注意力分支的缓存分属不同生命周期（档案 vs 状态）。CSA main KV 正是 K=V 篇里那份「干两份活的 entry」，它是本篇「档案」的一种。K=V = 每份缓存长什么样；本篇 = 缓存之间怎么分家。两个维度正交，正文必须写明。
- 数学深度：双深潜。① **磁盘 vs 重算权衡**——读盘省掉的是 prefill 的 GPU 计算，交叉点在哪、什么时候读盘开始赢；② **lcm(m, m') 对齐**——为什么压缩块必须跨 lcm(m, m') 个原始 token，对齐才能落盘按块检索。
- 实验：三实验。① 权衡曲线（前缀长度扫描，读盘 vs 重算耗时交叉点）；② SWA 三策略对比（存储×重算二维权衡）；③ lcm 对齐模拟（不同 block 边界下的对齐复用开销），标注「机制演示，不是官方性能基准」。
- 下一篇预告：Lightning Indexer（08-11，注意力怎么学会只看重点）。
- **不是唯一解的声明**：缓存命中率极高是各家前沿模型的共同目标，但不是只有 V4 的「KV 存 SSD」一条路。Kimi K3 用 KDA 线性注意力把历史压成固定大小状态（不随序列增长），vLLM 实现用「每 32K token 存检查点」做前缀复用；Kimi API 侧 Mooncake 平台仍用分层缓存（HBM→DRAM→SSD）实现编码工作负载 >90% 命中率。正文第 8 节设「同题不同解」对照，避免把 V4 方案写成唯一解。

## 核心结论

1. **秒回的真因是共享前缀复用，落盘是手段**：很多请求共享长前缀（同一文档、同一代码库），重复 prefill 极浪费。V4 把适合长期复用的压缩 KV 落盘，下次命中前缀时直接读取，跳过 prefill。
2. **深潜①**：SSD 顺序读带宽约 3-7 GB/s，HBM 约 1-3 TB/s（差约 50 倍量级），但 prefill 的代价不是带宽而是 GPU 计算（每 token 每层都要算注意力）。磁盘 KV 的账：花零点几秒读盘，换掉的是数秒到数十秒的 prefill 计算——「慢」是相对的，省的是更贵的东西。
3. **暗线（档案 vs 状态）**：V4 的缓存是异构的——CSA main KV / CSA indexer KV / HCA KV（压缩档案，适合长期复用）+ SWA KV / 未压缩 tail states（滚动状态，只和当前位置有关）。PagedAttention「所有层统一分页」的假设在这里失效：不同缓存生命周期不同、kernel 对齐约束不同。
4. **两段式布局**：state cache（SWA KV + tail states，每请求预留固定大小块，动态分配）+ classical KV cache（CSA/HCA 压缩条目，每请求多 block，**block 跨度 = lcm(m, m') 个原始 token**）。
5. **深潜②**：m 是 CSA 压缩比、m' 是 HCA 压缩比，block 必须跨两者的最小公倍数，不同压缩分支才能在同一 token 边界对齐——kernel 的缓存线 / padding 设计才能配合，落盘后按块检索。
6. **未压缩 tail 也是缓存职责**：CSA/HCA 要凑满一个压缩块才执行压缩，半块 token 的隐藏状态必须暂存——缓存系统同时是「未来待压缩输入缓冲区」。
7. **落盘边界**：压缩 KV 全部落盘，前缀命中复用到**最后一个完整压缩块**；最后未完成的尾块仍要重算（未压缩 KV 没存盘）。
8. **SWA 三策略**：SWA KV 体积约是压缩 KV 的 8 倍、存在于每一层，全量存盘会产生糟糕的 SSD 写入模式。三策略：Full SWA Caching（全存，几乎零重算，存储压力最大）/ Periodic Checkpointing（隔段存检查点，可调折中）/ Zero SWA Caching（不存，靠压缩 KV 重算最近窗口，存储最省）。**不同缓存类型，不该共享同一种持久化策略**。
9. co-design：稀疏 attention kernel 与 cache layout 一起设计——block 颗粒度、padding 规则、层间共享结构共同决定，否则压缩收益在访存上被吃掉。

## 标题与摘要

### 标题

**KV缓存存进SSD：慢50倍的硬盘，为什么反而更快？**

（反常识提问 + 数字型 ⭐⭐⭐：「KV缓存」关键词前置（搜一搜命中长尾词）；「慢50倍的硬盘，为什么反而更快」制造反常识冲突，命中「残差连接：为什么56层比20层还差」已验证公式；21 字 ≤ 22；单术语 KV缓存。与 K=V 篇「K=V：一份KV缓存怎么干两份活？」形成「KV缓存系列」对仗）

### 摘要

同一份 1M 长文，为什么第二个人问就秒回？答案不是显存变大了，而是 KV 缓存被分成了两种东西：压缩 KV 是长期档案，存进 SSD；窗口 KV 是滚动状态，留在显存。SSD 比显存慢约 50 倍，为什么把 KV 放进硬盘反而更快？因为读盘换掉的是更贵的 prefill 计算。DeepSeek-V4 用共享前缀复用让 1M 上下文秒回，还专门设计了 lcm(m,m') 块对齐让档案能被翻出来。（含 3 个搜索关键词：KV缓存、SSD、共享前缀）

## 正文结构

### 0. 开头：同一份长文，第二个人问为什么秒回（约 250 字）

场景：你上传一份 1M 字的文档，第一次问「总结一下」，等了十几秒；同事问同一个问题，几乎是秒回。同样的模型、同样的 GPU，为什么？悬念：答案不在显存里，在硬盘里——而且是一块比显存慢 50 倍的硬盘。

### 1. 回应弧线：FP4 篇的预告，今天兑现（约 300 字）

- 引 FP4 篇结尾预告原文：「下一篇拆 1M 上下文为什么能秒开——KV 缓存直接存进 SSD。」
- 承接 K=V 篇：K=V 解决「KV 怎么少占显存」（显存账），本篇回答「KV 怎么进硬盘、进了硬盘为什么快」（磁盘账）。
- 归属校准（系列惯例）：KV cache 落盘与共享前缀复用是推理系统的通用思路（vLLM prefix caching 等已有实践），V4 的增量贡献在：①异构缓存分层（档案/状态拆开管）；②lcm(m,m') 块对齐与 kernel co-design；③SWA 三策略的持久化取舍。
- 本篇回答：KV 为什么能进硬盘？进了硬盘为什么反而快？档案和状态为什么不能混着存？

### 2. 背景：1M 长文第一次问为什么慢（约 350 字）

- prefill 的账：每来一个 token，每层都要算注意力（Q 乘全部历史 K）。1M token 的 prefill = 每层对 100 万历史做点积——计算量随序列长度增长，GPU 就算力再高也扛不住。
- 回链 K=V 篇：KV cache 是推理的「记忆笔记」，token 越多笔记越厚（显存账已讲，此处只一句话回链，不重推公式）。
- 关键：**同一个文档被问 100 次，前 99 次的 prefill 都在重复计算同一段前缀**——这就是浪费的来源，也是「复用」的靶子。

### 3. 深潜①：慢 50 倍的硬盘，为什么反而划算（约 600 字 + 实验 1）

- 直觉类比：搬家时纸箱存进仓库，比每次搬家都重新打包快得多——仓库慢（取件要走一趟），但省的是「重新打包」（prefill 计算）。
- 数字：SSD 顺序读 ~3-7 GB/s vs HBM ~1-3 TB/s（约 50 倍量级，正文标注估算口径）。KV 存盘后读回要花时间——为什么总账还是赢？
- 核心论证：prefill 的瓶颈不是带宽而是**计算**（每 token 每层的注意力点积）。磁盘 KV 的账：读 1 GB 磁盘 KV 花约 0.2-0.3 秒，省掉的 prefill 是「1M token × 层数 × 注意力计算」——数秒到数十秒。**省的是更贵的东西**。
- 实验 1（支撑）：权衡曲线——固定模型规模，扫描前缀长度，画「读盘耗时 vs 重算 prefill 耗时」两条线，找交叉点；交叉点之前重算便宜，之后读盘赢。标注：机制演示，带宽/算力取量级参数。
- 数学表达：命中时成本 ≈ 读盘带宽 × KV 体积；未命中成本 ≈ prefill 计算量 / GPU 算力。交叉点 = 前缀长度阈值（与 KV 体积成正比、与算力成反比）。

### 4. 暗线揭示：KV 不是一种东西（约 550 字）

- 转场：但「把 KV 存进 SSD」说起来一句话，做起来要回答一个问题——哪些 KV 该存？
- **边界澄清（防自相矛盾，先讲清楚再展开）**：上一篇 K=V 说「一份 KV 缓存干两份活」——那是**每份缓存内部**的结构：一个压缩 entry 同时当 K 和 V。本篇说「KV 不是一种东西」——那是**缓存与缓存之间**的分类：不同注意力分支产生的缓存，生命周期完全不同。CSA main KV 恰恰就是 K=V 篇里那份「干两份活的 entry」，它是本篇「档案」中的一种。K=V 讲每份缓存长什么样（两个角色合一），本篇讲缓存之间怎么分家（档案 vs 状态）——两个维度不冲突，本篇站在 K=V 的肩膀上。
- V4 的答案：先承认异构。压缩 KV（CSA main / CSA indexer / HCA）适合长期复用 → 档案；SWA KV + 未压缩 tail states 只和当前位置有关 → 状态。
- PagedAttention 为什么失效（两障碍）：①不同 cache policy——SWA 只关心最近窗口（滚动），压缩 KV 面向长期复用（归档），生命周期完全不同；②kernel 对齐约束——稀疏 attention kernel 需要特定 block 对齐和 padding，不能随意分页。
- 一句话：V4 的缓存系统不是「统一的历史仓库」，而是「档案库 + 状态机」的混合体——每份档案仍是 K=V 的极简样式，但档案和状态分属两个房间。

### 5. 两段式布局与深潜②：lcm 对齐（约 600 字 + 实验 3）

- 布局：state cache（SWA KV + 未压缩 tail，每请求固定大小块，动态分配）+ classical KV cache（压缩条目，每请求多 block）。
- 深潜②问题：block 跨多少原始 token？CSA 每 m 个 token 产一个压缩条目，HCA 每 m' 个 token 产一个——两个压缩分支的边界对不上，落盘后按块检索就乱套。
- 数学：block 跨度 = lcm(m, m') 个原始 token。理由：只有跨最小公倍数，CSA 与 HCA 的压缩条目边界才能在**同一 token 边界**对齐；kernel 的缓存线 / padding 规则才能配合。
- 类比：两个人分别在每 3 步和每 5 步做记号，只有走到第 15 步（lcm）两人才同时落脚——档案柜的抽屉按「同时落脚的边界」做，翻档案才不跨柜。
- 实验 3（支撑）：模拟不同 block 边界（m 的倍数 / m' 的倍数 / lcm）下，一个检索请求需要跨多少个块——lcm 对齐的跨块数最少，检索开销最低。
- co-design 一句带过：kernel 与 cache layout 一起设计，否则压缩收益在访存和 padding 上被吃掉。

### 6. 落盘边界：什么能存、什么只能重算（约 400 字）

- 压缩 KV 全落盘；前缀命中复用到**最后一个完整压缩块**。
- 未压缩 tail 不落盘：它还没凑够一个压缩块（半块 token 的隐藏状态暂存在 state cache 里，等后续 token 来了一起压缩），复原成本靠重算承担。
- 直觉：档案柜只收「整理好的文件」；半成品文件留在桌面上（state cache），下次继续写。
- 缓存系统同时是「未来待压缩输入缓冲区」——这是缓存职责的扩展，不是简单的历史存储。

### 7. SWA 三策略：8 倍体积的取舍（约 450 字 + 实验 2）

- 问题：SWA KV 体积约是压缩 KV 的 8 倍、存在于每一层——全量存盘会在现代 SSD 上产生糟糕的写入模式。
- 三策略表：| 策略 | 特点 | 代价 |（Full SWA Caching 全存盘，几乎零重算，存储写入压力最大 / Periodic Checkpointing 隔段存检查点，存储重算可调 / Zero SWA Caching 不存，靠压缩 KV 重算最近窗口，存储最省）
- 实验 2（支撑）：同一份 1M 上下文，三种策略的「存储成本 × 重算成本」二维对比——Full 存储高重算低、Zero 存储低重算高、Periodic 中间可调。
- 哲学落点：**不同缓存类型，不该共享同一种持久化策略**——档案该存盘，状态该滚动；连状态内部也有三档取舍。
- 呼应第 4 节的暗线：这就是「档案库 + 状态机」在工程上的完整落地。

### 8. 同题不同解：Kimi K3 走了一条相反的路（约 450 字）

- 声明（不是唯一解）：缓存命中率极高不是 V4 独有——开源前沿模型 Kimi K3 同样做到了，但路线完全不同。
- K3 的答案：KDA 线性注意力把历史压成一个**固定大小的状态**（不随序列增长）——1M 上下文不需要为每个 token 存 KV，模型层面根本不依赖 SSD 扩容（对照 V4：压缩 KV 再小也随序列增长，SWA 还占 8 倍体积，必须分档落盘）。
- 但前缀复用怎么做？vLLM 对 K3 的实现：每 32K token 存一个 KDA 状态检查点，agentic 负载在 prompt 边界也存（interval-based prefix caching）——这正是 V4 SWA 三策略里 **Periodic Checkpointing** 的同款思路，说明「周期性检查点」是业界共识而非 V4 独创。
- Kimi API 侧：Mooncake 平台仍然把 CPU/DRAM/SSD 池化成分布式 KV cache（FAST'25 论文），编码工作负载缓存命中率 >90%（K3 官方技术页）——命中率是各家推理平台的共同目标，V4 不是唯一答卷人。
- 结论：V4 的「压缩 + 分档 + 落盘」是一条工程答案，K3 的「状态压小」是另一条——两条路线殊途同归：都是少算重复的 prefill。归属诚实：SSD 落盘（Mooncake）、周期性检查点（vLLM/vLLM-K3）都非 V4 发明，V4 的增量在异构分层 + lcm 对齐 + 三策略取舍。

### 9. 回扣与结尾（约 350 字）

- 完整因果链复盘：秒回 = 共享前缀命中 → 跳过 prefill → 压缩 KV 落盘可复用 → 档案/状态分层让落盘可行 → lcm 对齐让按块检索高效。每一环都在回答「为什么反而更快」。
- 回扣开头：同事的秒回不是玄学——第一次问时，GPU 把 1M token 的「档案」整理好存进了硬盘；第二次问，硬盘把档案读回来，GPU 只算最后那一小块。
- 与第 8 节呼应：V4 和 K3 选了两条路，但都指向同一个方向——把重复的 prefill 省掉；V4 靠分档落盘，K3 靠状态压小，殊途同归。
- 下一篇预告（Lightning Indexer，08-11）：把 KV 落盘要按块翻档案，那「翻档案」本身也要快——V4 训练了一个小模型专门负责选出该看哪些块：注意力怎么学会只看重点？
- 开放式问题：如果 KV 能存进 SSD，你觉得下一步该把什么「存进硬盘」？评论区聊聊。
