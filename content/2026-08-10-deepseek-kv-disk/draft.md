你往对话框里丢了一份 100 万字的技术文档，问「总结一下第三章」，等了十几秒才出第一个字。

同事接着问了同一个问题，你还没看清他怎么操作，回答已经出来了。

一样的模型，一样的 GPU，凭什么他不用等？

答案不在显存里，在一块比显存慢约 50 倍的硬盘里。

FP4 量化篇（待发布）结尾我预告过：1M 上下文为什么能秒开？今天兑现——KV 缓存怎么进硬盘、进了硬盘为什么反而快。

承接上文，一句话理清边界。上一篇 [K=V](https://mp.weixin.qq.com/s/88kscO8p0kMxHmeGm2llLA) 讲的是**每份缓存长什么样**：一个压缩 entry 同时当 K 和 V，靠 Partial RoPE 和 de-RoPE 分清职责。今天讲的是**缓存之间怎么分家**：哪些该留在显存，哪些该搬进硬盘。两个维度不冲突——今天出场的主角，正是 K=V 篇里那份「一份干两份活」的压缩 entry。

## 第一次问，为什么慢？

先把「慢」算清楚。

100 万 token 的文档，模型要先读完才能回答。这一步叫 **prefill**（预填充）：每个新 token 都要和之前所有的 token 做注意力计算。第 100 万个 token 进来时，它要跟前面 999,999 个 token 逐一比对——注意，是每一层都这么比一遍。

把计算量写成公式，注意力部分是每个 token 跟所有历史 token 做点积：

$$\text{FLOPs}_{\text{prefill}}(n) \approx L \cdot c \cdot n^2$$

$n$ 是序列长度，$L$ 是层数，$c$ 是「每层每个 token 对」的系数，跟注意力头数、维度成正比。**$n^2$ 是罪魁祸首**：第 $n$ 个 token 要跟前面 $n-1$ 个历史逐一比对，序列长一倍，计算量涨四倍。

代入 V4-Pro 的量级：$L=61$ 层，$n=10^6$ token，单卡约 1 PFLOPS（FP8 量级）。V4 的稀疏注意力能把有效计算量压到远低于密集 $n^2$ 模型，但 100 万 token 的 prefill 仍然要花几十秒到一分钟——这就是你第一次问要等的十几秒的真实来源。

更浪费的是：**同一个文档被问 100 次，前 99 次的 prefill 都在算同一段前缀。** 你问第三章，模型把第一、二章也完整读了一遍；同事再问，又把第一、二章读了一遍。

第二次问要等，第三次、第四次也要等。直到有人想到：**算过的结果，能不能存起来复用？**

能。算过的注意力中间结果就是 KV 缓存——把「读文档」变成「查档案」。第一次问：读完，整理成档案，存好。第二次问：直接翻档案，GPU 只算新增的那一小段。

![重复 prefill：同一个文档被问 3 次，前 3 次都在算同一段](01-prefill-cost.png)

但档案往哪儿存？KV 缓存是出了名的占地方。[K=V 篇](https://mp.weixin.qq.com/s/88kscO8p0kMxHmeGm2llLA)讲过，1M token 的 KV 缓存能占掉几十 GB 显存——显存是 GPU 上最贵的资源，模型权重还占着一大半。都堆在显存里，一张卡根本放不下。

于是 DeepSeek-V4 做了一个看起来很疯的决定：**把 KV 缓存存进 SSD。**

## 慢 50 倍的硬盘，为什么反而划算？

我第一次读到 V4 技术报告里「把 KV 缓存存到磁盘」这句话时，第一反应是：这工程师是疯了吗？

SSD 和显存的差距有多大？

量级上，HBM（显存）带宽约 1-3 TB/s，NVMe SSD 顺序读约 3-7 GB/s——**差约 50 倍**。硬盘慢成这样，把 KV 放进去，翻档案不更慢吗？

这里有个反直觉的点：**prefill 的瓶颈不是带宽，是计算。**

读硬盘再慢，读的是「已经算好的结果」；重算 prefill，花的却是 GPU 的算力——而算力比带宽更贵。搬家的比喻：仓库取件要走一趟路，但比每次搬家都重新打包快得多。

算一笔账。假设 100 万 token 的文档，KV 缓存约 10 GB（压缩后，量级）。从 SSD 读回来：

$$t_{\text{read}} \approx \frac{10\text{ GB}}{5\text{ GB/s}} \approx 2\text{ 秒}$$

重新 prefill 这 100 万 token 呢？V4 的注意力计算再省，也要几十秒到几分钟量级（视 GPU 而定）。**花 2 秒读盘，换掉几十秒的计算**——这就是「慢 50 倍的硬盘反而更快」的全部秘密。

更一般地写出来。设每 token 的压缩 KV 体积为 $k$ 字节、磁盘带宽为 $B_{\text{disk}}$、GPU 算力为 $G$，前缀长度为 $n$：

$$t_{\text{命中}}(n) = \frac{k n}{B_{\text{disk}}}, \qquad t_{\text{重算}}(n) = \frac{L c n^2}{G}$$

两者随 $n$ 的增长速度不同：读盘时间随前缀长度**线性**增长，重算时间随前缀长度**二次**增长。它们必然相交——交点就是读盘开始赢的临界长度：

$$n^{*} = \frac{k G}{B_{\text{disk}} L c}$$

把量级参数代进去（$k\approx10^4$ 字节、$G\approx10^{15}$、$B_{\text{disk}}\approx5\times10^9$、$L=61$），临界点大约在几万 token 量级。我跑了个机制演示（`experiment.py`），交叉点在约 36K token：**前缀短于它，重算更划算；长于它，读盘通吃。** 1M token 时读盘约 2 秒，重算约 60 秒，快约 30 倍。

（说明：以上是量级估算，用于演示权衡结构。实际交叉点取决于 GPU 型号、SSD 带宽、模型配置，真实部署里可能差一个数量级——但「线性 vs 二次、必然相交」的结构不变。）

这就是为什么短对话用不上这套（几千 token 的前缀，重算才零点几秒，何必读盘），1M 长文却是刚需。

![读盘 vs 重算：交叉点之后，读盘线一直在重算线下方](02-tradeoff-curve.png)

（读盘换重算是业界共识，不是 V4 的发明。Kimi 的 Mooncake 平台 2024 年就把 CPU、DRAM、SSD 池化成分散式 KV 缓存池，论文发表在 USENIX FAST'25。它还给这套权衡写了正式判据：带宽与算力之比要大于某个阈值，读盘才划算。对 LLaMA-70B 规模的模型，前缀 8192 token 时最低需要约 6 GB/s 的传输带宽——一台服务器的网卡就够。V4 的增量不在这里，在后面两节。）

## KV 不是一种东西

「把 KV 存进 SSD」说起来一句话，做起来要先回答一个问题：**哪些 KV 该存？**

V4 的答案是：先承认一件反直觉的事——**KV 不是一种东西。**

混合注意力（CSA/HCA，[上上篇](https://mp.weixin.qq.com/s/MQEgbY16mLs-N7g2xKW1HQ)讲过）给 V4 带来了好几种缓存条目，大小、更新规则、生命周期全不一样：

- **CSA main KV、HCA KV**：压缩后的「长期档案」，跨请求复用价值高
- **CSA indexer KV**：给 Lightning Indexer 用的打分缓存，维度还和主注意力不同
- **SWA KV**：滑动窗口注意力的缓存。[上上篇](https://mp.weixin.qq.com/s/MQEgbY16mLs-N7g2xKW1HQ)讲过它的分工：压缩路径管远处信息，滑窗负责最近 $n_{\text{win}}$ 个 token 的精确关系。它的 KV 只随窗口滚动，不面向长期复用
- **未压缩 tail states**：还没凑够一个压缩块的「半成品」

前两类是档案，适合长期保存；后两类是状态，只和当前位置有关，随用随扔。

这直接挑战了推理引擎界的老规矩。vLLM 的 **PagedAttention** 假设「所有层的 KV 都是往同一个分页体系里追加」，但 V4 有两道障碍绕不过去：

1. **生命周期不同**：SWA 只关心最近窗口，压缩 KV 面向长期复用——一个滚动、一个归档，共用一套淘汰策略必然互相拖累。
2. **kernel 对齐约束**：稀疏注意力 kernel 需要特定的 block 对齐和 padding 规则，不能随意分页。

所以 V4 把缓存拆成两套：

- **State cache**：装 SWA KV 和未压缩 tail。每个请求分配一个**固定大小**的块——因为这两种东西「只和当前位置有关」，体量有上限，固定池管理最省心。
- **Classical KV cache**：装 CSA/HCA 压缩条目。每个请求分配多个块，按块覆盖原始 token 区间。

一句话总结：**V4 的缓存系统不是「统一的历史仓库」，而是「档案库 + 状态机」的混合体。** 档案进硬盘，状态留显存。

![档案库 + 状态机：压缩 KV 是档案，SWA 与未压缩 tail 是状态](03-kv-split.png)

## 档案怎么对齐：lcm(m, m') 的算术

档案要进硬盘，就得按块存、按块翻。V4 的压缩 KV 是分块压缩的：CSA 每 $m$ 个原始 token 产一个压缩条目，HCA 每 $m'$ 个产一个。V4-Flash 的配置是 $m=4$、$m'=128$。

问题来了：两个压缩分支的块边界对不上，落盘后按块检索就乱套。

想象两个人分别每 3 步、每 5 步在地上做记号。你沿着路走，想一次捡起「两人同时落脚」的位置之间的所有记号——只有走到第 15 步（3 和 5 的最小公倍数），两人才同时落脚。

V4 的做法一模一样：**每个 cache block 覆盖 lcm($m$, $m'$) 个原始 token。**

$$k_1 = \frac{\operatorname{lcm}(m, m')}{m}, \qquad k_2 = \frac{\operatorname{lcm}(m, m')}{m'}$$

也就是 lcm(4, 128) = 128 个原始 token 一个块：CSA 产出 32 个压缩条目，HCA 产出 1 个。**两个压缩分支的边界在同一 token 处对齐**，kernel 的缓存线、padding 规则才能配合；落盘后按块检索，不跨柜翻档案。

说实话，我第一次读到这里也犯嘀咕：块大块小，不就是个工程细节吗？看完论文才意识到，这里藏着一个真正的数论问题。

为什么必须是 lcm，不能是别的数？两个理由。

第一，**任何公倍数都能对齐，但 lcm 是最小的那个。** 块越小，检索粒度越细——命中一个 128 token 的前缀，读一个块就够；块若放大十倍，同样的命中要搬回十倍无关内容。lcm 是「能对齐的最小块」，检索精度最高。

第二，**kernel 的块大小是另一条约束。** 稀疏注意力 kernel 通常假设每块固定 $B$ 个压缩 token（对应 CSA 的 $B \cdot m$ 个原始 token、HCA 的 $B \cdot m'$ 个）。块覆盖 lcm($m$, $m'$) 的倍数时，两个分支的块边界才会同时落在 kernel 的块边界上，padding 才不浪费。

这里还能看到一个更有意思的细节：V4 不是「先定缓存、再写 kernel」，而是让**缓存布局和稀疏注意力 kernel 一起设计**（co-design）。论文原话：padding 块对齐缓存线就能提升性能。压缩收益再漂亮，访存和 padding 上被吃掉就白干——所以 block 颗粒度、padding 规则、层间共享结构是统一设计的。

我在 `experiment.py` 里用演示参数（$m=6, m'=10$，lcm=30）模拟了检索开销：lcm 对齐的方案检索 300K token 前缀只需读 2667 块，而只按单分支对齐要读 8000 到 13000 多块——多出来的全是在边界块上的 padding 浪费。

![lcm 块对齐：两种压缩分支的边界在同一 token 处对齐](04-lcm-align.png)

## 什么能存盘，什么只能重算

档案分好了，落盘还有一个边界要划清。

**压缩 KV 全部落盘。** 前缀命中时，直接读盘复用——但只复用到**最后一个完整压缩块**。

最后那半个块呢？比如 130 个 token 的文档，压缩到第 128 个 token 刚好一个完整块，剩下 2 个 token 还没凑够压缩单位。这 2 个 token 的**未压缩 KV 不落盘**——下次命中时，最后 2 个 token 必须重新 prefill。

为什么？想想压缩的流程：CSA/HCA 不是来一个 token 就压一个，而是凑满 $m$ 个才执行压缩。凑不满的 token 得先暂存在缓存里当「未来待压缩输入缓冲区」。这些半成品没整理成档案，自然没资格进档案库。

这背后还有一笔算术账。未压缩 KV 的体积是压缩 KV 的 $m$ 倍——每 $m$ 个原始 token 才压成 1 个条目，半块的未压缩 KV 占的空间，够存 $m$ 个完整块。更关键的是，**尾部是每次请求都会变化的部分**。同一份文档，第一个人问「第三章」，第二个人问「第五章」——命中的前缀都到第 128 个 token 为止，但各自的后半段完全不同。花 $m$ 倍的存储去存一个大概率命中不上的尾巴，这笔账不划算——重算它，只花几秒。

所以缓存系统在这里多了一个职责：**不只是存历史，还要暂存「未来」。** 半成品留在 state cache 里，等后续 token 到了再一起压缩。

直觉版本：档案柜只收整理好的文件；半成品留在桌面，下次继续写。

## SWA：8 倍体积的取舍

先把 SWA 拉回来回顾一下（[上上篇](https://mp.weixin.qq.com/s/MQEgbY16mLs-N7g2xKW1HQ)细讲过）。CSA/HCA 把远处的历史压成摘要，但摘要会丢细节——所以 V4 保留一条**未压缩的滑动窗口**，只缓存最近 $n_{\text{win}}$ 个 token 的原始 KV，负责最近的精确关系。这条窗口随生成滚动：新 token 进来，最老的 token 滑出去。

就是这条窗口，成了所有缓存里最难伺候的一个。我第一次算它的体积时愣住了：一个只关心最近 128 个 token 的「小窗口」，凭什么比压缩档案还大？因为它**不压缩、每一层都有**——体积大约是压缩后的 CSA/HCA KV 的 **8 倍**。全量落盘？会在 SSD 上产生灾难性的写入模式——每个请求只访问一小部分 SWA KV，却要把整段都写一遍。

V4 给了三种策略，在**存储**和**重算**之间找平衡：

| 策略 | 做法 | 代价 |
|------|------|------|
| Full SWA Caching | 所有 SWA KV 都存盘 | 几乎零重算，但写入和存储压力最大 |
| Periodic Checkpointing | 每 $p$ 个 token 存一个检查点 | 命中时加载最近检查点 + 重算尾部，$p$ 可调 |
| Zero SWA Caching | 完全不存 SWA KV | 存储最省，但命中时要重算最近 $n_{\text{win}} \times L$ 个 token 的状态 |

注意第三种策略的数学：SWA 每个 token 的 KV 只依赖前一层最近 $n_{\text{win}}$ 个 token——所以重算量是**有界的**，不是全量重算。

这个有界性值得展开。要恢复第 $L$ 层的最近 $n_{\text{win}}$ 个 token 的 SWA KV，需要第 $L-1$ 层同样位置的窗口；而第 $L-1$ 层的窗口，又依赖第 $L-2$ 层的窗口……依赖链逐层往回传，每层只需要 $n_{\text{win}}$ 个 token 的计算量：

$$\text{重算量} \le n_{\text{win}} \times L \text{ 个 token 的注意力}$$

注意不是 $n_{\text{win}} \times L$ 个 token 的**全量** prefill——窗口是「局部因果链」，链条宽度 $n_{\text{win}}$、长度 $L$，两者相乘就是恢复状态的完整代价。V4-Flash 的配置是 $n_{\text{win}}=128$、$L=61$，也就是约 7800 个 token 的计算量——对 GPU 是零点几秒的事。这就是 Zero 策略敢「什么都不存」的底气：**有界的重算，才是可接受的重算。**

三种策略没有绝对优劣。走全量缓存，钱花在硬盘上；走零缓存，钱花在 GPU 上；走周期检查点，两头各付一半。**按部署场景选**——这就是论文说的「不同缓存类型，不该共享同一种持久化策略」。

有时候工程就是这样：没有一套放之四海皆准的优雅方案，而是把不同对象分开对待，各自给一个「丑但够用」的办法，合起来居然就稳了。

![SWA 三策略：存储与重算的天平，Full 到 Zero 逐渐倾斜](05-swa-strategy.png)

顺带说一句，这个「周期性检查点」的思路，Kimi K3 也在用——vLLM 给 K3 做前缀复用，就是每 32K token 存一个 KDA 状态检查点。殊途同归。

## 同题不同解：Kimi K3 走了一条相反的路

说到 K3，值得停下来做个对照——**缓存命中率极高不是 V4 独有，SSD 方案也不是唯一解。**

Kimi K3 用的是 KDA 线性注意力：把整个历史压进一个**固定大小**的隐状态矩阵，不随序列长度增长。复杂度上这是从 $O(n)$ 的 KV 存储降到了 $O(1)$——1M 上下文，KV 占用是常数，模型层面根本不需要 SSD 扩容。

作为对照，V4 的压缩 KV 是「每个 $m$ token 产 1 个条目」：再压缩，总量还是随 $n$ **线性增长**，只是斜率小了。所以 V4 必须面对「存不下」的问题，K3 从根上绕开了它。

但注意两个事实：

1. **K3 也要做前缀复用**：vLLM 的实现是每 32K token 存一个状态检查点（interval-based prefix caching）。线性注意力的状态是「累积值」，不存检查点就没法跳到任意前缀——这跟 V4 的 Periodic Checkpointing 是同款思路，说明「检查点换复用」是业界共识。
2. **K3 的 API 照样用 SSD**：Kimi 的 Mooncake 平台把 CPU/DRAM/SSD 池化成分布式 KV 缓存池，官方披露编码工作负载缓存命中率超过 90%。

所以准确的画面是：**模型层面，K3 靠「状态压小」绕开了磁盘；平台层面，Kimi 和 DeepSeek 都在用分层缓存。** 两条路线殊途同归——目标都是同一个：把重复的 prefill 省掉。

V4 的「压缩 + 分档 + 落盘」是一套工程答案，不是唯一答案。它的增量贡献要记清楚：**异构缓存分层、lcm 对齐与 kernel 协同设计、SWA 三策略取舍**——落盘本身（Mooncake）和检查点（vLLM）都不是 V4 发明的。

## 第二次问，为什么秒回？

文章开头那个问题，现在能完整回答了。

同事的秒回 = 共享前缀命中 → 跳过 prefill → 压缩 KV 落盘可复用 → 档案/状态分层让落盘可行 → lcm 对齐让按块检索高效。每一环都在回答同一个问题：**为什么反而更快。**

第一次问的时候，GPU 花了十几秒，把 100 万 token 的「档案」整理好存进了硬盘。第二次问，硬盘把档案读回来，GPU 只算最后那一小块——2 秒读盘，换掉十几秒重算。慢 50 倍的硬盘，赢在把最贵的算力省了下来。

下一篇拆一个更细的问题：档案按块落盘了，但**翻档案**本身要快——V4 训练了一个小模型（Lightning Indexer），专门负责从几万个块里挑出该看哪几个。注意力怎么学会只看重点？下篇见。
