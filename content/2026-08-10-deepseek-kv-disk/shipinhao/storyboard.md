## 段落设计（6 段）

| # | 场景 | 动画要点 | 配音稿 |
|---|------|---------|--------|
| S1 | 开场钩子：同事秒回 vs 你等十几秒 | 概念图「对话框」（两个人问同一文档，无数字）；「答案在慢 50 倍的硬盘里」爆点卡 | 你往对话框里丢了一份 100 万字的技术文档，问总结一下第三章，等了十几秒才出第一个字。同事接着问了同一个问题，你还没看清他怎么操作，回答已经出来了。一样的模型，一样的 GPU，凭什么他不用等？答案不在显存里，在一块比显存慢约 50 倍的硬盘里。今天拆：KV 缓存怎么进硬盘，进了硬盘为什么反而快。 |
| S2 | prefill 为什么慢 | n² 增长曲线（脚本画图：序列长一倍计算量涨四倍）；重复 prefill 图（3 次问同一文档都在算同一段，红叉）；KV 缓存复用图（第一次读文档存档案，第二次查档案）；「存哪？」悬念 | 先把慢算清楚。100 万 token 的文档，模型要先读完才能回答，这一步叫 prefill。每个新 token，都要和之前所有的 token 做注意力计算。第 100 万个 token 进来时，要跟前面 99 万 9 千多个逐一比对。计算量随序列长度平方增长：序列长一倍，计算量涨四倍。更浪费的是：同一个文档被问 100 次，前 99 次的 prefill 都在算同一段前缀。你问第三章，模型把第一、二章也完整读了一遍。算过的结果，能不能存起来复用？能。算过的中间结果就是 KV 缓存——把读文档变成查档案。但档案往哪儿存？1M token 的 KV 缓存能占几十 GB 显存，都堆在显存里，一张卡根本放不下。于是 DeepSeek-V4 做了一个看起来很疯的决定：把 KV 缓存存进 SSD。 |
| S3 | 慢 50 倍为什么反而划算 | 带宽对比条（显存 1-3 TB/s vs SSD 3-7 GB/s，50 倍）；读盘 2 秒 vs 重算 60 秒对比；线性 vs 二次曲线交叉图（36K 交叉点）；「算力比带宽更贵」卡 | 把 KV 缓存存进硬盘？第一反应是：这工程师疯了吗？SSD 和显存的差距有多大？显存带宽约每秒 1 到 3 TB，SSD 顺序读约每秒 3 到 7 GB——差约 50 倍。硬盘慢成这样，把 KV 放进去，翻档案不更慢吗？这里有个反直觉的点：prefill 的瓶颈不是带宽，是计算。读硬盘再慢，读的是已经算好的结果；重算 prefill，花的却是 GPU 的算力——算力比带宽更贵。算一笔账：100 万 token 的文档，KV 缓存约 10 GB。从 SSD 读回来，约 2 秒。重新 prefill 呢？要几十秒到几分钟。花 2 秒读盘，换掉几十秒的计算。更一般地看：读盘时间随前缀长度线性增长，重算时间随前缀长度平方增长。它们必然相交——交点就是读盘开始赢的临界长度，大约在三万六千个 token。前缀短于它，重算更划算；长于它，读盘通吃。1M token 时，读盘约 2 秒，重算约 60 秒，快约 30 倍。 |
| S4 | KV 不是一种东西 | 档案 vs 状态分类图（压缩 KV 档案 / SWA 状态 / 半成品状态）；两套缓存图（状态缓存固定块 / 经典 KV 缓存按块覆盖）；「档案进硬盘，状态留显存」结论 | 把 KV 存进 SSD，说起来一句话，做起来要先回答一个问题：哪些 KV 该存？V4 的答案是：先承认一件反直觉的事——KV 不是一种东西。混合注意力给 V4 带来了好几种缓存条目，大小、更新规则、生命周期全不一样。压缩后的长期档案，跨请求复用价值高；滑动窗口的缓存，只随窗口滚动；还有没凑够压缩块的半成品。前两类是档案，适合长期保存；后两类是状态，只和当前位置有关，随用随扔。所以 V4 把缓存拆成两套：状态缓存，装滑动窗口和半成品，每个请求分配一个固定大小的块；经典 KV 缓存，装压缩条目，按块覆盖原始 token 区间。一句话总结：V4 的缓存系统不是统一的历史仓库，而是档案库加状态机的混合体。档案进硬盘，状态留显存。 |
| S5 | lcm 对齐 + 半成品不落盘 | 两个压缩分支块边界错位图（红叉）→ lcm 对齐图（128 token 块）；「lcm 是最小的对齐块」卡；档案柜比喻概念图（整理好的文件 vs 桌面半成品，无数字） | 档案要进硬盘，就得按块存、按块翻。V4 的压缩 KV 是分块压缩的：CSA 每 4 个原始 token 产一个条目，HCA 每 128 个产一个。问题来了：两个分支的块边界对不上，落盘后按块检索就乱套。V4 的做法：每个缓存块覆盖 4 和 128 的最小公倍数，也就是 128 个原始 token。两个分支的边界在同一 token 处对齐。为什么必须是 lcm？任何公倍数都能对齐，但 lcm 是最小的那个——块越小，检索粒度越细。还有一条边界要划清：压缩 KV 全部落盘，但只复用到最后一个完整压缩块。最后那半个块，没凑够压缩单位的半成品不落盘——下次命中时，最后几个 token 必须重新 prefill。直觉版本：档案柜只收整理好的文件；半成品留在桌面，下次继续写。 |
| S6 | SWA 三策略 + 秒回链路 + 收尾 + 尾卡 | SWA 8 倍体积卡；三策略对比卡（全量/检查点/零缓存）；有界重算卡（7800 token）；秒回链路图（命中→跳过 prefill→落盘复用→分层→lcm 对齐）；尾卡：avatar + 黄色关注 + 当期标题 + 绿色引导 + 下一篇 Lightning Indexer 预告 | 还有一条最难伺候的：滑动窗口缓存，不压缩、每一层都有，体积大约是压缩档案的 8 倍。全量落盘？写入模式是灾难性的。V4 给了三种策略：全量缓存，几乎零重算，但存储压力最大；周期检查点，两头各付一半；零缓存，完全不存，命中时重算最近窗口——但重算量是有界的，约七千八百个 token，对 GPU 是零点几秒的事。回到开头的问题：同事的秒回，等于共享前缀命中，跳过 prefill，压缩 KV 落盘可复用，档案状态分层让落盘可行，lcm 对齐让按块检索高效。第一次问，GPU 花十几秒把档案整理好存进硬盘；第二次问，硬盘把档案读回来，GPU 只算最后那一小块——2 秒读盘，换掉十几秒重算。慢 50 倍的硬盘，赢在把最贵的算力省了下来。关注数解AI，下一篇拆 Lightning Indexer：注意力怎么学会只看重点？如果 KV 能存进 SSD，你觉得下一步该把什么存进硬盘？评论区聊聊。 |
