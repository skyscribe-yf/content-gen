# 大纲：Kimi K3：KDA怎么撑住1M上下文？

## 标题与摘要

- **推荐标题**：Kimi K3：KDA怎么撑住1M上下文？
- **关键词**：Kimi K3、KDA、线性注意力
- **摘要方向**：Kimi K3 把上下文推到 1M token。问题不只是“装得下”，而是生成每个新 token 时，既要快速处理漫长历史，也不能漏掉关键细节。本文用 KDA 拆解它如何让线性注意力与完整注意力分工。

## 核心结论

KDA 不是把注意力“压小”，而是让两种工作方式分工：大部分层用线性注意力把长历史持续写成高效的“会议速记”，少部分层保留完整注意力，必要时能回看“原始录音”。因此，百万上下文追求的不只是快，而是**快且不漏**。

## 叙事原则

- Kimi K3 的热点只作开场楔子，快速进入读者真正关心的问题。
- 本篇只讲 KDA；不展开 MLA 的原理，也不写成 KDA vs MLA 的胜负对比。
- 文章独立可读，只回顾“注意力会回看历史、找相关信息”，不重讲 QKV 推导。
- 全文统一用“会议速记 vs 回放录音”解释机制。
- 保留 **O(T²) → O(T)** 与 **3:1** 两个技术锚点，但不进行矩阵推导。

## 结构

### 开头：一台 2.8T 模型，为什么要为“回看历史”发愁？（~180 字）

- 热点事实只给一组：Kimi K3 是 2.8T 参数、1M token 上下文的开放 3T 级模型。
- 不接榜单、估值或名人评论，直接设问：它在一段超长任务里每生成一个新 token，难道还要从此前 100 万 token 的历史里逐一找线索？
- 用一个读者能感知的场景落地：让 Agent 读完整个代码仓库、执行几十轮修改后，再定位数百轮前的一条约束；它不能慢，也不能把那条约束忘掉。
- 转场：这就是 KDA 要处理的矛盾——**速度**与**找回关键细节**。

> 口径：2.8T 与 1M 均引自 Kimi K3 官方技术页；不沿用原大纲中的 2.5T。

### 第一段：为什么上下文一拉长，普通注意力会突然吃不消？（~250 字）

- 用两三句回顾：生成下一个 token 时，注意力要从历史中找与当前最相关的信息。
- 先说清 KV Cache 的作用：它避免反复计算旧 token 的 Key 和 Value；但每生成一个新 token，仍要向整段历史查询，历史从 10 万扩至 100 万，单步查询与缓存压力约增至 **10 倍**。
- 再给出整段输入时的平方墙：把一段历史整体送入模型（预填充）时，位置两两配对；长度从 10 万 token 到 100 万 token，工作量约增至 **100 倍**。

> **标准注意力：整段预填充约为 O(T²)；逐 token 生成仍随历史长度增长**

- 明确本篇的提问：若历史越来越长，怎样不反复“试听全部录音”？

### 第二段：线性注意力——先把录音变成会持续更新的速记（~300 字）

- 直觉：不再为每个新 token 翻遍所有旧 token，而是把历史逐步写进一个固定大小的状态；读下一句时直接读这份状态。
- 会议类比：不是保留一百万句录音并反复听，而是始终维护一份会更新的会议速记。
- 效率差异：处理整段历史时，长度增加 10 倍，线性路径的工作量约增加 10 倍；生成时则主要读取固定大小的状态，而不是逐一查询所有历史位置。

> **线性注意力：计算量随长度约为 O(T)**

- 只点到 KDA 的核心：它用更细粒度的门控更新有限状态记忆，目标不是“记得更短”，而是让这份速记在超长序列中仍有表达力。

### 第三段：只靠速记还不够——关键原话会被埋掉（~220 字）

- 反问：会议速记很高效，但读者若要核对一句措辞、一个例外条件，能只靠速记吗？
- 技术边界：线性注意力把历史压进有限状态，不应承诺“信息无损”；极少见但关键的精确关联，可能需要直接看完整上下文。
- 由此提出 KDA 的真正设计目标：不是用线性注意力替掉一切，而是让它承担大部分长程工作，再留出能精确回看的通道。

### 第四段：KDA 的答案——三次速记，一次回放（核心，~400 字）

- 先给结论：公开的 Kimi Linear 架构采用 **3:1 的 KDA : 全局完整注意力** 配比。
- 读法要精确：每 4 个注意力层中，3 层用 KDA 高效处理长历史，1 层让完整注意力访问全局上下文；不是“先挑几个 token 精读”。
- 继续会议类比：三位速记员负责快速整理会议脉络；每隔一次，允许一位工作人员回放原始录音，校验关键原话和关联。
- 用小图/一行结构表现分工：

> **KDA → KDA → KDA → 全局完整注意力 → 重复**

- 回扣核心：速度由多数线性层提供；“不漏”的保障来自仍存在的完整注意力层。KDA 的创新不是押注单一路线，而是按层分工。

> 注意：Kimi K3 官方页已确认采用 KDA，但未公开说明其层级比例。正文须把“3:1”明确归属为 Kimi Linear 的公开架构例证，不能写成 K3 已披露的具体配比。

### 第五段：把 1M 上下文从“能塞”变成“能用”（~220 字）

- 回到开头的 Agent 场景：长任务里，模型需要持续维护脉络（速记），也必须在关键时刻找回精确约束（回放）。
- Kimi K3 的 2.8T 与 1M 是问题规模；KDA 是它用来处理序列长度压力的基础架构之一。
- 边界说清：参数规模不是注意力成本的直接原因；真正推动注意力开销的是上下文长度，以及层数、隐藏维度等架构因素。
- MoE 只用一句带过：K3 同时以 16/896 的专家激活提升稀疏性，但那是另一条“减少每次计算量”的路线，本文不展开。

### 结尾：不是更快的摘要，而是有分工的记忆（~150 字）

- 一句话收束：KDA 让大多数层快速整理长历史，又不完全放弃精确回看的能力；百万上下文才有机会做到又快又准。
- 预告，不展开：今天讲的是“为什么要保留完整注意力”；下一篇再讲另一条路线——MLA 如何从 KV Cache 入手压缩记忆。
- 关注引导：关注后继续按“长上下文为什么贵 → KDA 的分工 → MLA 的压缩”拆解。
- 开放问题：如果让你设计长上下文模型，你会把更多层交给速记，还是把更多层留给回放？为什么？
