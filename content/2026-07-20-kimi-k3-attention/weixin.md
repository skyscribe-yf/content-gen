## 🎯 驱动问题：1M 上下文，难的不是塞进去

月之暗面发布 Kimi K3 时，最容易被记住的两个数字是 **2.8T 参数** 和 **1M token 上下文**；KDA 是它采用的注意力架构之一。

先别急着看跑分。

想象你让一个 Agent 读完整个代码仓库，改了几十轮代码，又在几百轮对话之后追问：

> “还记得一开始那条‘不能动支付接口’的约束吗？”

模型要找到它，不能每次都把一百万 token 从头翻到尾；但也不能为了快，把这条罕见却致命的约束忘掉。

**长上下文真正的难题，不是能不能装下，而是能不能又快又准地用起来。**

如果你对“注意力到底在做什么”还不熟，建议先回看[注意力机制那篇](https://mp.weixin.qq.com/s/KrilwX6VRjI9KfjvD7C6kw)：每个 token 会根据当前问题，从历史 token 中汇总自己需要的信息。今天只往前走一步：历史变成 1M token 后，这件事为什么突然变得昂贵？

![](01-long-context-dilemma.png)

*1M 上下文不是“塞得下”就够了：模型既不能慢，也不能漏掉关键约束。*

---

## 不是每次重算全部，但每次都得找历史

先澄清一个常见误解：模型生成新 token 时，通常不会把旧 token 的 Key 和 Value 从零再算一遍。

它会把旧 token 的 Key 和 Value 存进 **KV Cache**。这样，新 token 到来时只需要生成自己的 Query、Key、Value，再用自己的 Query 去和历史缓存匹配。

KV Cache 省掉了“重做旧题”，却没有省掉“查完整段历史”。

假设历史从 10 万 token 扩到 100 万 token。生成下一个 token 时，它需要面对的历史位置约多了 **10 倍**；KV Cache 也随之变大。对持续输出很长回答、不断调用工具的 Agent 来说，这个成本会一轮一轮累积。

更陡的一面发生在把整段历史送进模型的时刻，也就是预填充（prefill）。普通注意力里，位置之间需要两两计算关联：长度翻 10 倍，配对工作量约翻 **100 倍**。

> **整段预填充：计算量约为 O(T²)**

这就是为什么“支持 1M 上下文”不是在配置里填一个更大的数字，而是一道工程硬墙。

这两道墙，我们在[AI上下文为什么越长越慢？](https://mp.weixin.qq.com/s/PLVRS0TTHXHDve1Z3r6M7Q)里拆过一次：注意力的 **O(T²)** 计算墙，加上 KV Cache 的线性存储墙，会让“记得更长”迅速变成一笔算不过来的账。今天这篇只追问下一步：KDA 怎么改掉其中“反复回看历史”的做法？

会议类比会让它更直观：普通注意力像开会时，每来一句新话，都允许你在此前所有录音片段里逐一找关联；会议越长，可查的录音就越多。它很细，也很贵。

![](02-attention-cost-wall.png)

*从 10 万到 100 万 token：逐 token 生成的查询与缓存压力约增 10 倍；整段预填充的配对工作约增 100 倍。*

---

## 线性注意力：别反复翻录音，持续写一份速记

线性注意力的换法很大胆：不再把“逐一翻所有历史位置”当作默认动作。

它会维护一个固定大小的**状态**。每读到一个新 token，就把有用的信息更新进这份状态；下一个 token 来时，直接读取状态，而不是重新查询所有历史位置。

> **线性注意力：处理整段序列的计算量约为 O(T)**

还是那场会。

普通注意力像保留所有录音，再不断回放；线性注意力像有一位很强的速记员，会议一边开，一边把重要信息写进一份持续更新的笔记。会议从 10 分钟延长到 100 分钟，速记工作量大致也只延长 10 倍。

KDA 的关键词是 **Delta**，也就是“变化量”。它不是把每句话原样塞进状态，而是让新信息以“对已有记忆做多少修改”的方式写入；门控机制再决定哪些修改该保留、该衰减、该放大。公开的 Kimi Linear 架构把它描述为：用更细粒度的门控，优化有限状态记忆的使用。

不用记住算法细节。这里最重要的直觉只有一句：

**KDA 让模型不必每次都在百万条历史里重新翻找，而是先读一份会随对话更新的“会议速记”。**

![](03-meeting-notes.png)

*线性注意力不反复翻全部录音，而是持续维护一份有限状态的“会议速记”。*

## 但只靠速记，会不会漏掉关键原话？

会。

这不是 KDA 特有的缺点，而是所有有限状态记忆都要面对的取舍：一份速记再聪明，容量也不是无限的。

会议里大部分内容，写成“决定采用方案 A，风险由小王评估”已经足够；可如果后面发生争议，真正需要核对的可能是三小时前某人加的一句限定：

> “方案 A 可以用，但支付接口绝对不能改。”

只看速记，模型可能抓住了“采用方案 A”，却把“不能动支付接口”压得不够醒目。对闲聊，这是小误差；对长程编程、合同审阅或研究任务，它可能直接改变结果。

所以，不能把线性注意力宣传成“信息无损”。更准确的说法是：**它用有限状态换来了高效率，也必须想办法保留回看全局细节的能力。**

到这里，KDA 真正有意思的地方才出现：它不是要求所有注意力层都只当速记员。

---

## KDA 的答案：三次速记，一次全局回看

公开的 Kimi Linear 架构给出了一种很清楚的分工：**3 个 KDA 层，配 1 个全局注意力层。**

可以把它画成这样：

> **KDA → KDA → KDA → 全局注意力 → 重复**

前三层大部分时间负责高效地整理长历史；到第四层，模型保留一次面向全局上下文的回看机会。速记负责让会议继续开下去，全局回看负责在必要时重新建立远距离信息之间的精确联系。

这和“先筛出几个 token，再精读它们”不是一回事。它是**按层分工**：有些层负责把长序列跑得动，有些层保留能看完整个上下文的能力。

会议类比也要随之升级：不是一个人先猜哪些录音重要，而是三位速记员持续整理会议脉络；每隔一次，就有一位工作人员可以面对整套录音档案做全局核对。

于是，KDA 的目标就很明确：

- 多数层走线性路径，避免长历史把计算和缓存拖垮；
- 少数全局层留在系统里，避免模型只剩一份容易失真的摘要；
- 两种能力叠起来，才有机会让超长上下文既跑得动，也找得到关键细节。

这里有一个必须说清的口径：K3 官方页确认它使用 KDA，但**没有公开披露 K3 的具体层级配比**。上面的 3:1 来自 Kimi Linear 的公开架构，用来理解 KDA 的混合思路；不能写成“已知 K3 就是 3:1”。

![](04-kda-three-to-one.png)

*3:1 是 Kimi Linear 的公开架构例证，不是 Kimi K3 已披露的具体层级配比。*

## 2.8T 不是注意力变贵的直接原因

看到 2.8T 参数，很容易得出一句顺口的话：模型太大，所以注意力必须高效。

这句话方向没错，但因果还不够准确。

**让注意力成本陡增的直接变量，是上下文长度。** 层数、隐藏维度、注意力头的配置也会影响成本；2.8T 参数则说明这是一个不能随便浪费计算的大系统，却不是“注意力从 O(T²) 变贵”的唯一原因。

Kimi K3 的 1M 上下文，正好把这个矛盾推到台前：它想做长程编程、知识工作和推理，模型就得在很长的历史里持续工作。KDA 提供的是一条注意力层面的回答——把“全局逐一回看”从每层的默认动作，改成更有分工的系统。

K3 还把 MoE 的稀疏性推到“896 个专家里激活 16 个”。那是在回答另一道题：每次前馈计算该唤醒多少专家。想先弄清 MoE 为什么会挑少数专家干活，可以回看[DeepSeek便宜30倍的秘密：MoE混合专家入门](https://mp.weixin.qq.com/s/QdkD0CR2fD-HfY77-gX3Ug)：它讲的是“叫谁干活”；KDA 讲的是“怎么记住历史”，两者不要混在一起。

把这两条路线分开，才能看懂大模型为什么越来越像一个精细的系统工程：不是只把模型做大，而是让该省的地方省、该保留的能力保留。

---

## 回到开头：1M 上下文，靠的不是更大的记事本

Kimi K3 的 1M 上下文，真正值得看的不是“它可以一次塞进多少文本”，而是它怎么处理这段历史。

KDA 给出的思路是：

- 普通注意力在长序列上，整段计算会遇到 **O(T²)** 的配对墙；即使有 KV Cache，生成时也要面对越来越长的历史。
- 线性注意力把历史维护为有限状态，像持续更新的会议速记，让长序列的处理更接近线性增长。
- 但速记不能代替一切。公开的混合架构会保留全局注意力层，让模型不至于只靠一份摘要做决定。

所以 KDA 不是“更快的摘要器”。它是一种分工：**大多数时候快速整理，关键时刻仍能全局回看。**

下一篇，我们换一个完全不同的视角：如果不先改变“怎么回看”，而是先减少 KV Cache 这份记忆本身的体积，MLA 又是怎么做的？
