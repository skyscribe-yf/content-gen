## 结构（悬念链：小标题连起来是完整故事）

**开头（无标题，~180 字）**
- 场景钩子：我把一段 60 行的代码交给 agent，让它补测试。它补了二十几条，全绿，覆盖率 96%
- 反转：我把埋进去的 bug 摆出来——它写的断言里，有一条正好把这个 bug 的行为写成了预期值
- 驱动句（独立成段）：测试一个都没漏，它只是从没被告知「应该是什么」

**## 一、它不是不会写测试，是你没让它优化这个（~450 字）**
- 实验场景 A：正确实现 + 15 个手写变异体，两臂对照（同模型、同代码）
  - A 臂 prompt：「补测试，覆盖率尽量高」→ 覆盖率 X%，杀掉 n/15
  - B 臂 prompt：「目标是杀死变异体」→ 杀掉 m/15
- 结论：换目标函数，数字就上去了——**不是能力问题，是目标写错了**
- 但 B 臂也没到 15/15，剩下那几个正是「我没想到要测」的边界（引出下文）
- 【配图①：两臂杀伤率对比（脚本图）】

**## 二、验证器说全过，可能只是你的规格太弱（~400 字）**
- intent formalization 一句话定义：把「我想要什么」变成机器能检查的东西。Lahiri：瓶颈不在生成规格，在验证规格——**规格没有 oracle，除了用户本人**
- VeriAct 的 VR / MVR：验证通过率很高，但要求后置条件「既正确又完整」之后明显掉档（MVR 门槛：两项都 ≥0.5）
- 极端例子：一个 `true` 永远能过验证
- Verus-SpecBench（581 题、Codeforces 转 Verus）：失败模式三种——漏掉输入前提 / 接受错误输出 / 拒绝正确输出。**最后一条反直觉：规格太强也是错**
- 【配图②：VR vs MVR 落差（脚本图）】

**## 三、真正致命的是代码本来就错的时候（~400 字）**
- 回到场景 B：我往实现里埋了一个 bug，再让 agent 补测试。它给这个 bug 的行为写了断言，测试全绿
- ISSTA 2026 复现研究（11 个模型 / 10 万+ 用例 / Defects4J）：覆盖率与变异分数**只在「被测代码可假定无 bug」的回归场景、且只在跨模型比较时**才有信号；模型内部相关性普遍 <0.2
- 一旦代码本身有 bug：覆盖率失效，变异分析**根本不适用**（它预设测试全绿）
- 落点：上一节那套指标，在你最需要它的时候正好不灵
- 【配图③：bug 被写成断言的示意（脚本图）】

**## 四、你给的测试，就是它的目标函数（~350 字）**
- SpecBench（30 个系统级任务）：可见验证套件 vs 隐藏组合套件，Δ = 两者通过率差；隐藏套件**不引入新需求**，只要求特性可组合
- 所有前沿 agent 都能把可见套件刷满；Δ 的 90 分位随代码量 ×10 再涨约 28pp
- 最扎心的案例：Claude 那个 18.6 万行 C 编译器，验证 97.8% / 隐藏 83.3%，差的 14.5pp 几乎全在「拒绝非法 C」——GCC 那 900 多个测试只验证「对的程序输出对」，从没验证「错的程序要报错」
- 泼冷水（两条）：
  - 增加可见测试的覆盖，Δ 不保证缩小：SQL 库从 35pp 降到 9pp，C 编译器反而涨 25pp
  - 多数不是作弊：deliberate exploits 很少，组合失败占大头
- 【配图④：SpecBench Δ 图（脚本图，数字与正文一致）】

**## 五、三件套，以及它们各自的失效边界（~350 字）**
- 变异测试：只在「代码可假定对」时成立（承接第三节），用它当规格强度计要先验前提
- held-out 组合测试：不引入新需求、只要求可组合——这才是 Δ 的意义；但它测不到「我没想到的那一维」（CCC 的错误检测）
- 人类抽样：Fun2spec 人工核 100 条 → 2 错 / 41 条达最强；LLM-as-judge 漏检率约 26%，不能替代人
- 补一条：SWE-Mutation（ACL 2026）用 agentic 变异体，把检出率从 71.04% 压到 39.81%——手写变异体可能低估难度
- 【配图⑤：三件套失效边界表（脚本图）】

**## 六、语言能给的，只有稳定语义和可读位置（~250 字）**
- Fun2spec 的动机直接写着 C++ contracts 标准化：百万行 C++ 上合成后置条件，最高 87% test-validity——「要不要契约」在工程上已不是问题
- 语言能做的不是替你写规格，是让规格 (a) 语义稳定 (b) 工具可读 (c) 执行义务明确；C++26 contracts 给了 (b)，弱在 (a)(c)
- Búzios 11-16~21 悬念收尾
- 互动问：你的项目里，有没有一条测试是 agent 写的、你从没读过它的断言？

## 实验设计（写稿前必须跑完）

| 项 | 口径 |
|---|---|
| 被测代码 | `parse_duration("1h30m")` 类时长解析，≤60 行 Python，边界密集（空串 / 重复单位 / 大小写 / 负数 / 超长 / 纯数字） |
| 场景 A | 给**正确**实现 + 「请补测试」；两臂：A1「覆盖率尽量高」/ A2「目标是杀死变异体」 |
| 变异体 | 手写 15 个，每个一行改动，全部可解释（off-by-one / 边界方向 / 大小写处理 / 空输入 / 单位换算系数…） |
| 场景 B | 给**含一个隐蔽 bug** 的实现（如 `"1h30m"` 在重复单位时覆盖而非累加，或大小写混用时返回 None），同样的补测试 prompt |
| 主模型 | Claude（claude CLI 2.1.293，headless） |
| 复核 | DeepSeek 跑一遍场景 B，结论写一句进脚注 |
| 记录 | 每个 prompt 原文、返回的测试全文、每个变异体的生死、场景 B 里 agent 写的那条断言 |

### 槽 3 · 第二节「规格没有 oracle」之后
- 状态：已填
- 类型：判断 / 亲历

### 槽 4 · 第三节「代码本来就错」之后
- 状态：已填
- 类型：亲历
- 原句：很多次看到，一个coding agent会把代码库里面本来有问题的实现代码作为一个基本假设，然后在错误的道路上一路狂奔。事实上，从底层原理来看，带入上下文的错误代码或者混淆信息，agent很难做具体的分辨，并且因为模型困惑度的增加（前面文章提过）而导致看起来模型被降智的情况出现。
