## 定位

- 读者：看 AI 和工程的人，不是 Elixir 用户。转发场景是技术群里要决定「这张图能不能引用」的人。
- 任务：读完能说清一句——150 倍和 4.4 倍不是同一轮优化的成绩。
- 不站队。不回答该不该改写成 Rust。

## 结论

**只证明这一句**：公开图上的约 150 倍，和仓库初版说明里的 4.4 倍，不是同一轮成绩，不能并成「Rust 赢了 150 倍」。

不证明：Rust 更快、Elixir 被亏待、DHH 在作弊、agent 时代就该改 Rust。

## 标题

定稿：**Agent 写的 Rust 快了 150 倍，为什么第一版只快 4 倍？**

前 22 字含 Agent、Rust、150 倍。标题「4 倍」是约数，正文写 4.4。问的是记分牌。

## 结构

**开场（无小标题，约 220 字）**

先摆 The Register 2026-10-07 引的房间页：Rust 每秒 36,260 个请求，Rails 241，Elixir 722，Go 3,860。36,260 / 241 约 150 倍。

下一段立刻翻案：Rust 仓库自己的初版说明写着，房间页相对 Rails 是 4.4 倍，后面那份说明是在规划怎么把它抬到大约 11 倍。作者原话接在这里，一句就停：「这年头，反转可太多了。」

驱动问题与标题同一句。

**一、这张图量的是房间页（约 280 字）**

- 只钉核对过的房间页四个数。另外四项任务 Register 说 Rust 也领先，具体请求数没核到原图，正文不写。
- 他没说用的哪家模型。原话口径是：原版代码不长，每次改写几个小时。
- 这一节不评谁赢。把「150 倍」收成「房间页、那张公开图、那一个时点」。

**二、第一版自己写着 4.4 倍（约 360 字）**

- 出处是 `basecamp/once-campfire-rust` 的 `plans/perf-attribution.md`：初版基准里房间页 4.4 倍，同一份文件在算怎么抬到约 11 倍。这是仓库自己的字，不是评论区算的。
- jskalc 2026-10-05 说 Elixir 第一版是 Rails 的 3.3 倍。这是第三方说法，正文标明，不跟 4.4 并成官方对照。
- José Valim 2026-10-05 原话方向：Rust 有几百个 commit、好几轮优化、跨了几天；另外几份是初始 agent 改写的 1 到 2 个 commit。他还说各份的要求不一样，Go 的说明把 Rust 当范本，Elixir 的说明对的是 Rails。进正文前再打开那条帖，按原句引用。
- 398 这个整数、18 或 16 个性能 PR，是 10 月 5–6 日的第三方清点。GitHub API 当日限额，本大纲没有重数。正文写「第三方清点，截至那两天」，不写死 398，除非成稿前对上仓库。
- 图 `01-two-rounds.png` 只画两个已核对的数：初版 4.4 倍，公开图约 150 倍。不把 398 画上去。

**三、Elixir 那份代码，查询排成了一队（约 280 字）**

- Zach Daniel 的说法：agent 交出来的 Elixir 把 SQL 收进一个 GenServer，查询在那里串行等待。
- 人话一句：所有数据库查询排成一队，一次只办一件。
- 紧接半句：这是说简单了。Elixir 可以同时查，是这份代码把查询收进了一个进程。
- 不解释进程，不解释邮箱。没有提示词，不猜模型为什么写成这样。
- Register 还写了：有人改写 Elixir 之后，有些任务上 Elixir 超过了 Rust。具体超过多少没核到原帖数字，正文只保留「有些任务上反超」，不写倍数。

**四、他的反方：前提换了，比赛就换了（约 420 字）**

三步，节末不宣布谁赢。

1. 他原来扛住 Ruby 慢，是因为人还在读代码。原话方向：「生产率带来的回报很大的时候，我不在乎性能。」Register 引的是 productivity and developer joy。
2. 前提换成「人不读了」。他 9 月 28 日写过：代码丑、啰嗦 6 倍，他一眼没看，这是 prompt 的编译目标。10 月 4 日又写：要看的是前沿 agent 在不同环境里开箱交出来的东西。记分牌就只剩 agent 交出来的那一版。
3. 「专家能写出更快的 Elixir」打的是另一场比赛。他的原话方向：前沿 agent 找不到加速开关，不能算 Elixir 加分。专家不在他的前提里。

这一节要让读者看见张力，不替任何一边收束：他说自己量的是开箱成绩，公开图上的 150 倍却落在几百个 commit 之后。把这两句并列，不写「所以他自相矛盾，因此输了」。

编译慢只带一句：他自己提过 Rust 编译可以很慢。不展开。

**五、第二天，记分牌换人了（约 180 字）**

- 2026-10-08 他发：让 agent 跑了一天，过了一遍提交上来的 PR，能对上的就合并，再把架构改进带到每个实现里。老 C 现在领先。
- 同一天他还说：有一份 PR 数字很好看，对不上，就没算。
- 不写 C 的请求数。原图没核到。
- 这一节的用处是把开头那句「反转可太多了」做成第二件事实，不是新结论。

**结尾（约 160 字）**

把开头的判断再说一遍：150 倍和 4.4 倍不是同一轮。不另起「所以该不该改 Rust」。

留言问题：你发版时会引用第一版的 4.4 倍，还是调完的 150 倍？

点赞、收藏、关注按账号惯例。不写下一篇预告。
