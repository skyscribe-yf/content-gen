先看一张这两天刷屏的图。Ruby on Rails 作者 DHH 做了个实验。AI agent 把他的 Campfire 聊天应用，分别改写成 Elixir、Go、Rust。再和原版 Rails 比速度。The Register 10 月 7 日报道引了那张图。房间页的数字是：Rust 每秒 36,260 个请求，Rails 241，Elixir 722，Go 3,860。

36,260 除以 241，大约 150 倍。

![公开图上的房间页：Rust 每秒 36,260 个请求，Rails 241，Elixir 722，Go 3,860（The Register 2026-10-07 引）](02-room-page.png)

看到这，你可能已经给 Ruby 判了死刑。别急。

Rust 仓库自己的初版说明里写着：第一版改写的房间页，相对 Rails 是 4.4 倍。同一份文件还在规划，怎么抬到大约 11 倍。已经见到太多不经实践就盲目吸引眼球的自媒体瞎震惊后，我早就对这些数字免疫了，看到这些数字，第一印象就是想去查查看，背后是否有猫腻？

这年头，反转可太多了。

150 倍和 4.4 倍，不是同一轮成绩。这就是本文唯一想证明的事。

## 一、这张图量的是房间页

先把数字钉死。图上量的是房间页，就是一个聊天室页面。截至发稿，这张图被浏览了超过 90 万次。

两点说清楚。第一，其他几项任务 Rust 也领先，数字没核到原图，不写进来。第二，DHH 没公开用的是哪家模型。

所以「150 倍」的准确说法是：房间页、那张公开图、10 月初那个时点。离开这三个条件，这个数就失去了锚。

## 二、第一版自己写着 4.4 倍

4.4 这个数，出处不在评论区，在仓库里。Rust 改写版开源在 `basecamp/once-campfire-rust`。仓库里的 `plans/perf-attribution.md` 记录了初版基准：房间页相对 Rails 4.4 倍。后面还在规划，怎么抬到大约 11 倍。写这份 Rust 的人自己知道，第一版离极限还远。

对于高强度实践了AI coding一年多的我来说，想要达成某方面特别好的效果，还是要使用者付出很多精力做指令下发，和不断调整的。

后来的差距是补出来的。第三方 10 月 5 日到 6 日清点：Rust 版第一版之后，又吃进几百个 commit、十几个性能优化 PR。大部分来自 DHH 本人（未亲自重数）。Elixir 初版按 jskalc 的说法是 Rails 的 3.3 倍，同样是第三方说法，不跟 4.4 并成官方对照。

Jose Valim（Elixir 语言作者）指出另一层不对等。Rust 版几百个 commit、跨好几天，另外几份只是初始改写的 1 到 2 个 commit。各份要求也不一样——Go 版说明把 Rust 当范本，Elixir 版对标的是 Rails。

![同一张记分牌，两种投入量：Rust 版几百个 commit、跨好几天；Elixir / Go 版只有初始改写的 1~2 个 commit](05-commit-gap.png)

150 倍那张图，量的是补完之后的样子。把两轮成绩并成一句「Rust 赢了 150 倍」，量的是谁，说不清。

![同一个房间页，两轮成绩：初版 4.4 倍，优化后的公开图约 150 倍](01-two-rounds.png)

## 三、Elixir 那份代码，查询排成了一队

那 Elixir 的 722 是不是「语言不行」？Zach Daniel 指出一个具体问题。agent 交的 Elixir 版，把 SQL 查询收进了一个 GenServer。所有数据库查询排成一队，一次只办一件。

这是说简单了。Elixir 可以同时查，是这份代码把查询收进了一个进程。看起来傻，但不全是语言的账。

以今天AI产生代码的速度之高，一一查看早就不太现实了，但是基本的架构选择和技术决策，和AI简单聊两句让它给一个事实陈述，绝大部分情况下准确率还是相当高的。类似这种看起来非常傻的代码，并不能算作语言不行，更多应该看作是，指挥agent来生成代码的人，没有一个持续一致的心智模型来引导AI持续创造和维护所期望的代码行为边界。

The Register 还提到：有人改写 Elixir 后，某些任务上反超了 Rust，幅度没核到，不给倍数。722 后面站的是一份有缺陷的初版代码，不是一个语言的极限。

![agent 交的 Elixir 版把 SQL 查询收进一个 GenServer，查询排成一队；Elixir 本来可以同时查](03-elixir-queue.png)

## 四、他的反方：前提换了，比赛就换了

看到这里，你可能觉得 DHH 的记分牌问题很大。但他有一套自己的逻辑。

第一步，他原来为什么能接受 Ruby 慢？因为人还在读代码。The Register 引的词是 productivity and developer joy。人和开发体验，把性能抵掉了。

第二步，前提换了。9 月 28 日他写过：agent 交出来的代码丑、比人写的啰嗦 6 倍，他一眼没看。这套 prompt 的编译目标，本来就不是给人读的。10 月 4 日他又写：要看的，是前沿 agent 在不同环境里开箱交出来的东西。代码没有人读，但是设计决策和可维护性方面的高层规划，还是需要人来做的，因为LLM至今，在实践上还困在概率采样的世界里尝试做非常复杂的短期高精度模式匹配，超长程任务都还是一个巨大挑战，更不要说跨越几天，几周，甚至几个月的一致性考虑和约束，目前来看，都还有非常多的问题需要人类来维持。前提换成「人不读了」，记分牌上就只剩 agent 开箱交出来的那一版。

第三步，「专家能写出更快的 Elixir」是另一场比赛。前沿 agent 找不到加速开关，不能算 Elixir 加分；专家不在他的前提里。

把两句事实并列在这：他说自己量的是开箱成绩；而公开图上的 150 倍，落在几百个 commit 的优化之后。怎么摆平，读者自己称。

![他的反方：原来的前提是人还在读代码，换过之后的前提是代码没人读了](06-premise-switch.png)

## 五、第二天，记分牌换人了

这场对账还没完。

10 月 8 日，DHH 又发一条。agent 跑一整天，过一遍社区提交的 PR，能对上的就合并，架构改进带给每个实现。结果一句话：Good old C is now in the lead——老 C 领先了。

同一天他还说：有一份 PR 数字很好看，但对不上，就没算。

不得不说在自媒体持续轰炸之下，现在人们的注意力是越来越短了，然而好饭不怕晚，有些残酷的事实真相还是需要比较长的时间才能水落石出，或者甚至是跌宕起伏，难见终章。

「这年头，反转可太多了」，这是第二件证据。第一天 Rust，第二天 C——这张记分牌上任何数字，保质期都只有一天。

![这场对账的时间线：10 月 7 日报道引图 Rust 约 150 倍，10 月 8 日老 C 领先](04-scoreboard-timeline.png)

## 结尾

回到开头那句判断：150 倍和 4.4 倍，不是同一轮优化的成绩，不能并成「Rust 赢了 150 倍」。至于该不该改写成 Rust，这张记分牌回答不了。

在大家都不看代码疯狂vibe coding的当下，你觉得这些性能方面的喧嚣和编程语言的争论是否结束了，还是鹿死谁手，尤未可知呢？
