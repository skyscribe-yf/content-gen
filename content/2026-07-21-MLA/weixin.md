昨天我们聊了 [Kimi K3 的 KDA](https://mp.weixin.qq.com/s/_RR5LLWgjGNm-qXdSdnAGA)——线性注意力，用"会议速记"的思路绕开长上下文的 O(T²) 配对墙。那是 Kimi 的方案：换个方式算注意力。

今天换一个角度，看同一道难题上 DeepSeek 的答案。KDA 解决的是"怎么算得过来"——MLA 解决的是"怎么存得下"。**为什么模型参数没变，聊天聊长了，显存却还是会爆？**

---

## 你的显存，可能不是被模型权重吃掉的

我第一次把 RTX 4090（24GB 显存）塞进机箱的时候，心想：24GB，够了吧。

当时跑的是一个 7B 模型，4-bit 量化，模型本身只占 **4GB 多**。头几天一切正常。直到有一天我拖了一整篇论文进去让它分析——大概 30 页 PDF，切完 token 差不多 25K 上下文。聊了没几轮，OOM。

我第一反应跟所有人一样——"显存不够，该换卡了"。直到我用 `nvidia-smi` 盯着显存看了一下午，才发现一件让我头皮发麻的事：**模型权重加载完就不动了，但显存还在匀速涨。每多聊一句，多吃几十 MB。**

什么东西在长？

模型权重像一本已经印好的百科全书：加载进显存后，大小基本不再变化。真正会在对话过程中不断变胖的，是 **KV cache**——模型为记住前文留下的一摞"阅读笔记"。我那个 7B 模型在 25K 上下文下，KV cache 已经膨胀到 **~10GB**——比模型本身还大一倍多。

> 模型权重像煤矿：挖出来、放在那里，体积基本固定。
>
> KV cache 像进出矿区的货车：每说一句话又来一辆，越积越多，最后把路堵住。

这个现象在消费级显卡上只是"有点烦"，到了服务器级就变成了硬瓶颈。

以 LLaMA-3-70B 为量级参照（这里说的是 8×A100 80GB 或 2×H100 80GB 上的部署，不是 4090——70B 模型单张 4090 根本装不下，即使 4-bit 量化也要 ~35GB，超过 24GB 上限）。

在 BF16 精度、100K 上下文下：模型权重大约是 140GB，KV cache 约 31GB。

**31GB 是什么概念？** 一张 A100 有 80GB 显存，光 KV cache 就占了近四成；两张加起来才 160GB，KV cache 吃掉近五分之一。而且上下文继续变长——权重不动，KV cache 还会继续长。

> 注：这里的计算基于 BF16（16 位，每参数 2 字节）。今天的模型几乎不会这样存储权重——早已推进到 INT8/INT4 甚至更稀疏的量化。以 INT4 为例，70B 权重大约只有 35GB，但 KV cache 该 31GB 还是 31GB，此消彼长之下 KV cache 反而成了更大的那个。后面的比例图如果按量化权重重画，KV cache 的占比还会更高。

我后来跟一个做推理部署的朋友聊起这件事，他说了一句让我印象深刻的话：**"大家以为买显存是在买模型的门票——其实一大半是在付对话的房租，而且是按 token 计费的。"**

说到这个——你可能会想：7B 太小了，换个大的不行吗？GLM-5.2 能不能装进 4090？

来，算一笔账。GLM-5.2 是 MoE 架构，总参数 **753B**（40B 激活），用到了和 MLA 一样的低秩压缩来省 KV cache。从 [HuggingFace 公开的 config.json](https://huggingface.co/zai-org/GLM-5.2/blob/main/config.json) 掏真实数字：78 层、KV 压缩到 512 维、外加 64 维 RoPE key。

算下来，每 token 的 KV cache 约 **88 KB**。128K 上下文一开——**光历史记录就 10.7 GB**。模型还没装呢。

模型本身呢？753B 参数，就算你压到 4-bit 量化也要 **~377GB**。一张 4090 24GB——显卡直接笑出声。你就是买十六张 4090 串起来，刚够装模型权重，KV cache 另算。

所以你看，我那个 7B 小模型在 4090 上还能苟一苟，换成 GLM-5.2 连门都进不去。显存这台账，算到最后全是 KV cache 的锅。

![](01-kv-ratio.png)

所以，判断一个模型能否处理长文本，不能只问"它有多少 B 参数"，还得问：**每多一个 token，它要留下多少 KV cache？**

## KV cache 到底在记什么？

[注意力机制那篇](https://mp.weixin.qq.com/s/KrilwX6VRjI9KfjvD7C6kw)我们详细拆过 Q、K、V。这里只抓最关键的一点：模型生成下一个 token 时，拿当前的 Query 去查前面所有 token 的 Key，按结果汇总 Value。

我一开始的理解是——那每次推理把前面所有 token 的 K、V 重新算一遍不就行了？后来才知道这个想法有多天真。重新算一遍 128K 上下文的 K、V，推理延迟会炸到没法用。所以必须缓存。这份缓存，就是 KV cache。

每生成一个 token，KV cache 就多一条记录；每一层注意力都要留记录。因此它的大小近似满足：

> **KV cache ∝ 层数 × 上下文长度 × KV 头数 × 每头维度**

它最容易被忽略的性质是：**线性增长，而且不会自己停。** 上下文从 32K 翻到 128K，KV cache 也翻四倍。模型权重一字未增，显存预算却可能已经不够。

在[《为什么 AI 上下文越长越慢？》](https://mp.weixin.qq.com/s/PLVRS0TTHXHDve1Z3r6M7Q)里，我们讲过长上下文的两道墙。KV cache，就是其中那道"存储墙"的砖。

这个公式我盯着看了五分钟。**层数、长度、头数、维度——四个数全是乘在一起的，一个都绕不过去。** 当时就想：除非有人把这四个数里的某一个砍掉一大截，否则没戏。

## 实习生和便利贴

后来我是这样真正理解这件事的——

想象你是一个实习生，老板让你做会议记录。你坐在桌子尽头，每有人说一句话你就写一张便利贴，贴在面前的墙上。会开了一个小时，墙上贴了 200 张。这时老板突然问："第一分钟，老张说了什么？"

你从 200 张便利贴里翻。找到了，回答。但找的过程比会本身还长。

更要命的是，隔壁会议室也在开会——每间会议室都有自己的一面墙。30 层楼，每层十几间会议室。你是唯一的实习生。

好了，现在告诉我，你要怎么办？

你的第一个本能反应可能是：我少写几份，几间会议室共用一份记录。这就是 GQA——少雇几个做记录的实习生。

但你真正想要的，其实不是少写几份。你想要的，是**每张便利贴本身能不能只写一行关键词，而不是抄整个句子。**

这就是 MLA 的直觉。KV cache 就是那面墙上的便利贴。GQA 是少雇几个做记录的实习生——MLA 是把每张便利贴本身写得更短。

> GQA：少记几份完整笔记。
>
> MLA：每份笔记只写关键词，需要时在计算里把上下文补回来。

说实话，我第一次把这个想法讲给朋友听的时候，他的反应是——"压缩？那信息不就丢了吗？"我说你先别急，后面有数学兜底。

## GQA 减了一份，MLA 减了更多

GQA（Grouped-Query Attention）的思路非常朴素：让多个 Query 头共用同一组 K、V。好比原来每个人各有一名秘书记笔记，现在几个人共用一名秘书；KV cache 能小到原来的 1/4 甚至 1/8。

但 GQA 有个天花板——它仍然在保存完整的 K、V 向量，只是副本变少了。你省的是"份数"，不是每条记录本身体积。

我承认，我刚开始看 DeepSeek 论文的时候，以为 MLA 就是 GQA 换了个皮肤。毕竟"压缩 KV cache"这个说法，GQA 也能沾上边。看了 Table 9 的数据才闭嘴——**MLA 不是让记录变少，是让每条记录本身从一个完整向量变成了一行摘要。**

所以 DeepSeek 换了一个问题：**能不能不存全文，只存一份足够用的摘要？**

这正是标题里"省下约九成"的含义：它说的是 **KV cache 这笔开销**，不是说一台机器的全部显存都会自动少九成。

## MLA 的三步：摘要、改写问题、另存位置

好了，终于要拆 MLA 本身了。设计上看有三步，但直觉上其实是一条线。

![](02-mla-flow.png)

### 第一步：先写摘要，不存完整笔记

传统注意力会把每个 token 的完整 K、V 都存下来。MLA 先把当前 token 的隐藏状态压到一个更小的潜在向量 cᴷⱽ。在 DeepSeek-V3 的公开配置中，这个 KV latent 的维度是 **512**。

它不是随便删掉信息。这一点很重要——你要是手写一个规则说"保留前 512 维、扔掉后 15,872 维"，那就是随机丢失。但 MLA 的下投影矩阵是训练出来的。**模型自己在几万亿次试错中学会了：哪些维度的信息对回头查最有用，哪些可以丢掉。**

你在[词嵌入那篇](https://mp.weixin.qq.com/s/rDryn1z_hLt7mwi3X8fsxQ)看到的中药柜，是"用出来的"语义空间。MLA 的压缩投影，也是"用出来的"摘要——不是人设计的，是梯度逼出来的。

### 第二步：不解压，改写提问方式

我第一次看到这步的时候，脑子里的反应是——"摘要肯定不够用，到时候不还是得解压出来算吗？"

然后我看到了矩阵吸收。老实说，它花了我三天才想通。三天里我翻了三篇博客、看了原论文附录、还用草稿纸推了两遍——每次推到一半就卡在同一个地方："为什么可以先乘 Wᵁᴷ 再算注意力？顺序不对吧？"

直到我把矩阵乘法的结合律写在一行里。

若完整 Key 可以写成 K = Wᵁᴷ · cᴷⱽ，那么：

> **Q · (Wᵁᴷ · cᴷⱽ)ᵀ = (Q · Wᵁᴷ) · (cᴷⱽ)ᵀ**

左边是"先还原完整 K，再提问"；右边是"先把 Q 的提问方式改写，再直接问摘要"。结果相同。

关键在这：**右边需要的 cᴷⱽ 就是那行关键词，不需要先解压成长篇全文。** 于是推理时不必把每一条历史记录真的解压成完整 K——这就是矩阵吸收。

我后来用一个更蠢的理解记住了它：你要查"张三的生日"，不用先把整本通讯录背下来；只需要知道张三那一行的页码。矩阵吸收就是这个"知道往哪翻"的操作，它把"还原"从计算图里删掉了。

说实话，看懂这一行的时候我有点生气——就这么简单？我卡了三天，最后是一行结合律。

### 第三步：位置单独记，别把它搅进摘要

还有一个麻烦：K 不只携带内容，还携带位置。RoPE 位置编码会告诉模型"这个词在第几个位置"。如果把位置旋转和内容压缩硬混在一起，前面的矩阵吸收就不再好用——因为旋转操作不满足结合律，它会卡在中间，让你没法先把 Wᵁᴷ 乘到 Q 上。

这就尴尬了。你刚找到一个漂亮的数学等价变换，位置编码就告诉你——不好意思，不兼容。

DeepSeek 的做法是 Decoupled RoPE（解耦 RoPE）：

- 内容走压缩通道，留下 cᴷⱽ；
- 位置走独立通道，留下很小的 RoPE key；
- 两路在计算注意力时再共同发挥作用。

可以把它理解为：会议纪要写摘要，日期和座位号放在单独的索引卡上。摘要可以很短，索引也不会丢。

有时候工程就是这样——两个问题搅在一起无解，把它们拆成两路各管各的，突然就有解了。说实话，我越来越觉得，好架构师的直觉不是"把东西做复杂"，而是"把耦合拆开"。

## "省下90%"到底是怎么比较的？

这里需要把口径说清楚。我自己第一次写这篇文章的时候，差点写成了"MLA 省了 90% 显存"——被朋友纠了回来。省的是 KV cache，不是全部显存。显存里还有权重、激活值、优化器状态……KV cache 只是其中一笔账。

DeepSeek-V2 的技术报告做过成对实验：在其他架构尽量对齐的条件下，把注意力机制分别设为传统 MHA 和 MLA。结果是，MLA 的 KV cache 在小型 MoE 对照中是 MHA 的 **14%**，在大型 MoE 对照中是 **4%**。

换句话说，KV cache 分别减少了 **86%** 和 **96%**。标题里的"90%"是这个区间的通俗说法，不是承诺所有模型、所有显存都固定减少 90%。

我第一次看到 Table 9 的那两行数字——110.6K 变成 15.6K，860.2K 变成 34.6K——我心里想的不是"哇，好厉害"。我想的是：**如果我是审稿人，我会要求他们解释"为什么压缩这么多还能打平"。** 论文确实做了这件事，用 JL 引理给了理论支撑。

| 对照实验 | MHA 的每 token 缓存 | MLA 的每 token 缓存 | MLA 保留比例 |
|-----------|-------------------:|-------------------:|-------------:|
| 小型 MoE | 110.6K 个元素 | 15.6K 个元素 | 14% |
| 大型 MoE | 860.2K 个元素 | 34.6K 个元素 | 4% |

> 上表来自 DeepSeek-V2 技术报告 Table 9。元素数量与实际占用的字节数还会受精度影响，但比例关系不变。

表中的"元素"数指的是每 token 的 KV 缓存中需要存储的标量个数：MHA 要为每一层存完整的 Key 和 Value 向量，MLA 只存压缩后的低维潜向量，因此元素个数大幅减少。元素个数乘上存储精度才是实际占用的字节数。

这也解释了为什么不要把不同模型的一串"KB/token"直接当成 MLA 的唯一成绩单：模型层数、KV 头数、头维度和缓存精度都会改变绝对值。比如 DeepSeek-V3 的公开配置是 61 层、512 维 KV latent、64 维 RoPE key；按 BF16 存储计算，KV cache 约为 **70KB/token**。这个数字适合估算 V3，却不是所有模型共用的常数。

## 压缩这么多，为什么不等于"把记忆忘掉"？

我第一次听到"压缩 32 倍还能保住注意力关系"的时候，反应很简单——扯淡。

后来翻到 JL 引理（Johnson-Lindenstrauss），才勉强服气。它的大意是：把一堆高维点随机投影到一个低维空间，点之间的距离关系大概率能保住。单个坐标当然会丢，但相对关系不太丢。

注意力关心的恰好是向量之间的点积和相对相似度，而不是必须逐坐标还原完整向量。保存"关系"所需的空间，可能远小于保存"原样副本"所需的空间。

更妙的是，MLA 不是直接用随机投影。它的下投影和上投影是训练出来的——模型自己学会了哪些关系重要、哪些可以扔。这不等于无损，但它比我想象的"随机扔掉 97% 的信息"聪明得多。

> 把它想象成：考试前老师让你把整本教材压缩成 3 页提纲。3 页当然不等于原书，但如果这 3 页是围绕考试题反复练出来的——它可能比逐页翻书更好用。

（说句实话：JL 引理给的是存在性证明——"存在一个投影能保距离"。它没告诉你这个投影长什么样，也没说从数据里学出来的投影一定满足它的误差界。MLA 的实际效果是靠实验验证的，不是靠 JL 引理推导出来的。我觉得论文作者引 JL 更多是给读者一个"这事不违反数学直觉"的底气，而不是严格的理论保证。）

![](05-jl-lemma.png)

*JL 引理直观图解：高维点随机投影到低维，单个坐标丢失，但点间距离关系近似保留*

## 回到显存这笔账

MLA 省的不是模型参数，而是推理时每一层都在累积的历史记录。

它用低秩摘要减少要存的内容，用矩阵吸收避免把摘要重新展开，再用解耦 RoPE 单独保留位置信息。DeepSeek-V2 的同架构实验给出的结果，是 KV cache 节省 **86%–96%**。

所以，下一次看到"支持 128K 上下文"的模型，别只看参数量。再多问一句：**它每个 token 要留下多少 KV cache？它用的是 MHA、GQA，还是 MLA？** 这往往比"多少 B"更能决定长对话到底跑不跑得动。

MLA 解决的是"存得下"；但上下文极长时，模型仍要面对全部历史记录。怎样从海量记录里更快找到真正相关的部分，是另一道题。

说个题外话——有一次我翻推理框架的文档，发现 KV cache 本身还可以继续量化压缩，而且已经是标准操作了：

- **INT8** 几乎零精度损失，被 OpenVINO 设为默认；
- **INT4** 在 LMDeploy、vLLM 等框架普遍可用，2026 年的新技术（如块对角 Hadamard 旋转）把精度损失压到了 1–3 分；
- 更激进的做法是 **Key 4-bit + Value 2-bit 的混合精度**（如 TurboQuant），平均 3-bit 就能近无损运行。

我是看到这个才意识到：MLA 的低秩压缩和 KV cache 量化不是竞争关系，是叠加关系。MLA 先把每 token 的缓存从 110K 元素压到 15K，**量化再在 15K 的基础上把存储位宽砍到 1/4 甚至 1/8**。这套"蒸馏 + 量化"的双重压缩，让 DeepSeek-V3 的 KV cache 在 70KB/token 的基础上还能再降几倍。

## 注意力三连击，先停在这里

注意力这条线，我们连写了三篇——从[基本机制](https://mp.weixin.qq.com/s/KrilwX6VRjI9KfjvD7C6kw)到 [Kimi 的长上下文方案](https://mp.weixin.qq.com/s/_RR5LLWgjGNm-qXdSdnAGA)，再到今天 DeepSeek 的显存压缩。三篇合在一起，应该能帮你建立起一个直觉：**长上下文的瓶颈不是一道题，是一组题——计算怎么省、记忆怎么存、相关信息怎么快速找。**

下一篇回到大模型原理的主线。我们讲 FFN——Transformer 里真正存放"知识"的模块。注意力和 FFN，一个是"找信息"的系统，一个是"存知识"的系统。它们是 Transformer 的两半大脑，下一篇把那半拉补齐。 

还有一句话想先放在这里——MLA 远不是终点。注意力机制的演进路线比很多人想象的要丰富：**MLA（低秩压缩）→ NSA（原生稀疏注意力）→ DSA（DeepSeek Sparse Attention）**，每一步都在解决上一步遗留的问题。MLA 让记忆体积变小，NSA 让模型只看重要的位置，DSA 进一步硬性选出最相关的 top-k token。而 DeepSeek-V4，又在这条线上走出了完全不同的路。

有时候回头看这条路线，会有一种奇妙的感受：最开始大家只是想把便利贴写短一点，写着写着，发现整面墙都不需要了——只需要翻到正确的那一页。

这大概就是做系统的人最上瘾的时刻：你不是在优化一个数字，你是在改写一个问题的定义。

后面的文章会逐一拆解这段演进，这里先留一个楔子。
