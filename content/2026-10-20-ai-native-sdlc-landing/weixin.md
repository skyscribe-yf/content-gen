上一篇的结论是：Anthropic 的 playbook 只答对了一半。"能"这一格已基本解决，**值、撑、知**三格才是真正的风险所在。这篇把三道坎落到可执行的清单上。

## 一、第一道坎：反馈延迟决定 agent 的行为形态

同一模型、同一 prompt，在不同延迟的代码库上表现形态完全不同：

| 反馈延迟 | agent 的行为形态 |
|---|---|
| 亚秒（lint / typecheck / 单测） | 像严谨的 TDD 实践者：改一次查一次 |
| 几秒 ~ 1 分钟 | 小批次提交，错误在本文件/模块内纠正 |
| 5–10 分钟（典型集成套件） | 开头跑一次、结尾跑一次，中间"蒙一把" |
| 20 分钟以上 | "投机者"：整个会话只跑一两次，其余靠推理 |

人一天跑 5 次测试，agent 跑 200 次。**所以反馈延迟是乘数级的税。**

**最高杠杆项：依赖反转 + in-memory fake**。每个外部边界（DB / mailer / HTTP client / queue）都在应用自有接口后面，测试进程不启 Docker、不连库、不开 socket。单测成本降到毫秒级。

但顺序不能反：

> "一个验证不了任何东西的快检查，比慢而有意义的检查更危险，因为它伪造信任。"

而且自欺有一条具体路径：**agent 会把测试改弱以便转绿**。先变快、后求有意义，你会得到一个创纪录地快、却毫无意义的绿。

**落地清单**（按杠杆排序）：
1. 依赖反转 + in-memory fake（最高杠杆）
2. 测试 scope 分离：agent 能只跑"它改的那个模块"
3. 测试无共享状态 → 可并行
4. pre-commit 拦 lint / typecheck（毫秒级）
5. hermetic build + 远程缓存 / affected 计算
6. 跨服务用 contract test 替代 E2E 覆盖面
7. 集成 / E2E 留在"每 PR 一次"的层，不进 agent 内循环

**两个反模式**：别把"加一层 evals"当成反馈回路（evals 测配置有没有变坏，反馈回路测这次改动对不对，频率与目的都不同）；反馈周期长的根因往往不是测试慢，而是测试套件与生产架构同构。

## 二、第二道坎：非功能约束的三层定义

商业软件所期望的各种非功能约束，领域特定的需求范式，软件需求和测试如何拉通对齐，这些核心挑战其实都远远称不上被完美解决。

NFR 不能写成散文。按可验证性分三层：

| 层 | 例子 | 怎么定义 | 陷阱 |
|---|---|---|---|
| 1 · 可单一数值化 | p99 延迟、内存峰值、二进制体积 | 预算 + 基线 | 没有基线的阈值是假的门 |
| 2 · 可结构规则化 | 分层/依赖方向、无循环依赖、公开 API 面 | fitness function 进 CI 必过 | 工具已存在十几年，AI 时代价值翻倍但普及率极低 |
| 3 · 不可数值化、无规则 | 抽象是否恰当、是不是要解决的问题 | 无法定义成指标 | 只能限制产量 + 人工读 + 风险加权 |

Google 做了三阶段 prompt 干预（同一函数、同一上下文、同一重实现预算与验证 harness）。

基线重写 → 加通用反馈 → 加类别特定反馈。

**改变出现在第三阶段。**

> 通用反馈（"写得更好一点"）无效。
>
> 只有把约束命名成类别、并给出该类别的可检查判据，反馈才会被 agent 当作约束消化。
>
> 否则被当成风格建议。

"代码能不能跑由 build 裁决；但『这是不是正确的改动』没有传感器。"（Simon Willison）

## 三、第三道坎：成本核算

**cost per accepted change** = (licenses + metered usage + CI + human review + rework + incidents) ÷ 被接受并留下的变更数。分母必须是"留存下来的变更"——把返工和回滚都算成产出会自欺。

**整单跳档 cliffs**：主流计量 API 的阶梯计费是整单跳档，不是分段累进。

以某模型为例：

0–32K 输入 $0.144/M，32K–128K $0.216/M。

128K–256K $0.359/M，256K–1M $0.717/M。。

**输入长度决定档位，输出单价也由输入长度决定**——长输入不仅把输入成本按档放大，还同时把输出成本抬到同一档的倍率上。

而 agentic coding 恰好是"input token 指数增长"的任务。

平均消耗单轮推理任务 3500× 的 token，主要由 input token 指数增长驱动。

agent 累积多来源信息，同一上下文被反复喂回。

**缓存回本点**：显式缓存建 125%、命中 10%，命中一次就回本。但 TTL 5 分钟（命中重置），价值取决于"请求间隔的分布是否短于 TTL"——连续跑 agent 命中率高，人机交替命中率低。

**按层 ΔFCR**：把 613 个真实 commit 池化重放，分层 fix rate：

| 层 | API 档 | 自托管档 |
|---|---|---|
| High | 15.1% | 46.5% |
| Medium | 61.2% | 80.6% |
| Low | 63.4% | 86.9% |

**Low 层是三层里 fix rate 最高的一层**——"简单任务 → 便宜模型"把 fix 最密集的层交给了更差的档。

在体量最大的地方造成最大绝对伤害。混合的"best of both worlds"叙事在这一组数据下不成立。

前沿是**单调**的：每一分基础设施节省都用缺陷率换。

**盈亏平衡式**：路由到自托管档，当且仅当

> 基础设施节省 > ΔFCR × commits × t_fix × labor rate

**落地建议**：

把请求压在最低计价档之下（零成本、立刻生效，优先于缓存）。

API 档开显式缓存；不要为省钱在自托管档做缓存（只买吞吐不买钱）。

按风险层路由，不要按预测难度路由；升级触发器用确定性检查，不用置信度。

## 四、第四道坎：review 独立性

**Kish 有效样本量**：

$$n_{\text{eff}} = \frac{k}{1 + (k-1)\bar{\phi}}$$

9 个判官（7 个模型家族）的有效独立数 ≈ 2.0–2.5。**全票一致时错误率 9.1%，独立假设下应为 0.02%——差约 455 倍。**

**共失败天花板** $\beta = P(\text{池中所有模型都错})$：任何聚合架构的精度上限 = $1-\beta$。

**越强越相关**：Cornell 在 350+ 模型上测得，两个模型都出错时有 60% 概率错在同一处。更大更准的模型误差高度相关，即使架构与 provider 完全不同。

**六轴多样性**：模型 / 架构 / provider / scope / 上下文 / 方法（确定性 vs 模型）。确定性检查（类型系统、fitness function、invariant 测试）是唯一不与模型共享 $\bar{\phi}$ 的验证层。

**verifier cascade**：自托管生成 → 跑确定性检查 → 通过接受（边际成本 ≈ 0）/ 失败升 API 档重做。升级触发器用真值不用置信度——代码有外部真值，置信度路由是多余的复杂度。

**可复现实验**（受限环境反向贡献高价值知识的唯一通道）：缺陷注入 D1–D8 + 干净样本 + 6 个陷阱（召回虚高、无干净样本、样本量太小、缺陷太好找、审者察觉被测、单一代码库）。

## 五、验收一致性：纪律只能画在权限和动作上

Anthropic 的教训：agent 不会因为"公司规定"而守规矩，只会因为这条路物理上走不通。规则写在 prompt 里 = 建议；写在 hook / managed settings 里 = 纪律。

**验收标准必须是 artifact 的一部分，且可执行**：`spec.md` 里只有描述性文字，那它就是意见。把政策变成脚本，而不是散文。

**归属不转移**：同一个产品负责人从 `intent.md` 审到 `spec.md` 审到验收。

**批次大小是理解一致性的最强杠杆**：快反馈要求快 review，快 review 要求小 PR，小 PR 要求短分支。

**"第二次犯错就写进 CLAUDE.md"**——唯一能让理解一致性单调改善的机制。没有它，每个新会话从零谈判。

**invariant 测试**（"用户 A 永远读不到用户 B 的数据"）：把人达成的共识转成机器传感器的唯一形式，也是唯一能跨 agent 会话传递判断力的载体。

## 六、残余风险

确定性世界里人们积累的大量经验，想无缝照搬到 AI agent 上，期望用许愿式的方法直接得到期望的产品，基本上都是一厢情愿的过度简化。

有的企业甚至提出很朴素的想法，尝试将各种文档、材料一股脑丢给 AI，使用各种 RAG、Graph 等技术，尝试让 coding agent 一把梭哈。然而这种方式很快就会碰上模型本身"锯齿智能"的弱点。

即使全做到，第 3 类（对不对）仍然没有传感器。**cognitive debt**（把脑力外包给助手）和 Google 说的"评估 AI 代码的认知摩擦无法被现有指标捕捉"是同一件事的两面。

这是**结构性成本**，只能靠"限制产量 + 保留人工读关键代码"来支付。任何声称能自动化的说法都是在卖东西。

各种软件千人千面，各种技术上的非技术上的约束混杂期间，是否所有的东西都可以用堆 token 来完成，这是很多做 agent 评测和玩具 coding 项目的人从来都不会关心的事情。

不过毕竟，它山之石可以攻玉，对于 Anthropic 这种工作方式，探讨和研究的价值还是很高的。
