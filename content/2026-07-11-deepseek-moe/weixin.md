## 🎯 驱动问题：30 倍到底从哪来？

上一篇我们拆了[AI 上下文为什么越长越慢](https://mp.weixin.qq.com/s/PLVRS0TTHXHDve1Z3r6M7Q)：对话越长，KV Cache 越占显存。这一篇接着往模型内部看，除了少存上下文，能不能也让每个 token 少做一部分计算？

让代码助手修一个报错时，第一轮通常很“重”：系统提示词、仓库目录、团队规则、相关文件，都要带进去。第二轮你往往只补一句：“这个测试还是失败，再查一下。”

这时有两个问题同时出现：重复的仓库上下文能不能不再重复收费？模型内部遇到每个 token 时，能不能也不必让所有参数同时计算？

前一个问题由缓存回答，后一个问题正是混合专家（Mixture of Experts，MoE）要解决的事。

“DeepSeek 便宜 30 倍”不是脱离场景的通用结论。它成立，前提是要把**输入、缓存命中和输出**分开算；更重要的是，调用场景确实存在大量重复上下文。

### 笔者真实写代码的 token 结构

下面不用“假设 1M 输入加 100K 输出”的演示口径，直接采用笔者写代码时记录到的调用结构：**每 1M 总 token 中，99.5% 是输入，0.5% 是输出；输入 token 里，95% 命中缓存，5% 是新写的需求、代码和问题。**

这不是所有开发者的 API 基准，而是一组个人真实使用数据。它对应的是反复携带仓库文件、系统提示词和团队规则的代码助手场景。

每 1M 总 token 的成本公式是：

> **成本 = 0.995 ×（0.95 × 缓存命中输入价 + 0.05 × 普通输入价）+ 0.005 × 输出价**

以 DeepSeek-V4 Pro 为例：

> **0.995 ×（0.95 × ¥0.025 + 0.05 × ¥3）+ 0.005 × ¥6 = ¥0.202881**

| 模型 | 每 1M 总 token 成本 | 相对 DeepSeek-V4 Pro |
|---|---:|---:|
| DeepSeek-V4 Pro | **¥0.203（US$0.0298）** | 1 倍 |
| GLM-5.2 | ¥2.429（US$0.357） | 12.0 倍 |
| GPT-5.6 Sol | ¥5.924（US$0.871） | 29.2 倍 |
| Claude Fable 5 | ¥11.509（US$1.693） | 56.7 倍 |

这个真实结构下，DeepSeek-V4 Pro 对 GPT-5.6 Sol 是 **29.2 倍**，按传播口径可以说“约 30 倍”；对本文比较中单价最高的 Claude Fable 5 是 **56.7 倍**。表格保留精确值，标题和正文使用“约 30 倍”这一轮整表达。首次建立缓存的写入成本、不同项目的缓存命中率和输出比例，都可能改变结果。

价格账只是结果。接下来才问原因：一个总参数量很大的模型，为什么不必每次都为所有参数付计算费？

## 💡 直觉解释：把全科会诊改成分诊

传统的稠密模型（dense model）像一次全科会诊：一个 token 进入前馈网络（FFN）后，相关的计算单元都会参与。

混合专家（Mixture of Experts，MoE）像分诊台。模型先看当前 token 的状态，再决定请哪些专家处理。写代码时，可能更需要语法、程序结构和逻辑关系；翻译时，可能更依赖语言对齐与语义消歧。不是每一份知识都要同时计算。

![](01-hospital-triage.png)

这里有一个容易混淆的点：专家不是人工贴好的“代码专家”“翻译专家”标签。训练会让它们在数据中形成不同的分工，路由器（router）则学会在不同 token 上调用不同组合。

DeepSeek-V3 是一个直观案例：它有 256 个路由专家（routed experts），每个 token 只选择其中 8 个，另有 1 个所有 token 都会经过的共享专家（shared expert）。

这意味着什么？

- 总容量可以很大，模型有更多位置存储不同模式。
- 单次计算不必把所有专家都跑一遍。
- 但模型仍要付出路由、跨设备通信和注意力计算的成本。

因此，MoE 不是“免费变大”，而是把“所有人一起干活”改成“只找最相关的人干活”。

---

## 📐 数学原理：路由器怎样选人？

设当前 token 的表示为 **x**，共有 **N** 个专家。路由器先为每个专家打分：

> **sᵢ(x) = router(x)ᵢ**

然后取分数最高的 **k** 个专家，这一步叫 Top-k 路由（Top-k routing）。最后把选中专家的输出按权重合并：

> **y = Σᵢ∈Top-k wᵢ(x) · Expertᵢ(x)**

其中 **wᵢ(x)** 是归一化后的路由权重。

![](02-gating-router.png)

这三步可以记成：**打分 → 选人 → 合并答案**。

如果 256 个专家中只选 8 个，专家前馈分支需要执行的专家计算大致是全量执行的 **8/256 = 1/32**。这是 MoE 最核心的省算力来源。

但要注意边界：这不是整个模型端到端恰好快 32 倍。注意力层、路由器、专家间通信、内存访问都还在；实际吞吐提升取决于硬件和服务系统能否把这些额外开销压下去。

这也是为什么“只激活 8 个专家”可以解释稀疏计算，却不能单独解释 API 最终价格。

## 💡 为什么专家不会全挤到一个窗口？

分诊还有第二个问题：如果所有病人都被送往同一科，那个科室会排队，其他科室闲着。MoE 里这叫负载不均衡（load imbalance）。

早期做法常在训练目标中加入辅助损失（auxiliary loss），鼓励 token 在专家间更均匀地分配。但惩罚项太强，可能干扰模型原本该学的任务；太弱，又压不住拥挤。

DeepSeek-V3 采用的是无辅助损失的负载均衡（auxiliary-loss-free load balancing）。直观地说，系统为较忙或较闲的专家调整选择时的偏置（bias）：

- 某专家近期太忙，就让它在下一轮 Top-k 选择时不那么容易入选。
- 某专家近期太闲，就提高它进入候选名单的机会。
- 专家被选中后，合并输出仍使用原始路由分数，而不是用偏置改写内容权重。

![](03-bias-trick.png)

可以把辅助损失想成“对每位病人收拥堵税”，而偏置调节更像“分诊台根据排队长度调整导流”。前者直接改训练目标，后者主要改谁能进入候选队列。

它解决的不是“模型会不会回答”，而是“模型能否稳定地把大量 token 分散到不同 GPU 上运行”。

## 🔧 MoE 省下来的，到底是哪一段？

Transformer 里，注意力层负责让 token 看上下文；前馈网络（feed-forward network，FFN）负责对每个 token 做更深的非线性变换。MoE 通常把后者替换成专家集合。

![](04-moe-dataflow.png)

所以更准确的说法不是“90% 参数没有用”，而是：**在当前 token 的这一次前向计算中，大多数路由专家没有被调用。** 它们仍然是模型容量的一部分，只是在别的 token、别的任务上可能被选中。

这也解释了 MoE 的两个同时成立的特性：

1. 总参数可以继续增加，容纳更多模式。
2. 每个 token 的专家计算不会随总专家数同比例增长。

代价则转移到另一个工程问题：token 要被分发到正确的专家，专家输出还要收回来。专家越分散，通信越可能成为瓶颈。

## 🔄 回到价格：MoE 是第一把钥匙，不是全部答案

现在可以把开头的 30 倍拆开了。

**第一层，缓存复用。** 95% 缓存命中让重复的仓库上下文变得很便宜。这是提示缓存（prompt caching）的作用，不是 MoE 专属能力；换一家模型服务，只要有缓存，也会受益。

**第二层，稀疏计算。** MoE 让专家前馈分支只运行必要专家，是 DeepSeek 能在大容量与低单 token 计算之间折中的关键设计。

**第三层，系统工程。** 真正把稀疏计算变成低账单，还要依赖数值精度、通信、并行策略、批处理和服务调度。任何一环效率不足，理论上的省算力都会被等网络、等显存、等队列吃掉。

所以，更完整的公式应当是：

> **低成本 API = 缓存复用 + 稀疏计算 + 低精度计算 + 高效通信与服务**

MoE 负责“谁干活”，但它不负责全部故事。

## 📌 一句话总结

按笔者真实写代码的 token 结构，DeepSeek-V4 Pro 每 1M 总 token 约为 ¥0.203，约是 GPT-5.6 Sol 的 1/30、是本文比较中单价最高的 Fable 5 的 1/56.7。这个差距不能简单归因于 MoE：缓存压低了重复输入成本，MoE 压低了专家前馈计算，而精度、通信和服务工程决定这些优势能否落到 API 价格上。
