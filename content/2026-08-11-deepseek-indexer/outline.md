# 几万块挑几百块：Lightning Indexer 凭什么敢这么挑

## 文章定位

- 本篇是 DeepSeek 技术解密系列的新一篇，主线是 **V4 CSA 里的 Lightning Indexer——一个 FP4 精度的小打分网络，负责从几万个压缩块里替核心注意力挑出 top-k 个**（DeepSeek-V4 Technical Report §2.3.1 + Obsidian 第 3.3 课 + HF transformers 开源实现 `modeling_deepseek_v4.py`）。
- 兑现 KV 落盘篇（08-10）文末预告：「档案按块落盘了，但翻档案本身要快——V4 训练了一个小模型（Lightning Indexer），专门负责从几万个块里挑出该看哪几个。注意力怎么学会只看重点？」——标题与预告同频。
- 承接 KV 落盘篇（08-10）档案线：上篇讲**档案怎么落盘**（压缩 KV 存 SSD、按 lcm 对齐分块），本篇讲**档案怎么被翻出来**（Indexer 从几万块里挑出该看哪几块）。同属「KV 缓存与长上下文」工程线。
- 主线冲突：**先筛后算的死结**——注意力想跳过不重要的块，但只有看完才知道哪些不重要。选择依赖计算，计算依赖选择。全注意力靠「全都算」绕开死结，代价是 O(L²)。
- 暗线：**小模型凭什么敢替大模型做决定**——小（FP4、64 head×128 dim、参数占比 <1%）到可以每个 token 都跑；错（选漏几块只是多算一点）到可以接受。筛选是弱判断，计算是强成本，「粗糙但便宜」配「精确但昂贵」。
- **与 CSA 篇（08-04）的边界（防炒冷饭）**：CSA 篇已给过打分公式 `I = Σ w·ReLU(q·K)` 与 top-k 概念。本篇不重推公式，公式只做「回味」回链；增量在三个「为什么」：①为什么 ReLU 淘汰制（FP4 精度下 exp 直接爆炸，软硬件协同约束）；②k=512 vs 32K 块的稀疏比账（选错块的代价上限在哪）；③Indexer 是怎么被训练出来的（CSA 篇完全没讲，本篇主场）。
- 数学深度：B 级。主公式一个（打分 + top-k），出现但不推导，逐项讲物理意义；配一个 128K 上下文的具体数字例子走完全程（128K token → m=4 压缩 → 32K 块「几万块」→ top-k=512「几百块」→ 64× 稀疏）。
- 实验：`experiment.py`——小型真实 Transformer 复现「全注意力 vs Indexer+稀疏注意力」，双指标：①召回率（Indexer 挑出的 top-k 块覆盖了真实注意力权重的多少，呼应论文 99.7% 验收口径）；②FLOPs 节省（稀疏 vs 全量）。标注「机制演示，不是官方性能基准」。
- 下一篇预告：MTP（08-12，一次猜两个词，训练快 1.8 倍）——用「时间账」线过渡：Indexer 省的是推理时翻档案的时间，MTP 省的是训练时猜词的时间。
- **归属校准（系列惯例）**：Lightning Indexer 首次出现在 V3.2 的 DSA（arXiv 2512.02556），不是 V4 原创；V4 的增量是 ①打分对象从原始 token 变成压缩块（CSA 内层）；②FP8→FP4；③与 CSA 联合的两阶段训练。NSA（2502.11089）的「压缩副产品打分」是更早的粗筛雏形。正文第 8 节「同题不同解」交代进化链，不把 Indexer 写成 V4 独家发明。
- **开源可核验声明**：V4 已开源（MIT，2026-04-26 发布，HF transformers 2026-05-02 支持），本篇全部参数来自真实 config.json 与开源实现，正文开头点一句增强可信度。

## 核心结论

1. **死结**：注意力想省计算就得先知道哪些 KV 重要，但「知道哪些重要」本身要看完所有 KV——选择依赖计算，计算依赖选择。全注意力用「全都算」回避这个死结，代价 O(L²)。
2. **压缩块把问题缩小，但没解决**：CSA 把 128K token 压成 32K 块（m=4），核心注意力从「对 128K 个 token 全算」变成「对 32K 个块全算」——省了 m 倍，但仍是「对全部块全算」，1M context 下每个 query 还是要面对 25 万个块，不够。
3. **Indexer 的答案**：先筛后算——一个 FP4 精度、64 head × 128 dim 的小打分网络，对每个 query 给全部压缩块打分（ReLU 淘汰 + 多头加权），只留 top-512 给核心注意力。选择成本 O(L/m)（打分本身），计算成本 O(k)（只算选中的块）。
4. **为什么敢（三支柱）**：①ReLU 淘汰制是 FP4 下的唯一活路（exp 在 4-bit 动态范围下溢出，除法精度崩；max(0,x) 只有比较，零精度损失）；②多头加权让打分更聪明（w 可正可负，不同 head 看不同维度，query-dependent）；③选错代价有上限——漏块只是「没看到」，不是「看错」，核心注意力仍会加权兜底，召回率 99.7% 就是验收线。
5. **怎么学会的（两阶段 warmup）**：前 1T tokens 用密集注意力正常训练（Indexer 还不存在/不生效）→ 64K 序列长度时引入稀疏 → 设一个短阶段专门 warmup Indexer（老师信号 = 密集注意力的注意力权重，让学生模仿「真正重要的块」，此为合理推断，论文只写了存在 warmup 阶段）→ 之后全程稀疏训练。top-k 的 argmax 不可微，用打分网络的连续输出 + 召回率目标绕开。
6. **训练后的工程打磨**：FP4 QAT 量化 Indexer 的 QK 路径（index scores 从 FP32 压到 BF16），top-k 选择器提速 2×，KV 条目召回率保持 99.7%（论文 §5.2.1）——「小」不是偷工减料，是精度预算的刻意分配。
7. **进化链归属**：NSA 粗筛（压缩副产品打分，门卫兼面试官）→ V3.2 DSA Indexer（独立打分网络，ReLU+FP8，逐 token）→ V4 CSA Indexer（打分对象换成压缩块，FP8→FP4）。Indexer 是 V3.2 的设计，V4 把它嫁接到压缩块上并做低精度化。

## 正文结构

### 0. 开头：同事的追问（约 250 字）

场景（承接上篇档案室）：同事第二次问同一份长文档，秒回。但这次他追问了一句：「它怎么知道该翻哪几卷档案？」——上篇回答了「档案怎么存进硬盘」，本篇回答「档案怎么被翻出来」。悬念：V4 训练了一个小模型专门干翻档案这件事，它凭什么敢替 600B 级的大模型做决定？（顺带点一句：V4 已开源，下面所有参数都能在 config.json 里查到。）

### 1. 回应弧线：KV 落盘篇的预告，今天兑现（约 300 字）

- 引 KV 落盘篇结尾预告原文：「档案按块落盘了，但翻档案本身要快——V4 训练了一个小模型（Lightning Indexer），专门负责从几万个块里挑出该看哪几个。注意力怎么学会只看重点？」
- 承接上篇：压缩 KV 按 lcm(m,m') 对齐落盘后，检索时面对的是几万个块——全算回去又变成 O(L²) 的噩梦，落盘省下的 prefill 会在「翻档案」时还回去。
- 归属校准：Indexer 不是 V4 原创（V3.2 DSA 首发），V4 的增量 = 打分对象换成压缩块 + FP8→FP4 + 两阶段联合训练。本篇主角是「怎么挑」，压缩块只是舞台。
- 本篇回答三个问题：①为什么非筛不可？②凭什么敢筛？③怎么教会它筛？

### 2. 死结：选择依赖计算，计算依赖选择（约 400 字）

- 复述上篇 prefill 账一句话回链：注意力每来一个 query 要跟全部历史 KV 做点积。
- 核心悖论展开：想跳过不重要的块，前提是知道哪些块不重要；想知道哪些块不重要，得先读一遍所有块——读一遍所有块的代价，跟全量注意力是同级的。
- 直觉类比：图书馆查资料，目录卡只有「读了正文才知道哪本有用」——你要么全读（O(L²)），要么赌（可能漏）。
- 为什么全注意力能工作：它把「读全部」的代价内化为 O(L²) 计算——正确性满分，成本爆炸。长上下文场景（1M）下这个成本不可承受。
- 两阶段加速的思想预告：先便宜地粗筛（小模型），再贵地精算（大模型）——粗筛的质量只要不把关键块漏掉，总账就赢。

### 3. 压缩块：把问题从 128K 缩小到 32K（约 350 字）

- 回链上篇：CSA 每 m=4 个 token 压成一个块，KV 落盘篇已讲压缩机制，此处只一句回链不重推。
- 数字例子开始铺设：128K token → 32K 块（「几万块」）。核心注意力从「对 128K 个 token 全算」变成「对 32K 个块全算」——省了 m 倍，但**仍然是全算**：1M context 下要面对 25 万个块。
- 关键转折：压缩解决了「存得下」，没解决「算得完」——对每个 query 遍历全部块，还是 O(L/m) 量级的点积，1M 下 25 万次。稀疏是下一步必须。
- 预告：Indexer 的工作就是在这 32K（或 25 万）个块里，给每个 query 挑出 512 个。

### 4. 主角登场：一个 FP4 的小网络（约 400 字）

- 真实参数（开源 config.json 可查）：`index_n_heads=64`、`index_head_dim=128`、`index_topk=512`（V4-Flash）/1024（V4-Pro）、CSA `compress_rate=4`。
- 小到什么程度：FP4 精度（比 FP8 还狠，MoE 专家权重同款待遇）、64 head × 128 dim 的打分空间、相对主模型参数占比 <1%。
- 它做什么：对每个 query，给所有压缩块算一个「相关分」→ 挑分数最高的 top-512 → 核心注意力只对这 512 块做真正的 attention。
- 一句话定位：**主模型负责精读，Indexer 负责速览**——速览便宜到每个 token 都能跑，精读贵到只留给选中的块。
- 类比（局部）：图书馆的检索卡片——卡片本身没内容，但它告诉你哪本书值得翻。vault 笔记的「面试官团队」类比可做花絮。

### 5. 为什么敢：三个支柱（约 550 字）

- **支柱① ReLU 淘汰制（为什么不是 Softmax）**：
  - 公式回味（回链 CSA 篇）：$I_{t,s} = \sum_h w_{t,h} \cdot \mathrm{ReLU}(q_{t,h}^\top K_s^{IComp})$
  - 不重推公式，讲为什么：Softmax 需要全序列归一化（每个分数依赖所有分数），ReLU 每个分数独立计算、可以边算边筛；更致命的是精度——Indexer 跑在 FP4 上，exp(x) 在 4-bit 动态范围下直接溢出，除法精度崩坏，而 `max(0, x)` 只有比较运算、零精度损失。**不是设计偏好，是软硬件协同的必然**。
  - 高维空间的副产品：随机向量点积接近 0，ReLU 天然截掉一半负分——粗筛免费送。
- **支柱② 多头加权**：64 个 head 学不同的「重要性标准」（语义相关、位置模式、特殊 token），每个 head 的权重 $w_{t,h}$ 由 query 动态生成、可正可负——「某个 head 的高分反而是负面信号」也能表达。比单路打分（NSA 的副产品 score）更精确。
- **支柱③ 选错代价有上限**：这是「敢」的底气。Indexer 选错了 = 漏掉一个关键块 = 核心注意力没看到它——**漏看 ≠ 看错**，只是信息少了一点；而全量计算是刚性成本。k=512 vs 32K 块 = 64× 稀疏，只要召回率守住 99.7%（论文 QAT 段披露），质量损失可忽略。赌注结构：输的代价小（漏块），赢的收益大（省 64× 计算）。

### 6. 怎么做到的：15 行伪代码 + 数字走一遍（约 500 字）

- 伪代码（~15 行，简化但链路完整）：

```python
# 压缩块已就绪：C[0..T-1]（T = L/m 个块，如 32K 个）
def lightning_indexer(query, C, W_q, W_w, k=512):
    scores = []
    for head in range(64):                      # 64 个 indexer head
        q_h = query @ W_q[head]                 # query 的低秩投影（每 head 一份）
        s_h = relu(q_h @ C.T)                   # 与全部压缩块点积 → ReLU 淘汰
        scores.append(s_h)
    w = query @ W_w                             # query 动态生成 head 权重（可正可负）
    score = sum(w[h] * scores[h] for h in range(64))   # 多头加权求和
    return topk(score, k)                       # 只留分数最高的 k 个块
```

- 数字走一遍（128K 场景）：query 向量 → 64 个 head 各对 32K 块算点积（FP4）→ ReLU 截掉负分 → 加权求和 → top-512。核心注意力只算 512 块，全算则要算 32K 块——**64 倍稀疏**（32K/512）。打分本身的成本：64 head × 32K 块 ≈ 200 万次 FP4 点积，廉价到可以每个 token 都跑；相比之下全量核心注意力是 32K 次全精度点积/query，且随上下文继续增长。
- 数据流一句话：Indexer 自己的压缩器（同 CSA 压缩操作，head_dim=128）产「检索键」；query 的低秩 latent 与主注意力共享（$c_t^Q = h_t W^{DQ}$，一句话回链，不展开）。
- 提示：真实实现里还有个因果细节——query 只能看「已闭块」（窗口还没凑满的块不可见），vLLM/HF 实现里用 -1 哨兵处理。正文一句带过，体现「做到位」而非「说概念」。

### 7. 怎么学会的：两阶段 warmup（约 600 字，本篇主场）

- 问题：Indexer 是随机初始化的，直接稀疏训练 = 随机丢块 = 训练崩。必须先教会它「哪些块重要」。
- **阶段一（1T tokens）**：模型用密集注意力正常预训练（论文 §4.2.2 原文：先 dense attention warmup 前 1T tokens）。此时没有稀疏、没有 Indexer 的负担——主模型先把语言能力学好。
- **阶段二（64K 序列长度起）**：引入稀疏注意力，但在此之前设一个**短阶段专门 warmup Lightning Indexer**（论文原文 "a short stage to warm up the lightning indexer in CSA"）。
- 老师信号（合理推断，正文明确标注）：warmup 阶段主模型仍按密集方式跑（或保留密集分支），把**密集注意力的真实注意力权重**当作老师——学生（Indexer）的任务是预测「密集注意力会把权重放在哪些块上」。学的是「真正重要的块长什么样」，不是自己瞎猜。论文未披露监督细节，此为与两阶段训练事实一致的合理解释。
- top-k 不可微怎么绕：`argmax`/`topk` 的索引选择不可导，梯度没法穿过「选了哪几个块」。绕法：训练时用打分网络的**连续输出**（每块的分数）接排序/召回类损失（如被选中块的密集注意力权重和），推理时才离散化成 top-k。梯度走分数，不走索引。
- 验收标准：召回率——Indexer 挑出的块覆盖了「密集注意力真正看重」的 KV 的比例。训练后 QAT 阶段披露 99.7% 召回率（FP32→BF16 压分之后仍守住）。
- 为什么两阶段而不是端到端：稀疏结构一旦固定就很难改（块选错的信息再也进不来），必须先让「选择器」成熟再让「精算器」依赖它——先学全量、再学偷懒，偷懒才不至于变成瞎。

### 8. 他山之石：GLM 和 Kimi 的两条路（约 600 字）

- 声明（不是唯一解）：Indexer 不是唯一的「先筛后算」方案，中国开源前沿模型至少有三条路线并存。
- **路线一：DeepSeek 系（本篇主角）**——独立打分网络，ReLU + 低精度，从 token 到压缩块。
- **路线二：GLM-5 系——同一套 DSA，但把 Indexer 共享化**：
  - GLM-5（z.ai，744B，2026-02 开源）直接采用 DeepSeek 的 DSA + Lightning Indexer（config：index_topk=2048、index_n_heads=32、index_head_dim=128），这是「Indexer 不是 V4 独家」最直接的证据。
  - GLM-5.2（2026-06）更进一步提出 **IndexShare**：清华 IndexCache 论文（arXiv 2603.12201）实测相邻 DSA 层的 top-k 选择有 **70%-100% 重叠**——相邻层对「哪些 token 重要」的判断几乎一致。于是每 4 层共享一个 indexer（full, shared, shared, shared），1M 上下文下 per-token FLOPs 降 2.9×。
  - 洞察：**粗筛自己也会变成瓶颈**。IndexCache 实测 200K 上下文时 indexer 点积消耗 **81% 的 prefill 时间**——「先筛后算」的「筛」也是 O(L²) 量级，只是常数更小。GLM 的答案是把「筛」的次数除以 4；V4 的答案是把「筛」的对象从 token 变成压缩块（除以 m）。两条路线其实在解决同一个新问题：**筛选成本本身**。
- **路线三：Kimi K3——压根不筛**：KDA 线性注意力把历史压成固定大小的递推状态（2.8T 模型、1M 上下文，69/93 层 KDA），选择问题被结构消解——没有 top-k，也没有 indexer。代价是压缩状态丢失精确历史，靠 24 层 Gated MLA 定期做全局检索兜底。
- 三线对照表：
  | 方案 | 选择机制 | 筛选成本 | 精度 |
  |------|---------|---------|------|
  | V4 CSA Indexer | 独立打分网络，ReLU+FP4，选压缩块 | O(L/m)，FP4 廉价 | 打分对象是压缩块 |
  | GLM-5.2 IndexShare | 同款 indexer，4 层共享 1 个 | 打分次数 ÷4，FLOPs 降 2.9× | 相邻层 70-100% 重叠 |
  | Kimi K3 KDA | 无选择，固定状态递推 | 无 top-k，O(1) 状态 | 靠 24 层 MLA 兜底 |
- 小结一句：DeepSeek 发明了「筛」，GLM 把「筛」变便宜，Kimi 把「筛」整个省掉——但三者都在回答同一个问题：1M 上下文下，注意力凭什么敢不全算。

### 9. 回扣与结尾（约 350 字）

- 完整因果链复盘：秒回 = 档案落盘可复用 → 但翻档案要先筛后算 → Indexer 用 FP4 的廉价打分挑出 top-512 → 核心注意力只算选中的块 → 64× 稀疏让 1M 上下文算得动。每一环都在回答「凭什么敢这么挑」。
- 回扣开头：同事的追问有了答案——不是大模型自己翻档案，是一个「残缺数字」训练的小网络替它速览；大模型只精读小网络推荐的 512 卷。
- 升华一句（呼应系列暗线「什么东西该放哪儿」）：这行的聪明人不是把一件事做到极致，而是想清楚「什么事该用多大的力气做」——翻档案用 FP4 的小模型，精读才用得上 600B。
- 下一篇预告（MTP，08-12）：Indexer 省的是推理时翻档案的时间，下一笔时间账在训练侧——一次猜两个词，训练为什么快 1.8 倍？
- 开放式问题：如果「先筛后算」这么好用，你觉得模型里还有哪些「全部算一遍」的地方可以换成先筛后算？评论区聊聊。
