## 交付句

- **转 1（机制）**：相似度不是理解。它只能告诉你「这两句字面像」，拼不出**跨段、整体结构、意图**——而这三样恰好是「懂一个项目」要的。加 reranker 也没用，它只重排候选，召回阶段丢掉的补不回来。
- **转 2（落点，中立但有工具）**：别急着卸掉记忆、也别急着写一屋子文档——先把「**记住**」和「**懂**」分开。三句话自检：它召回的是 what 还是 why？跨段关系拼得出来吗？过期和错的谁发现？

## 结构（7 节，悬念链，~2000 字）

### 0. 开头钩子：它读了我的 docs，还是不听（作者亲历，2 段内掉头）
- 画面（**作者原声，逐字进稿**）：我用 opencode 改一个自己项目的代码，它经常选择性忽略我写在 docs 目录里面的一些关键要求，自作主张按照自己的理解去执行，导致最后出来的结果完全不符合预期，需要后续再来纠偏
- 掉头：这不是「它没记住」——恰恰相反，我**写了、它也读了**，还是不听。于是问题从「怎么让它记住」变成「**记住，到底能不能解决问题**」
- 引出：最近有篇文章吵上了 HN，标题就说得很直白——Agent 不需要记忆，它需要文档
- ⚠️ 禁止「上一篇 / 我们知道 / 系列」开头

### 1. 那篇文章说：记忆插件在解决错的问题
- 架构（原文）：扫会话 → 抽片段 → 塞向量库 → 每次 prompt 注入 top-5 → 不够再给检索工具
- 五条硬伤（挑 3-4 条精讲，其余一带而过）：相似度 ≠ 正确；片段丢上下文；把过去当真相（代码每天都在变）；agent 不知道自己不知道；存储不可审计（一万条 embedding，哪些过期/错误/从没被用过？）
- 它的主张：换成 Markdown「文档大脑」，循环从 `prompt → build → forget` 改成 `prompt → consult → build → update`——人能读、能改、能提交；单个 `AGENTS.md` 不够
- 配图：`01-memory-pipeline.png`（脚本画：四步流水线 + 「token 燃烧机器」注释）
- 落点：听起来有道理。但我先想到的，是自己踩过的坑

### 2. 我的 RAG 亲历：相似度天生漏东西（机制层，本篇核心）
- **作者原声（逐字）**：自己做 RAG 类似的应用的时候，就发现这方面的问题非常突出，相似度捞回来的东西经常遗漏最关键的一部分，即便是加上了 reranker 机制，还是没法做到完全可靠
- 把「漏掉的部分」拆成三类（人话 + 图）：
  - **A 多跳**：答案不在一段里，要跨好几处拼；按单段相似度排序，天生拼不出跨段关系
  - **C 整体结构**：得知道整个项目/知识库怎么组织、哪些块之间什么关系，不是一段段比相似
  - **B 意图**：表面词重合，真正要的是背后的约束（有时成立）
- reranker 为什么救不了：它只在**候选池里重排**，而候选池在召回阶段就按相似度丢了跨段/结构信息——重排救不回没进来的人
- **作者原声（逐字）**：关于最深层次的理解，不是浮于表面形式的那种相似性，其实目前的 embedding 机制天生还是有很大缺陷，距离非常完美的程度还有很大差距，所以没有办法把需要的东西都捞回来
- **留口子（红线）**：不说「embedding 永远不会好」，只说「只要还是**按段相似度召回**这个范式，reranker 再强也补不回召回阶段丢掉的跨段/结构信息」
- 配图：`02-recall-gap.png`（脚本画：一段问题 → 相似度捞回几个孤立片段 / 缺失的跨段连线）
- 落点：所以那篇文章把矛头指向「记忆」的时候，我关心的其实不是记不记，是**它记的方式**

### 3. 但评论区吵翻了（HN 辩论复盘，呈现辩论，不站队）
- 背景：HN **335 分 / 203 条评论**（写作时复核）——原文说文档是纯增益，评论区一半人反对
- 正方一句：记忆是「未策展、不透明」的，文档是纯增益
- **反方 ①（kaydub）**：代码就是文档，我把文档全删了；stale 的 markdown 只会污染上下文，而且模型几乎不会「删除」，只会不断追加
- **反方 ②（mzhaase，具体翻车）**：我让 agent 记「决策」，结果它自己越写越多、还自创规则「D-236」，我在 code review 里被它拿一条我压根没批准过的规则怼；明令不许碰这些文件，它照样碰——最后只剩 context bloat
- **反转 ③（CapitalistCartr，最关键）**：这些批评**同样适用于作者自己的方案**——Markdown brain 一样不知道该先读哪篇、一样会 stale、一样要靠后台进程去更新。他补一句：**「他的 GitHub 比他的文章好」**（实际方案里每份文档带 catalog + read_if 条件，是有设计的）
- **安全炸弹 ④（panarky，一句话带过）**：有人指出这套方案把记忆文件**直接注入 system prompt**、优先级还高于 `AGENTS.md`——clone 一个恶意 repo 就可能被静默执行指令。**只一句，不展开成安全文**
- **平衡 ⑤（crazygringo，一句）**：只要在指令里强制「只保留当前状态、禁止 append、禁止堆 D EPRECATED」，stale 其实真能治住
- **元观察 ⑥（可放开头或此处，机灵句）**：一篇讲「记忆工具没用」的文章，评论区变成了**记忆工具集市**——203 条里十来个在推销自家方案
- 落点：**两边都翻过车。** 记忆记不准，文档会腐烂、还会被忽略——这正是我开头那一幕

### 4. 那这些工具怎么做记忆：有界、按项目、还「刻意不记」
- 把三个做法并排放（**共同点才是看点**）：
  - **ZCode Memory**（智谱 z.ai）：给 Agent 提供**项目级**长期记忆；官方还专门写了「**刻意不记**」什么——代码结构和 Git 历史，因为 agent 随时能重新读（呼应原文「存储不可审计」那条）
  - **Kimi 记忆空间**：**最多 50 条、每条 ≤500 字**，可逐条查看、修改、删除（2026-04 前的旧记忆例外）
  - **Hermes Agent**（Nous Research）：**有界、经过整理**的记忆（MEMORY.md ≈2200 字 / USER.md ≈1375 字上限）
  - （**GLM 记忆机制文档**补一句官方判据：主记忆文件建议 **≤200 行**、**指令型 vs 学习型**分开）
- **本篇新洞察**：能用的记忆几乎都是**小而有限、按项目、且明确「不记什么」**——没一个是「一万条 embedding 全量囤着」。这不是巧合
- **张力（作者亲历）**：但记忆一有用，边界就成了问题——zcode 最近的「上传代码事件」引发社区反感；能确认的是客户端**存在项目快照打包与上传行为**，透明度与权限边界受质疑。隐私的东西，有几个人会不在意
- 配图：`04-bounded-memory.png`（脚本画：50 条 / 2200 字 / 200 行 / 「刻意不记」几个有界记忆 vs 记忆插件一万条 embedding 的对照）
- 落点：方向对（有界、按项目），但「有界」的另一面是**边界由谁定、隐私归谁**；而且写了它是否照做，仍是另一回事（呼应第 3 节 + 开头 opencode 那一幕）

### 5. 落点：三条自检问题（可截图工具，§9 判据）
- 给读者一张能复述、能截图的卡：
  1. **它召回的是 what 还是 why？**（事实能捞回来，约束/前提/为什么常常漏 → 对应 A/B）
  2. **跨段关系它拼得出来吗？**（多跳、结构，单段相似度天生拼不出 → C）
  3. **过期和错的，谁发现？**（存储能不能被审计、被删，而不是只增不减 → 对应原文第 5 条硬伤）
- 用法一句：下次看到「记忆插件」，先拿这三句过一遍再决定装不装
- 配图：`03-checklist.png`（脚本画：三问卡片，可直接截图转发）
- ⚠️ 中立红线：只给自检工具，不替读者下「装/不装」的结论

### 6. 回扣 + 结尾
- 回扣开头：opencode 那次，问题不在「它没记住」，在我以为**记住就等于懂**
- 中立收束：不劝你卸掉记忆，也不劝你写一屋子文档；先把「记住」和「懂」分开——**记忆是仓库，理解是地图，仓库再大也画不出地图**
- 开放式问题（**作者原声槽**，句由作者手打）
