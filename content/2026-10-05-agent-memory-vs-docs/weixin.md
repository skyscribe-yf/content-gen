我用opencode改一个自己项目的代码，它经常选择性忽略我写在docs目录里面的一些关键要求，自作主张按照自己的理解去执行，导致最后出来的结果完全不符合预期需要后续再来纠偏。

这不是它「没记住」——恰恰相反，我写了，它也读了，就是不听。

于是问题从「怎么让它记住」，变成更麻烦的那个：**记住，到底能不能解决问题？**

最近有篇文章，把这件事吵上了 Hacker News 首页，标题很直白——**Agent 不需要记忆，它需要文档。**

## 一、那篇文章说：记忆插件在解决错的问题

市面上的「记忆插件」，架构拆开看几乎一样：

扫会话 → 抽片段 → 塞进向量库 → 每次提问注入最像的 5 条 → 还不够，再给个检索工具。

![记忆插件流水线](01-memory-pipeline.png)

原文列了五条硬伤，我挑最要命的三条：

**相似度只告诉你「像」，不告诉你「对不对」。** 两条话在向量空间里挨得近，说明不了哪条对、哪条过期。

**片段丢掉了上下文。** 一句从会话里抠出来的「记忆」，能装下的有限，环境、动机、取舍全没了。

**最狠的一条：存储不可审计。** 一万条 embedding 躺在库里，哪些过期、哪些是错的、哪些从没被用过——**没人知道**。

他的结论：把「记忆」换成 Markdown 的「文档大脑」——干活前查阅，干完更新，人能读、能改、能提交。

其实我们自己用多了就会知道，尽管agent的能力一直在飞速进化，它一直还是只有一个“金鱼记忆”，每次推理开始的时候，它都依赖于输入给他的前缀提示。很多工程上照搬人类记忆的做法，尝试为它施加大记忆恢复术的方法，都会遇到各种各样的后遗症。

## 二、我的 RAG 亲历：相似度天生漏东西

那篇文章把矛头指向「记忆」，我想到的是自己踩过的一个坑。

自己做RAG类似的应用的时候，就发现这方面的问题非常突出，相似度捞回来的东西经常遗漏最关键的一部分，即便是加上了reranker机制，还是没法做到完全可靠。

「相似度漏掉的那部分」往往不是边角料，**恰恰是最关键的那一块**。我把它归成三类：

- **多跳**：答案不在一段里，要跨好几处拼；按「一段一段比谁更像」排序，天生拼不出跨段关系；
- **结构**：得先知道整个知识库怎么组织、哪块和哪块什么关系，而不是孤立地比；
- **意图**：表面词对得上，背后要的却是另一层约束，这类也会漏。

有人会说：加个 reranker 重排不就行了？不行。reranker 只是在**已召回的候选里重新排队**；召回阶段丢掉的跨段关系和整体结构，它补不回来——**没进来的，永远排不到前面。**

![相似度盲区](02-recall-gap.png)

关于最深层次的理解，不是浮于表面形式的那种相似性，其实目前的embedding机制天生还是有很大缺陷，距离非常完美的程度还有很大差距，所以没有办法把需要的东西都捞回来。

不过我也不敢断言 embedding 永远不会变好。只要还是「**按段相似度召回**」这条路子，reranker 再强，也救不回召回阶段丢掉的东西。

## 三、但评论区吵翻了

这篇在 HN 拿到 335 分、203 条评论——评论区将近一半人不同意它。

支持一方说：记忆是未策展、不透明的，文档是纯增益。

反对最响的是「代码就是文档」派：有网友说自己把文档全删了——过期的 markdown 只会污染上下文，而模型几乎不会「删除」，只会一路往上加。

更典型的是具体翻车：一位网友让 agent 记「决策」，它却越写越多，还自创规则 **D-236**；code review 时，它拿这条没批准过的规则来怼人。明令不许碰，它照样碰——最后只剩占上下文。

这个例子实在是太过于典型了，众所周知目前agent的进化速度飞快，用来写代码做项目，每次产生大量的思考过程输出和工具调用，没有人能一直盯着看的，所以有时候混入的一些猫腻，只有事后才发现，但是即使这时候你想去强迫它更正，才发现它完全不太听你的指挥，这些问题都不是简单一句“指令遵循能力不好”可以带过去的。

最扎的一刀是反转：这些批评**同样适用于作者自己的方案**——Markdown 大脑一样不知道该先读哪篇、一样会过期、一样要靠后台进程更新。他补了句挺客气的：**「他的 GitHub 比他的文章好。」**（实际方案里，每份文档都带目录和「什么条件下该读」的标注。）

还有人指出：这些记忆文件会被**直接注入系统提示**、权限高于 `AGENTS.md`，安全边界成了新问题。

也有唱反调的：强制「只保留当前状态、禁止追加、禁止堆废弃标记」，过期问题真的能被治住。

**两边都翻过车。** 这正是我开头那一幕。

## 四、那这些工具怎么做记忆：有界、按项目、还「刻意不记」

最有意思的是看真正在用的产品——几乎没一个是「一万条 embedding 全量囤着」：

- **ZCode 的 Memory**：项目级长期记忆；官方还专门写了它「**刻意不记**」什么——代码结构和 Git 历史，因为随时能重读。
- **Kimi 的记忆**：最多 **50 条**、每条 **500 字**，可逐条查看、修改、删除。
- **Hermes Agent**：有界、经过整理的记忆（MEMORY.md 约 2200 字、USER.md 约 1375 字上限）。
- **GLM 的编程文档**给出类似判据：主记忆文件建议不超过 200 行，把「人写的指令」和「agent 自己攒的经验」分开。

共同点很一致：**小而有限、按项目、并且明确「不记什么」。**

zcode的记忆机制其实挺有趣的，很多时候它可以自动完成一些机械重复的工作，极大提高缓存命中率和token效率，然而最近的上传代码事件，还是引起了社区很大的反感，毕竟隐私的东西，有几个人会不在意呢？不过话说回来，它按照项目文件夹保留的内部记忆，很多时候还是非常有用的，有点hermes agent的那个味道了。

这里得把两件事分开：按官方口径，Memory 本身是本机 Markdown、不上传；引发反感的是同期被发现的「代码库索引」——它**静默打包本地工作区上传云端**，默认开启，官方回应数据不留存、不用于训练，随后开源代码库、接受安全审查。**记忆越有用，边界越躲不开：边界由谁定、说没上传就可信吗，才是更难回答的那一问。**

## 五、留给你的三个问题

给 agent 装「记忆」前，先过这三问：

1. **它召回的是 what，还是 why？** 事实也许捞得回来；但「当初为什么这么定」「有什么前提不能动」，常常捞不回来。
2. **跨段关系，它拼得出来吗？** 要跳好几处才拼得出的答案，按单段相似度排序，天生拼不出。
3. **过期和错的，谁发现？** 记忆能不能被审计、被删掉，还是只增不减、越滚越大？

![三条自检](03-checklist.png)

为什么这一点最难防？其实模型还是非常善于捕捉文本表面的相似性，但是有时候有些专业术语或者领域黑话方面的东西，召回的内容让领域专家一看就明白，但是模型自己却会陷入极大的困惑中不能自拔，很多幻觉就因此爆发了。

## 六、记住是仓库，理解是地图

回到开头：opencode 的问题，不在「它没记住」，在我以为**记住就等于懂**。

我不劝你卸掉记忆，也不劝你写一屋子文档。先把两件事分开——

**记住是仓库，理解是地图。仓库再大，也画不出一张地图。**

如果只转一句话给同事：**相似度不是理解——记住了，不等于懂了。**

你被各种agent的记忆机制坑过吗？你是如何发现这类问题，又是怎么绕过去的？如果你自己设计agent,记忆机制你会怎么选？
