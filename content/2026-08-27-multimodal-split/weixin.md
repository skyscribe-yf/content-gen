你让 DeepSeek 挂进 opencode 帮你写代码，它自动去读 GitHub 里的 issue 描述。

跑着跑着，工具突然报错：当前模型不支持读图，无法理解 issue 描述里面的图片。

更聪明的 DeepSeek V4 Flash 0731 版本，有时候甚至会自己写一段 Python 代码做像素分析，然后给你猜一个啼笑皆非的答案出来，让人哭笑不得。

你的选择只剩两个：要么自己写个 proxy，把图片传给第三方多模态模型，翻译成文字再传回来；要么找一个 MCP 服务来完成曲线救国。

8 月 21 日，DeepSeek 终于上线了它的视觉模型，V4-Flash-Vision-Exp。没有发布会，没有技术报告，甚至没开源。社区连夜实测：连梁文锋本人最具代表性的照片都认不出来。

AI 都能生成视频了。DeepSeek 为什么连图都读不懂？

## 国产旗舰，分成了两个世界

先看看牌桌两边的差距。

DeepSeek V4 系列，4 月发布，1.6T 参数的 Pro 版本加 284B 的 Flash 版本，清一色纯文本。1M 上下文、万亿参数、Codeforces 评分 3206——全球开源模型推理第一，但输入模态只有 text 一个词。

智谱 GLM-5.2，同样纯文本。744B 参数、1M 上下文、开源 SOTA，官方文档里「输入模态」一栏写得很诚实：Text。

另一边是原生多模态阵营。

Kimi K3，2.8T 参数，从预训练开始就把图文揉在一个模型里，还从零训练了自己的视觉编码器 MoonViT。Qwen3.8-Max，原生视觉，全模态。MiniMax M3，多模态融合是卖点。

同样是国产头部，一边是「最强文本模型」，一边是「能看的模型」。

用户不会管你路线怎么分——用户只知道，DeepSeek 里传图，会得到一句「未提取到文字」。

![国产旗舰的视觉能力对照：一边纯文本，一边原生多模态](01-model-table.png)

## 三位创始人，三个说法

这个分歧，在创始人的公开表态里看得最清楚。

DeepSeek 梁文锋在投资人交流会上说：「多模态对智能的上限，它是一个组件，它不是主线本身。」

智谱唐杰更直接：多模态对提升 AGI 的智能上界，帮助有限。

但智谱自己的评论区出卖了他。唐杰在 X 上公开征集 GLM-5.3 想要什么功能，评论区清一色两个字：视觉。

最反讽的是月之暗面杨植麟。他说：「多模态只要不损伤文本的『脑子』，就已经很好了。」——这可能是三个人里最保守的说法。

但他做的是三个人里最激进的事：Kimi K3 原生多模态，2.8T 参数，视觉从预训练阶段就进来了。

嘴最克制的人，动作最猛。

一位开发者这样吐槽梁文锋的「组件论」：「国外 Claude 系列、GPT 系列，一直都有视觉能力。MiniMax 和 Qwen 早就多模态融合了。这个说辞顶多是一家之言，而且给用户带来了诸多不便，属于稍微有些傲慢的对用户需求的无视。」

你说多模态不是主线。可你的用户天天在传截图。

## 一张图，是怎么被翻译进大脑的

要理解这场分歧，先得看一张图是怎么进模型的。

图片不能像文字那样直接喂给模型。一张 1024×1024 的图，是约 100 万个像素、每个像素三个数字——300 万个数字直接赛进去，任何模型都扛不住。图像和文字的“数据结构”就不一样：文字是离散的（有限的词表），图像是连续的（像素值几乎无限），所以必须先“翻译”。

翻译第一步是切块：把图切成 16×16 的小块（patch），每块交给一个视觉编码器——一个专门训练认图的子网——编码成一个向量。这一步相当于把“像素的语言”翻译成“模型的语言”。视觉编码器通常还拆成两路：一个低分辨率看“大概”（这是猫、画面里有五个人），一个高分辨率看“细节”（小字、按钮、图表里的数字）。DeepSeek 自己的 DeepSeek-VL 就是这么做：两个编码器并行，输出 576 个视觉 token，相当于把一张 1024×1024 的图压缩成 576 个“视觉单词”。

这 576 个视觉 token 还要再叠一层投影（MLP），把视觉向量映射到文本 token 的维度空间——像翻译官，把视觉语言转写成文本语言。然后视觉 token 和文本 token 拼接成一条序列，喂给大语言模型。

这是“嫁接眼”的标准做法：模型本身不动，外接一个视觉翻译官。图像 → 编码器 → token → 投影 → 拼接 → 模型推理，中间隔着两三层翻译。

Kimi 的原生路线不一样：MoonViT 是从零训练的视觉编码器，视觉表示直接进入下一 token 预测的目标——模型预测下一个词的同时，也在预测下一个视觉 token。没有翻译官，视觉和文本共用同一套 token 空间。翻译得再准也是二次转述，直接说同一种语言才是原生。

这个差别，就是后面所有故事的根源。

## 装眼睛，为什么怕伤脑子

但「组件论」不是没道理的。给模型装眼睛，真有个大坑：视觉会跟文本抢同一个大脑。

先看 DeepSeek 自己论文里的消融实验。DeepSeek-VL 训练时，把图文数据比例拉到 100%，模型的文本能力（MMLU）直接掉 10.3 分；把配比控制在 70% 图文 + 30% 文本，只掉 0.3 分。

Kimi K2.5 的技术报告也记录了同样的现象：如果在训练中后期才加入视觉数据，文本能力会先下降，再慢慢恢复。

图像和文字的数据结构、信息密度、学习速度都不一样。同一次训练，视觉数据会跟文本、代码、数学、推理争模型容量，目标互相干扰。就像让一个人同时学钢琴和举重——不是练不出来，是每个动作都在跟另一个动作抢肌肉记忆。

![图文配比决定文本能力掉多少分：100% 图文掉 10.3，70% 只掉 0.3](02-ablation.png)

这就是 DeepSeek、GLM 不敢迈出那一步的真实原因，这不是傲慢，是风险账本。

## 有人用 2.8T 参数把「伤脑子」证伪了

但 Kimi 在 GTC 2026 上放出的数据，把这个账本掀了。

K2.5 改用早期融合：从训练一开始就把视觉和文本混在一起训，而不是先把文本训完再把视觉「贴」上去。

结果有两组反直觉数字：

第一组，只训练视觉任务（数数、识图、视觉问答），完全没加数学和编程训练——文本推理能力居然变强了。

第二组更离谱：K2.5 采用「零视觉 SFT」——所有微调数据全是纯文本，视觉能力全部靠文本与视觉联合的强化学习训出来，最终视觉任务还是接近最先进水平。

一句话：练看的同时，想也变强了。

![伤脑子的不是多模态，是融合时机：后期拼接先降后恢复，早期融合一路上行](03-fusion-curves.png)

「伤脑子」的锅，根本不是多模态，是后期拼接。

把视觉在训练最后才接上去，两个模态互相没磨合过，当然打架；从最开始就一起训练，视觉反而变成了文本推理的「杠杆」。

这才有了 Kimi K3 敢上 2.8T 原生多模态的底气。也是这个账号之前拆解过的「原生多模态 vs 嫁接」路线差的全部含义。

## 嫁接眼和原生眼

现在你大概能理解，DeepSeek 8 月 21 日上的「视觉模型」为什么翻车了。

V4-Flash-Vision-Exp 大概率是「嫁接眼」：把视觉编码器接到 V4-Flash 的文本引擎前面，图片折算成最多 384 个 token 交给语言模型推理，而不是从预训练开始就和文本融在一起。官方放出的评测，清一色是 Agent 基准（读图表做决策、终端操作），没有一项是「看图答题」式的视觉基准。

社区实测结果：认不出梁文锋照片，复杂图表漏关键信息。

独立评测机构 Artificial Analysis 的数据也印证了这一点：V4 Flash Vision 在 Intelligence Index 上拿 51 分，比不带视觉的原版 V4 Flash 还低 1 分；但换到 Agentic Index，加了视觉的版本却大幅领先原版。

![社区实测：Vision 版智能指数反降 1 分，Agentic Index 大涨](05-tweet-ai-index.png)

嫁接眼还有一条更野的路：社区自己搭桥。OCR 工具、第三方视觉模型、MCP 服务，先把图片翻译成文字，再把文字喂给 DeepSeek。我在开头说的 proxy 和 MCP 曲线救国，就是干这个的。但 OCR 带过来的视觉理解，很多时候因为底层技术上的原因，会导致出现理解偏差——图片被压缩成几行字，位置关系没了、细节丢了，漏掉一个字，意思就完全反过来。

「这未必是翻车，更大概率属于 DeepSeek 自己学艺不精，」一位 AI 从业者表示，「毕竟研究 DeepSeek OCR 的顶级研究员，前面刚有离开公司加盟百度、搞出 Unlimited OCR 的先例。DeepSeek 在 2025 年初自己也推出了多模态模型，只是没有引起很大的反响。R1 系列的确很强，但出现不擅长的低谷也是很正常的现象，不能因为一家公司一时的成败就否定技术本身。」

![嫁接眼：外挂镜头接大脑；原生眼：视觉长在大脑里](04-graft-native.png)

原生眼（Kimi 的 MoonViT）从零训练视觉编码器，视觉直接进下一 token 预测，跟文本共享同一个代表空间。嫁接眼（DeepSeek 的 Vision Exp）是视觉前端 + 文本引擎，跑分全放 Agent 基准，连创始人照片都认不出。

你让模型「看」的方式，决定了它「懂」的程度。

## 多模态不是要不要，是用户等不等得起

多模态融合是提高智能上限还是拉低智商，技术界还有争议。

但有一件事没有争议：用户的需求是实实在在的。

「如果有得选，我更愿意用带视觉能力的模型——其他条件相同的情况下。毕竟能省点功夫用一个模型搞定，谁愿意费劲去搞 proxy 或者 MCP 来给模型做视觉？」

这句话，是几乎所有开发者的心里话。

DeepSeek 克制的理由（算力、现金、战略排序）都是真实的，DeepSeek-VL 论文里「加视觉会掉文本分」的恐惧也是真实的。但 K2.5 已经给出了另一个答案：用早期融合，把「伤脑子」变成「补脑子」；用 K3 的 2.8T 参数，证明「全都要」不是梦。

当文本能力越来越难拉开差距，视觉能力正在成为国产模型的下一个分水岭。谁先把自己的眼睛装进模型，谁就先赢得用户的工位。

**一句话总结**：DeepSeek 的「多模态是组件」不是技术判断，是资源账本；Kimi 用 2.8T 参数验证了「视觉练强推理」，而用户的需求很实在——能用吗，就选谁。
