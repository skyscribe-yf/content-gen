| S2 | 墙一：握手 O(T²) | 会议室概念图嵌入（img/handshake.png，圆桌多人握手，无数字）；10 人全连接图 45 条线（Create）→ 100 人密集连线爆点（grow 点数 10→100，连线数 45→4950 counter_value）；「翻 N 倍 → 翻 N² 倍」标签；悬念结尾 | AI 的「记忆」就是注意力：每个词，都要回头看之前所有的词。想象一个会议室。10 个人开会，每个人要跟其他 9 个人握手，一共 45 次。100 个人开会？4950 次。人数翻 10 倍，握手数翻 100 倍。这就是第一道墙：序列长度翻 N 倍，计算量翻 N 的平方倍。100 万字的上下文，计算量是 1 万字的 1 万倍。GPU 再快，也扛不住。可就算算得动，还有第二道墙，在前面等着。 |
| S3 | 墙二：KV cache 笔记 | 笔记本堆成山概念图（img/notebooks.png，笔记山压垮桌面，无数字）；KV cache 公式条 T×d×L×2；5 TB vs H100 80 GB 对比条（grow_bar，60 倍爆点）；两道墙叠压动画；「数学上跑不动」定格 | 每次握完手，还得记笔记，方便下次直接查。人越多，笔记越多，本子写不下了。这就是 KV cache——显存爆炸的那道墙。每个 token，都要缓存自己的 Key 和 Value。100 万字的上下文，用传统方式记，这份笔记要 5 TB 显存。一张 H100 才 80 GB。5 TB，比它大 60 倍。两道墙叠在一起：计算炸了，存储也炸了。这就是为什么大多数模型的记忆，只能停在几万字——不是不想扩，是数学上，跑不动。 |
| S4 | 实测：O(T²) 是物理定律 | 延迟增长曲线脚本画（1K→2K→4K 实测点 + 抛物线 Create，counter_value 0.10→0.38→1.53s）；32K 崩溃爆点：屏幕裂开/黑屏特效（transition_out 变体）；「不是理论，是物理定律」白字定格 + 红叉否定「翻不过去？」 | 这两道墙有多硬？写这篇文章的时候，我做了个实验：用 PyTorch 实现标准注意力，从 1K 序列开始往上测。1K，0.1 秒。2K，0.38 秒。4K，1.53 秒——长度翻 4 倍，延迟翻了 15 倍。然后，我试着跑 32K。电脑，直接崩了。没有报错，没有警告，就是黑屏重启。32K 的注意力矩阵，光这一个矩阵，就吃掉了所有内存。O(T²) 不是理论，是物理定律。那这道墙，真的翻不过去吗？ |
| S5 | 第一招 DSA：只跟 2048 个人握手 | Indexer 挑人概念图（img/indexer.png，信使从人群里挑出最相关的几个，无数字）；全连接 → 漏斗筛选 → 只连 2048 个（结构脚本画：T 个点 → 漏斗 → k 个点）；「陷阱：Indexer 自己也是 O(T²)」红字爆点卡 | GLM-5.2 给出了答案，而且不止一招。第一招，DSA，稀疏注意力。标准注意力，每个 token 看所有历史 token。DSA 加了一个 Indexer：先从所有历史里，挑出最相关的 2048 个，只在这 2048 个上算注意力。从「跟所有人握手」，变成「只跟最相关的 2048 个人握手」。T 再大，计算量只线性增长。但这里有个陷阱——Indexer 自己，也是 O(T²)。它要从 T 个 token 里选出前 2048 个，本身就要跟所有 token 算一次。问题，只是换了个位置。 |
| S6 | 第二招 IndexShare：稀疏化可以递归 | 78 层 Transformer 堆叠脚本画（78 个小方块）→ 21 层点亮跑 Indexer、57 层复用（counter_value 78→21）；跨层相似度 >0.8 标签条；2.9× 收益 counter_value 爆点；悬念：存储那堵墙？ | 这就是 GLM-5.2 最独家的洞察：稀疏化，可以递归。DSA 是第一层稀疏化；IndexShare 是第二层——对 Indexer，也做稀疏。78 层里，只有 21 层跑 Indexer，剩下 57 层，直接复用最近的索引。凭什么？因为相邻 Transformer 层的注意力模式高度相似，跨层相似度超过 0.8，4 层窗口内复用，依然有效。两招叠加，1M 上下文下，每个 token 的计算量降低了 2.9 倍。计算这道墙，翻过去了。那存储那道墙呢？ |
| S7 | 第三招 MLA：5 TB 压到 78 GB | 维度压缩脚本画：6144 宽条 → 512 窄条（morph，>10× 标签）；KV 总量 5 TB → 78 GB 对比（grow_bar 从爆表缩到 H100 边界）；三招协同三卡（DSA / IndexShare / MLA 各拆一道墙，CheckMark 依次点亮）；「缺一不可」强调 | 第三招，MLA，压缩 KV cache。标准 KV，每个 token 缓存完整的 Key 和 Value 向量，维度 6144。MLA 用一个 512 维的压缩表示替代，需要时再展开——压缩超过 10 倍。1M 上下文，KV cache 从 5 TB，压到 78 GB。从「完全不可行」，变成「多卡能扛」。三招协同，缺一不可：DSA 拆掉注意力的平方项，IndexShare 拆掉 Indexer 的平方项，MLA 压掉 KV 的线性增长。任何一招缺失，1M 上下文，都跑不动。 |
| S8 | 总结 + 翻墙概念图 + 品牌尾卡 | 翻墙概念图嵌入（img/wall-jump.png，翻过两道高墙的背影，无数字）；三招回顾链（DSA→IndexShare→MLA 依次亮）；1.0 → 13.0 +1200% 回扣（counter_value）；尾卡：avatar 圆角图 + 黄色「关注「数解AI」」+ 当期文章标题 + 下一篇预告（推测解码）+ 开放式问题 | 回到开头：AI 为什么干到一半会崩？因为记忆是有代价的——注意力的 O(T²)，KV cache 的线性增长，在长序列下同时爆炸。GLM-5.2 用三招翻墙，把 1M 上下文，从数学上不可能，变成工程上可行。SWE-Marathon 从 1.0 到 13.0，涨了 1200%，不是魔法，是数学。更深的启示：稀疏化可以递归——任何 selector 自己，都可能成为下一个瓶颈。下一篇，我们拆「AI 为什么说话这么慢」——推测解码的数学。你觉得，1M 上下文真的有必要吗？评论区聊聊。 |

## 制作流程

1. 口播录音：`scripts/voice_studio.py` 录音室（后台启动 → 用户逐段录音 → handoff `tts/sentence-boundaries.json`）→ `scripts/voice_process.py` 修音 + 时长 + 停顿分析（门禁 4/5）
2. 动画：每段一个 Manim Scene（S1..S8），`construct` 末尾 `pad_to_voice()`；**at() 严格挂 tts/pauses.json 静音结束点**（先声音后动画门禁）
3. 构建：`scripts/manim_video_build.py` mux 配音 + 无缝拼接 + 黄色字幕烧录（MarginV=210, 75 号，整行 + 150ms 淡入）+ 品牌尾卡
4. 封面：Cover 场景单帧渲染（复用两道墙剪影视觉）→ `<标题>-封面.png`（1080×1920，内容集中中间 3:4 安全区）
5. 归档：`content/2026-07-04-ai-memory-crash/shipinhao/`
