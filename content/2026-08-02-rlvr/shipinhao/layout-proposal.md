# RLVR Manim 整体 Scene 设计重构方案

状态：待作者人工 review。本文档确认前，不改 `scenes.py`、不重新渲染成片。

## 1. 先看当前版本的问题

当前成片的根因不是某两个坐标点，而是页面组织方式：

1. **动态数字没有参加整页排版。** S1 的 `pass_num` / `fail_num` 在 `layout_page(page2)` 之后才创建，并且 `counter_value()` 先把数字加到场景原点、播放完才 `next_to()`。所以 00:12–00:13 的数字会压到下方说明卡上。
2. **跨页复用了同一个 mobject。** S1 的 `question` 同时属于 `page3` 和 `page4`；`page4` 先重新 `layout_page()`，再在 00:20 左右 FadeOut `page3`，导致旧页元素还在屏幕上时，新页布局已经移动了它。于是出现“问题文字被结论卡压住”的重叠。
3. **页面仍是“标题 → 元素逐条向下接龙”。** 虽然调用了 `page_stack()`，但很多数字、标记、箭头在布局之后才追加，整页 box 并不是最终画面。布局器只是在给“不完整的页面”居中。
4. **每个 Scene 都重复放大标题和页脚。** 主体被压缩到中间，纵向可用空间没有转化为叙事空间；页面只好频繁清屏换下一屏。
5. **多数页面把所有信息都做成卡片。** 图片、说明、数字、结论都挤在同一列，缺少“主视觉 / 证据 / 结论”层级。
6. **动画语法单一。** 大量 `play_scroll_unroll()` + `FadeOut()`，没有让上一页内容变形、留存、退到背景或成为下一页的结构基础，所以观感像 PPT 翻页。

当前音频边界也暴露了一个独立问题：S5 的“数学”、S6 的“而”、S7 的“verifier”、S8 的“变/成”、S9 的“评/论区”被切成碎片。这不是本次布局重构的前置阻塞，但后续 build 时必须单独修正字幕边界，否则画面节奏仍会显得生硬。

当前 9 段实际配音总长约 242.8 秒（约 4 分 03 秒），与 storyboard 中的“目标 2–3 分钟”也不一致。本方案先不改声音，只按现有声音时间线设计画面。

## 2. 新的整体画面语法

每个 Scene 不再理解成“几页卡片”，而理解成一个持续发展的舞台。每个舞台固定有四个层级：

```text
┌──────────────────────────┐
│ 章节标签 / 极短标题        │  ← 小、稳定，不占主体空间
│                          │
│        主视觉层            │  ← 流程、轨迹、图、数字
│   （画面主要动作发生在这里） │
│                          │
│      证据 / 结论层          │  ← 随台词变形、强调，不另起一页
│                          │
│ 字幕安全区                 │  ← 不放内容
│ 数解AI · 大模型原理         │
└──────────────────────────┘
```

具体规则：

- 标题改成 **30–32 号的章节标签**，只在 Scene 开头完整出现，随后缩到左上角，不再用 38–40 号标题长期占屏。
- 主体内容使用显示带的 55%–70% 高度，主动把视觉重心下移到字幕安全区上方；不再把所有元素压在中间一小块。
- 每个画面只保留一个主视觉焦点：流程、数字、轨迹、对比或防线，不能图片、五张卡、说明文字同时抢焦点。
- 结论不通过清屏产生，而通过 `ReplacementTransform`、高亮、退场到背景、轨迹连线等方式从主视觉中长出来。
- 每一次换页前，先建立下一状态的完整稳定 box；动态数字、箭头、标记都必须有最终位置占位。禁止 `layout_page()` 后再用 `next_to()` 把可见元素追加到页面外。
- 一个 mobject 只属于一个页面状态。跨状态必须复制或 `ReplacementTransform`，禁止同一对象同时挂在两个 page group 上。
- 每个 Scene 最多 1 次主结构切换；短台词只改变状态，不清屏。真正换主题时才清屏。

## 3. 9 个 Scene 的新设计草案

### S1｜开场：终点只有一个数字（24.8s）

目标：让观众看到“多步行动 → 一个 0/1 → 反馈回到整条轨迹”，而不是看四次卡片翻页。

```text
章节标签：RLVR · 只有 0/1 的奖励，怎么学会纠错？

读仓库 → 改代码 → 跑测试 → 看报错 → 再改一次
      ╲       ╲       ╲       ╲       ╲
                 ─────── 轨迹线 ───────▶ 终点
                                      测试通过 1 / 失败 0
                                      ↖ 反馈回传整条轨迹
```

- 0–7s：五步工作流沿一条纵向/斜向轨迹出现，步骤之间保留连接线；不清屏。
- 7–13.8s：终点结果卡从轨迹末端展开；`1` 和 `0` 在各自卡片内部滚动，数字位置从一开始就参加整页布局。
- 13.8–20.7s：终点到前面步骤画一条回传弧线，依次点亮“拆任务 / 调工具 / 反复纠错”；工作流保持在背景。
- 20.7–24.8s：把终点卡 morph 成“RLVR：可验证奖励”主卡，轨迹退成低透明度背景；不再让旧问题文字与新卡重叠。

### S2｜定位：奖励设计和策略更新是两层（18.0s）

目标：用一张二维结构图讲清 RLVR、PPO、GRPO，不做三个孤立卡片。

```text
             奖励从哪里来？
                 RLVR
              ╱       ╲
             PPO       GRPO
          策略更新   策略更新
```

- RLVR 放在上方“奖励层”，PPO / GRPO 放在下方“更新层”。
- 两条箭头保留到结尾；最后只在“RLVR = GRPO”上加红叉，不清除结构图。
- 删除重复 `footer()`；页脚只保留一份。

### S3｜R1-Zero：最小闭环和数字证据（28.3s）

目标：先让闭环成为主视觉，再把数字证据嵌入闭环，而不是从流程图硬切到一堆卡片。

```text
                 生成
              ↗       ↘
          更新  ←  Verifier  →  奖励
              ↖       ↙
                 检查

        AIME 2024：15.6%  ─────▶  77.9%
```

- 0–12.6s：四节点闭环占据主体，Verifier 在视觉中心；数学题 / 代码题作为两枚侧边证据徽章。
- 12.6–21.9s：闭环缩到上半区，底部出现一条由 15.6% 到 77.9% 的增长轨迹；先显示旧值，再滚动到新值。
- 21.9–28.3s：闭环中的“反思 / 验证”节点亮起，底部结论条变为“提高可验证结果的概率”。不清屏。

### S4｜coding 外溢：轨迹选择，而不是卡片堆叠（25.8s）

目标：把“投篮类比 → coding agent 行为 → 力量/危险”做成同一条轨迹的三次解释。

```text
投篮示意（上）
成功轨迹  ━━━━━━━━━▶  终点
失败轨迹  ┄┄┄┄┄┄┄┄▶  终点

先读文件 → 看到报错 → 换假设
                         ↑
                  投机步骤也会被强化
```

- 篮球概念图只做开场锚点，随后退到左上角，不再与下方卡片争空间。
- 成功/失败用两条不同透明度的轨迹表达；数字 0/1 贴在终点，不在轨迹外另挂数字。
- “力量”和“危险”不是两张新卡，而是同一条反馈箭头的绿/红两次强调。

### S5｜SWE-RL：一条证据链 + 一组迁移结果（25.1s）

目标：突出 41.0% 这个主数字，五个域作为迁移结果围绕它，而不是纵向堆四个大卡。

```text
真实软件工程 → patch 相似度 → SWE-bench Verified
                                      41.0%
                         ↙   ↓   ↘
                 函数编程  库使用  代码推理
                         ↘   ↓   ↙
                   数学 / 语言理解
                 SFT baseline：退化（底部红线）
```

- 41.0% 放在中心大数字卡，数字滚动位置预留在卡内。
- 五个域做成两行小芯片或径向迁移线，避免单列占满中间。
- 只在最后显示 SFT baseline 红线，作为对比落点。

### S6｜Reward hacking：三层攻击面（31.0s）

目标：把“表面指标 → 环境漏洞 → 篡改奖励代码”做成逐层深入的系统剖面。

```text
┌ 指标层：堆关键词                         ┐
├ 环境层：改单元测试                       ┤  verifier 边界
└ 奖励层：改写 reward code                  ┘

神经网络奖励  ≠ 规则奖励免疫
两者只是偏差方式不同
```

- 三层攻击面纵向占据主体，每层出现时上一层保留但降透明度。
- “规则不会被攻击？”直接在边界线旁被红叉否定，不另开一张页面。
- 最终比较条放在底部，用形变替换掉三层攻击面，不让旧层和新卡同时争中心。

### S7｜防线：四层防御塔（18.7s）

目标：把现在的 2×2 小卡改为纵向四层防御塔，充分利用竖屏高度。

```text
        审计层｜行为日志 · 人工抽检
        评估层｜多测试集 · 独立 verifier
        环境层｜沙箱 · 只读测试 · 最小权限
        目标层｜明确成功条件
        ─────────────────────
           verifier 是系统边界
```

- 四层从下向上依次搭建，层间有防护连接，不清屏。
- 最后一条结论线从防御塔底部拉出，画面重心自然下移。

### S8｜结果验证 vs 过程验证：双轨时间线（20.1s）

目标：不用“图片 + 五张卡”纵向堆叠，改成同一任务的两条反馈轨道。

```text
结果验证：开始 ───────────────▶ 终点打卡
          清晰 / 便宜 / 信号稀疏

过程验证：开始 ──●──●──●──●──▶ 终点
          中间推理与工具调用，反馈更密

              过程 verifier 也要可靠
```

- 上下两条轨道占据主体，图片只作为淡背景纹理或不再使用。
- 先亮结果轨道，再补过程轨道；结尾 warning 变成底部红色边界条。

### S9｜收束：三条结论变成尾卡（51.1s）

目标：解决最长 Scene 的“前半总结、后半 CTA、最后又清屏”的割裂感。

```text
① RLVR：规定奖励如何验证
② PPO / GRPO：规定策略如何更新
③ verifier：就是系统边界
                 ↓ morph
点赞 / 收藏 / 关注「数解AI」
同名文章 · 下一篇：真实 Agent 环境的权限隔离
问题：最终测试 / 过程 verifier / 人工抽检？
```

- 三条结论从上到下逐条出现，保留在背景。
- CTA 不是新页面，而是三条结论压缩成顶部摘要后，底部展开 CTA 区。
- 最终品牌尾卡单独出现，但只带 logo、文章标题、下一篇，不再和互动问题同屏。
