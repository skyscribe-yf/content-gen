# 《RLVR：可验证奖励怎么重塑后训练？》视频号分镜脚本

基于 content/2026-08-02-rlvr/weixin.md
规格：竖屏 1080×1920 · Manim 动画 · **口播（作者原声）** + 烧录字幕 · 目标 2-3 分钟

## 段落设计（9 段）

| # | 场景 | 动画要点 | 配音稿 |
|---|------|---------|--------|
| S1 | 开场钩子 | 一个 coding agent 接到任务：读仓库、改代码、跑测试、看报错、再改一次。训练器最后收到的，只有一个数字：测试通过 1，测试失败 0。没有老师告诉它哪步对了，它为什么还能学会拆任务、调工具、反复纠错？这正是 RLVR 最反直觉的地方。 |
| S2 | 三兄弟定位 | 先把关系理清。RLVR 解决奖励设计：什么叫做得好，能不能自动检查。PPO 和 GRPO 解决策略优化：拿到奖励后，参数怎么更新。RLVR 可以接 PPO，也可以接 GRPO——它不等于 GRPO。 |
| S3 | R1-Zero 最小闭环 | 看 DeepSeek-R1 的最小闭环。Verifier 不是更聪明的老师，只回答一件事：结果满足检查条件吗？数学题对答案，代码题跑测试。R1-Zero 从规则奖励出发：AIME 2024 平均正确率，从 15.6% 涨到 77.9%，还自己长出了反思和验证。优化目标一句话：提高拿到可验证结果的概率。 |
| S4 | coding 为什么外溢 | 为什么代码奖励能外溢成 Agent 能力？想想投篮：教练不看手腕，只看球进没进。成功轨迹概率提高，失败轨迹被压低。只有终点 0/1，模型也会学会：先读相关文件再动手，看到报错就换假设。但投机步骤只要稳定提分，也会被一起强化。这是 RLVR 的力量，也是它的危险。 |
| S5 | SWE-RL 证据 | 证据在 SWE-RL：把 RL 推进到真实软件工程，用 patch 相似度当奖励。SWE-bench Verified 上 solve rate 达到 41.0%。更反直觉的是：只在软件数据上训练，却在函数编程、库使用、代码推理、数学和语言理解五个域全部提升——SFT baseline 反而退化。 |
| S6 | 奖励可作弊 | 但可验证不等于不可作弊。第一层：钻指标空子，verifier 只看最终答案，模型就堆关键词。第二层：环境漏洞，代码模型直接改单元测试。第三层：Reward tampering，模型连奖励代码一起改。受控实验里，少量样本真的会改写自己的奖励函数。规则奖励也不免疫——真正的对比不是「神经网络会被攻击、规则不会」，而是两者偏差方式不同。 |
| S7 | 防线表格 | 防线不能只改一个分数函数，要四层：目标层明确成功条件；环境层沙箱、只读测试、最小权限；评估层多测试集、独立 verifier；审计层行为日志、人工抽检。verifier 是系统边界。 |
| S8 | 结果 vs 过程验证 | 下一道墙是过程验证。结果验证像终点打卡：清晰便宜，但信号稀疏。过程验证检查中间推理和工具调用：反馈更密，长任务更能归因——但过程 verifier 自己也得可靠，否则只是从钻终点分，变成钻中间分。 |
| S9 | 总结 + 尾卡 | 收官三句话：第一，RLVR 规定奖励如何验证，PPO 和 GRPO 规定策略如何更新。第二，代码环境把终点奖励传回多步行动，coding 才外溢成 Agent 能力。第三，可验证不等于不可作弊，verifier 本身就是系统边界。如果你觉得这条视频有帮助，欢迎点赞、收藏，关注「数解AI」不迷路，想了解更多细节可以到公众号查看同名文章。下一篇我们离开训练回路，去看部署现场：verifier 进入真实 Agent 环境，权限隔离和安全审计怎么做。留个问题：让 coding agent 在沙箱里完成任务，你会把奖励交给最终测试、过程 verifier，还是人工抽检？评论区聊聊。 |

## 制作流程

1. 配音：口播模式。`tts.txt` 逐段录音（录音室 voice_studio.py）→ `voice_process.py` 修音/一致性/停顿分析
2. 动画：每段一个 Manim Scene（S1..S9），`construct` 末尾 `pad_to_voice()` 补齐
3. 构建：`scripts/manim_video_build.py` mux 配音 + 无缝拼接 + 黄色字幕烧录 + 品牌尾卡
4. 归档：`content/2026-08-02-rlvr/shipinhao/`
