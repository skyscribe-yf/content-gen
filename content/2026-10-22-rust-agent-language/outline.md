# 大纲：Rust是AI agent时代的最佳语言？192个任务测完，答案分两半

## 定位

- **标题**：Rust是AI agent时代的最佳语言？192个任务测完，答案分两半
- **类型**：行业观察（K 组·圈外工程大事件续篇，语言生态线）
- **系列**：行业观察（10-09 DHH 篇同系，本篇不依赖前篇可独立阅读）
- **摘要（digest）**：固定模型、固定工具、八种语言、192 个真实任务——唯一一次像样的实测里，Rust 简单任务通过率 74.7 全场第一，难任务掉到 24.7 垫底，全程最贵。口号传开，是因为三件不同的活被混成了一句。关键词：Rust、AI agent、编程语言、实测。
- **结论**：Rust 不是这个时代的默认语言。它是强约束语言里最强的一个，也是 agent 反馈循环里最贵的一个。它赢的不是「写」，是「有答案纸的搬」。按活选语言，不按时代口号选。

## 结构（叙事弧线：每节回答上一节的问题）

### 开头（无标题，前两段钩子）
- 个人故事（作者原声，槽 1）：许多 skill 内嵌的工具/命令行一开始用 Python/TS 写，因为早期 agent 对这两种语言拟合最好、更容易一遍就好；问题是 skill 调用后 agent 要耗费很多时间等待不能秒回的操作，严重到很快用 Rust 重写了绝大部分；今年下半年以来的开源模型和 harness 都能处理得很好了。
- 转折（AI 写）：这次重写让我想起最近传开的那句口号——「Rust 是 AI agent 时代的最佳语言」。我去查了公开讨论和唯一一次像样的实测，答案分两半。
- 钩子类型：个人故事 + 直接抛问题（爆款公式三选一，禁系列导航开头）
- 注：作者原声里「Python/TS 写得顺」与「Rust 等不起」两端并存，正好是全文张力的种子

### 一、这个口号，把三件不同的活混成了一句
- 三件事拆解（表或并列）：
  1. Agent 写应用代码时 Rust 最好写——有人吹，测量不支持全面胜利
  2. 写 agent 的运行时、沙箱、CLI，Rust 常常更合适——成立，有生产案例（我的沙箱就是）
  3. 整个 AI 栈都该换 Rust——几乎没有认真的人这么说
- 过渡句：口号能传开，是因为三件不同的活被混成了一句。拆开之后，每一件都要单独算账。

### 二、正方真正抓住的一点：能编译就大致正确
- Greg Brockman：`if it compiles it's ~correct`
- GoDaddy 论文：所有权、借用、生命周期、穷尽匹配把合法程序的空间压窄，无效实现在执行前被拒绝
- heise：人不再写的时候「写得开不开心」失去对象；编译器是第二套确定性反驳，补测试到不了的并发
- GitHub Copilot 运行时迁移（最硬生产案例）：83 万行生产 Rust、128 个 PR / 14.5 周；动机不是语言信仰，是要离开 Node/V8；一轮会话 5.25s → 292ms（18 倍）
- 过渡句：写代码变便宜以后，瓶颈从「写得顺不顺」挪到「有没有一个不会被说服的检查器」。这个论点成立。但它有个没说出口的前提——检查器本身不便宜。

### 三、实测：192 个任务，答案分两半
- ProgramBench 设计（一段讲清）：固定模型 gpt-5.5、固定 harness Codex、八种语言、断网沙箱、每种语言带 top 100 依赖离线镜像、n=192、每题一次运行
- 结果三数字：
  - 简单任务：Rust 74.7 第一（也最靠右=最贵）
  - 难任务：Rust 24.7 垫底，跌 50 点（全场最大跌幅），与 JS/Go/Java/C 挤在低分区；Python/TS 留在上面
  - 全程最贵：$1.40/任务，构建轮次最多，每次修复付一次 cargo build
- quickjs 整解释器重写：从零写的语言全崩（Rust 3.1%），靠宿主 JS 运行时的才活
- 过渡句：这个「分两半」不是测量噪声——50 点的跌幅远超单次运行的波动。问题变成：难任务上，Rust 输在哪？

### 四、难任务为什么崩：反馈循环按分钟计费
- zack（前 Bun）：编译时间太长，瓶颈是时间不是智能
- Ryan Dahl（Node 作者）：Rust 从来不是 agent 的默认语言，应用代码属于默认语言
- Armin Ronacher：能选就推荐 Go——显式 context、go test 有缓存、语言马虎 agent 不容易猜错、生态十年向后兼容
- 掘金体感：生命周期报错牵着函数签名、结构体、调用链一起动，不像 Go 类型不匹配一步修好
- 过渡句：「能编译就大致正确」的另一面是——为了能编译，每一次重试都在付账。简单任务上这笔账划算：逻辑直、轮次少。难任务上账越滚越大：错误螺旋、重试变多、每次等 cargo。护栏是真的，但护栏按分钟计费。

### 五、Rust 真赢的时候：有答案纸的移植
- Anders Hejlsberg：TypeScript 编译器移植试过 Rust，不可行——借用检查器不允许循环数据结构（带 parent 指针的树、互相引用的 symbol），移植会变重写，重写会变成另一门语言。选 Go，11.9 倍提速，错误信息还是原来的
- 一周后：bun check（typescript-go 7.0.2 的 Rust 移植，错误码与 tsc 相同，Next.js 2881 文件 2.4s vs tsc 6 的 14.8s）；tsc-rs（5 个月、约 2 万美元 token、一行没读）
- 做成的条件：答案纸已经存在——tsc 7 的错误码就是测试，Go 编译器是裁判
- DHH 一句回调：上个月那篇 150 倍的账，算的是同一件事的另一面——没有答案纸的时候，agent 交付的是被任务书带偏的对照实验
- 过渡句：把三、四、五节放在一起，规律出来了——Rust 赢的不是「写」，是「有裁判的搬」。

### 六、按活选语言，不按时代口号选
- 分层表（四行）：
  - 模型、评测、实验胶水 → Python
  - agent 产品、MCP、插件、界面 → TypeScript
  - 新后端服务，要快而确定的改-编译-测试循环 → Go
  - 运行时、沙箱、权限边界、必须嵌进别的语言的热路径 → Rust（前提：团队里还有人能审查所有权和架构）
- 收束（回扣开头）：人可以少写，不能不会读。编译通过只排除了一类错。架构差、测量不公平、行为只是看起来像，编译器都不说话。团队里没有人能分辨「借用检查器在抓真 bug」和「agent 在讨好编译器」，Rust 会把审查能力一起拿走。我的沙箱还是 Rust——但那是因为不可信代码跑在里面，不是因为 Rust 赢了时代。

- 原句：我的许多skill里面内嵌的工具和命令行程序，一开始使用的是python或者typescript写的，原因很简单，早期的agent对这两种语言拟合的最好，更容易一遍就好。问题是很多时候，skill调用起来后，Agent会耗费很多时间等待不能秒回的调用操作。这个问题如此严重以致于我很快就要rust重写了里面的绝大部分，今年下半年以来的开源模型和harness都能处理的很好了。
