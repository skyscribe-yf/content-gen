中文没有空格，BPE 会不会把词切错？

很多人第一次听到 BPE，都会有一个很自然的疑问：

英文单词之间有空格，中文却是一整串连续字符。中文连“词”都不好切，怎么做 BPE？会不会因为分词歧义，把模型带偏？

先给结论：中文没有空格，不妨碍 BPE；BPE 也不需要先知道“词”在哪里。

BPE 不是中文分词器。它不先判断“南京市”是不是一个词，也不先给句子画词语边界。它做的事情更朴素：从字符或字节开始，统计哪些相邻片段经常一起出现，然后按固定的合并规则把它们粘起来。

这篇回答先把逻辑讲清楚。明天中午的公众号完整版会补上原创图解和真实 Tokenizer 输出。

把中文想成一串没有空格的磁贴

英文像是已经分好组的磁贴：Today is sunny。空格提供了一个很明显的边界。但 BPE 并不依赖这个边界。中文可以直接从更小的磁贴开始：

今｜天｜天｜气

如果训练语料里“今天”和“天气”经常出现，那么 今｜天、天｜气 就可能成为高频相邻片段，被合并成：

今天｜天气

如果“今天天气”整体也非常常见，它还有可能继续合并成更大的 token；如果某个生僻人名很少出现，就可能继续保持为更小的片段。

所以 BPE 的核心不是“有没有空格”，而是：常见片段越合越大，罕见片段保留小块。

这也解释了为什么 token 不等于词：它可能是一个汉字、几个汉字、半个英文单词、一个数字，甚至是 byte-level BPE 里的字节片段。

“切分歧义”和“语义歧义”不是一回事

中文确实存在语义歧义。比如“南京市长江大桥”，人类可以讨论它的词语边界和句法结构。但 Tokenizer 并不会在这里做一次中文阅读理解。

Tokenizer 更像一个固定规则的条形码打印机：输入完全相同的字符串，就按词表和 merge rules 打出完全相同的 token ID。它不需要根据上下文临时猜：“这次的‘长’到底是不是‘长度’的‘长’？”

真正的语义理解发生在后面的 Transformer 里。可以把两者分开看：

  • Tokenizer 负责把文字切成模型能查表的片段，并分配 token ID；
  • 词嵌入和 Transformer 负责让这些片段进入上下文，逐步形成含义。

就像切菜刀不会决定一盘菜是甜是咸。刀负责把食材切成可处理的大小，味道还要看后面的烹饪过程。

因此，BPE 的切法可能不符合人类的词感，但这不等于它把句子“理解错了”。它只是在执行一套确定的编码规则。

中文为什么有时会显示成“乱码”？

现代模型常见的 byte-level BPE，会先把文字落到 UTF-8 字节，再对这些字节片段做合并。于是打印 tokenizer 内部 token 时，中文可能出现类似 è¯·、çĶ¨ 的显示形式。

这不是中文被破坏了，而是内部字节被映射成了可打印字符。模型真正使用的是对应的 token ID，编码过程仍然可以还原原文。

以文章里实际跑过的 DeepSeek-V4-Pro Tokenizer 为例：

请用 Python 写一个 Transformer，参数量 7B。 → 14 个 token

其中，Python 和 Transformer 可能以带前导空格的片段出现，7B 则被拆成 7 和 B。同一句话里，中文、英文、数字和标点可以采用完全不同的切法。

这才是 BPE 有意思的地方：它不按人类的“字数”计量，而按训练语料里形成的片段来计量。

顺便看一个真实配置里的数字：公开 config.json 中，DeepSeek-V4-Pro 的 vocab_size 是 129280；tokenizer.json 中基础 BPE 词表是 128000 条，另外还有 added tokens 和特殊 token。两个字段表达的不是同一个统计口径，不能简单相加。

为什么这件事和 API 账单有关？

因为模型真正接收的不是“几个汉字”，而是一串 token。

同样长度的三段输入：

  • 中文说明
  • Python 函数
  • 7B + UTF-8

token 数可能完全不同。token 越多，同一个上下文窗口能容纳的原文越少；按 token 计费的 API，用量也可能更高。

所以“中文是不是一个字一个 token”不是一个可靠的估算方法。常见短语可能被合并成大块，代码、数字、罕见符号也可能被切得更细。真正要估算上下文和成本，应该先跑一遍对应模型的 Tokenizer。

一句话总结

中文没有空格，照样可以做 BPE。BPE 不需要先分出“词”，它从字符或字节开始，按频率合并相邻片段；切分规则是确定的，真正的语义消歧交给后面的上下文建模。
