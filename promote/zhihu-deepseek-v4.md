# DeepSeek V4 全面支持百万上下文 token，这意味着什么？到底有多厉害？

先给结论：**DeepSeek-V4 的 1M 上下文，真正厉害的地方不只是“能塞进更多文字”，而是模型开始有机会连续处理整座代码仓库、长篇资料和长周期 Agent 任务。**

但这里有一个更重要的限定：**1M token 是工作记忆的容量，不等于模型会平均、稳定地理解其中每一个 token。**真正的技术难点是三件事：装得下、找得到、算得动。

## 先把“1M”说准确

1M 指的是一百万个 token，不是一百万个汉字。

Token 是模型处理文本时使用的基本片段。同一句话，中文、英文、代码、数字和特殊符号的切分方式都可能不同。因此，1M token 到底能装下多少汉字、多少行代码，不能直接用字符数估算，要看具体 tokenizer。

这就像搬家时数的不是“书的页数”，而是“箱子里的小件数”：一本中文书、一本英文书和一摞代码，页数相同，装箱方式可能完全不同。

所以，DeepSeek-V4 的 1M 更准确的理解是：**它把模型一次可接收的 token 序列上限，推到了百万级。**官方发布说明确认，V4-Pro 和 V4-Flash 都支持 1M 上下文，并同步提供预览版和开源模型。

## 为什么“把窗口做大”这么难？

因为 Transformer 的注意力，不是把文本往一个大硬盘里一存就完事。

每个 token 都要和上下文中的其他 token 计算关系。把序列长度记成 T，注意力的核心计算量可以直觉地写成：

> **注意力计算量 ≈ c × T²**

T 增加 10 倍，计算量大约增加 100 倍。这像开一场会议：10 个人互相确认信息，关系数还有限；100 个人进来，每个人都要和其他人建立关系，沟通次数不是增加 10 倍，而是接近增加 100 倍。

还有第二堵墙：KV Cache。

模型生成新 token 时，需要把历史 token 的 Key 和 Value 保存下来，后面继续查。它的规模大致随序列长度线性增长：

> **KV Cache ≈ T × d × L × 2 bytes**

T 是 token 数，d 是缓存维度，L 是层数。上下文从 100K 变成 1M，KV Cache 至少也要面对约 10 倍的长度压力。

因此，百万上下文不是“买一块更大的显存”这么简单，而是同时撞上了**计算量平方增长**和**缓存线性增长**两堵墙。公众号「数解AI」之前那篇“AI 上下文为什么越长越慢”，讲的就是这两堵墙为什么会让 Agent 读到一半失忆、跑到一半崩掉。

## DeepSeek-V4 是怎样把这件事做成的？

第一层是 MoE：让模型拥有很大的总容量，但每个 token 不必让全部参数同时工作。

官方模型卡给出的规模是：

| 模型 | 总参数 | 激活参数 | 上下文长度 |
|---|---:|---:|---:|
| DeepSeek-V4-Flash | 284B | 13B | 1M |
| DeepSeek-V4-Pro | 1.6T | 49B | 1M |

“激活参数”可以理解成：这一次处理 token 时，真正参与主要计算的参数规模。总参数像一座拥有很多专科的医院，激活参数像当前病人实际被叫来的科室。医院可以很大，但不需要每个病人都让所有科室会诊。

公开的 V4-Pro `config.json` 里，还能看到 `n_routed_experts: 384`、`n_shared_experts: 1`、`num_experts_per_tok: 6`。这些配置说明了它的稀疏专家结构，但不能简单推出“模型每次只做全部计算的 6/384”——注意力、路由、通信和内存访问仍然要付成本。

第二层是注意力本身的变化。

DeepSeek 官方把 V4 的长上下文注意力描述为混合结构：**CSA（Compressed Sparse Attention，压缩稀疏注意力）+ HCA（Heavily Compressed Attention，重度压缩注意力）**。直觉上，它不是让每个 token 都重新翻遍整本书，而是：

- 用压缩表示降低“笔记”的体积；
- 用稀疏选择优先查看更相关的 token；
- 用更粗粒度的全局概览保留整篇材料的方向感。

这就是“装得下”和“找得到”同时处理。

官方技术报告给出的 1M 场景对比是：V4-Pro 的单 token 推理 FLOPs 约为 DeepSeek-V3.2 的 **27%**，KV Cache 约为 **10%**。这不是说任何任务都固定快 3.7 倍或省 90%，而是说明在百万上下文这个极端场景里，架构确实把主要开销压了下去。

从公开配置也能看到这条路线的痕迹：`max_position_embeddings: 1048576`，`index_topk: 1024`，并配置了滑动窗口等字段。配置能证明模型怎样声明自己的结构；至于不同任务下实际能否找准关键信息，还要看评测和真实调用。

## 到底有多厉害？看它改变了什么任务

以前使用长文档，常见流程是：先切块，再摘要，再把摘要交给模型。每压缩一次，就有一次信息损失；上下文越长，人工整理越重。

1M 上下文把一些任务的工作方式改了：

第一，代码 Agent 可以把更多仓库文件、规则、测试日志和历史修改放在同一个工作记忆里，减少“刚看过的文件又要重新解释”的次数。

第二，长文档问答可以跨章节找证据。合同、技术规范、项目文档不必每次都只截一小段给模型。

第三，长周期 Agent 有更大的轨迹空间。它可以连续经历读取、修改、测试和复盘，而不是做到一半就把早期决策压缩成一句模糊摘要。

但这不代表“把一百万 token 倒进去，模型就自动读懂一百万 token”。

上下文窗口更像一间更大的会议室，不是一个会自动整理重点的秘书。如果关键事实埋在几十万行日志中，模型仍可能检索不到、引用错位置，或者被大量相似信息干扰。长上下文也不会消除延迟、费用和推理质量之间的权衡。

所以我更愿意把 V4 的意义概括成一句话：

> **它不是简单把 AI 的“记忆硬盘”做大，而是在尝试把记忆变成一种可压缩、可选择、可持续计算的系统。**

这也是为什么“1M”只是表面数字，背后真正值得看的，是 MoE 负责“谁来干活”，CSA/HCA 负责“去哪里找信息”，工程系统负责“能不能把这套机制稳定跑起来”。
