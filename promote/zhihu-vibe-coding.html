vibe coding 降低了写代码的门槛，但拉高了判断代码的门槛

一个真实案例（无数人在复现）：有人用 Cursor vibe 出一个 TODO 管理 app。跑起来没问题，上线也没问题。三个月后用户数据全泄露——因为他不知道 AI 把用户 token 存进了 localStorage。

vibe coding 让"这个代码能跑"变得极其廉价。但"这个代码能跑"和"这个代码是对的"之间，隔着一条 AI 填不平的沟。

（图见文末——这篇回答里用到的几个核心概念，我在公众号「数解AI」里画了图解。）

vibe coding 的本质还是成语接龙

LLM 生成代码和生成中文，底层是同一个动作：猜下一个 token。

你敲 func getUser，它猜下一个最可能是 (。接上了，猜 userID。再接，猜 )。所有 token 链起来——一个函数签名出来了。

换成中文场景：你输入"程序员不"，它猜"会"。再猜"失"。再猜"业"。每次只猜一个。

从头到尾，没有理解你的业务逻辑，没有检查 localStorage 的安全性，没有想过"生产环境用什么存用户数据"。它只是在统计上最像"正确代码"的方向上接龙。

我在公众号「数解AI」里画过一张图：LLM 的 token 预测流。中文成语接龙 → 代码补全 → 同一个机制。回复"路线图"直接收到。

为什么 vibe 出来的代码"能用"？

因为大部分 CRUD 代码的模式极度重复。

以 DeepSeek-V3 为例：训练数据 14.8 万亿 token，其中代码占比不小。它见过：

func getUserByID 后面接 db.Query("SELECT ...") 几万次

router.HandleFunc("/api/users", ...) 后面接 handler 定义几十万次

SELECT * FROM users WHERE 后面接条件 ID 几百万次

这些模式在训练数据里出现的频率极高。概率预测在这种场景下出奇的准。你手感好，觉得"AI 太聪明了"——其实不是聪明，是你写的需求恰好众数一样的常见。

这就叫 高频模式吻合。和自动挡汽车一样——城市通勤、直线高速，自动挡和手动挡没区别。因为你的驾驶场景完全落在"最常见操作"的范围内。

什么时候崩？

当你的需求不落在训练数据的高频区间里。

想知道你的代码是不是危险，看一个指标：这次生成，AI 是从"见过最多的模式"里取的，还是你不确定它在哪取的。

三类典型崩法：

1. 安全边界

AI 永远猜不到你的攻击面。localStorage 存 session token 在代码库里出现过无数次（因为 demo 和教程都这么写）——AI 不会告诉你"生产环境别放这"。因为它见过的代码里，"存 localStorage"和"安全漏洞"之间没有 token 级别的关联。

2. 并发竞态

你 vibe 出一个 Go 的 goroutine 并发处理逻辑。跑了三天，偶尔丢数据。查 bug：两个 goroutine 同时写同一个 map。Go 的 map 不是并发安全的——但训练数据里到处都是 go func()，极少有人写完整的 sync.Mutex 包裹。AI 见过前者的次数远多于后者，它不会主动给你加锁。

3. 分布式共识

vibe 不出一个正确的 Raft 算法实现。不是因为 AI 没见过 Raft 论文——是因为任何一步 token 偏差都会导致整个系统脑裂。成语接龙模式在"每一步都必须绝对正确"的场景下，容错率为零。

一个直觉：自动挡 vs 手动挡

自动挡让所有人都能开车。城市通勤、周末出游——没区别。

但当你听到发动机舱传来金属摩擦声——

会修车的人：知道是变速箱问题，立刻停车叫拖车。

只开自动挡的人：继续开，高速上变速箱锁死。

vibe coding 就是自动挡。它让你更快地上路，更快地见到"跑起来了"的快感。但它也让你更快地撞上那些需要"知道下面在发生什么"才能避开的坑。

所以是好事还是坏事？

对"能判断代码"的人，是好事。对"只会写代码"的人，是坏事。

vibe coding 让"代码能跑"变便宜了，但让"判断代码对不对"变贵了。以前一个 bug 是你自己写的，你知道坑在哪。现在一个 bug 是 AI 写的，你连它的推导过程都看不到——因为它根本没有"推导"，只有 token 接龙。

这时候什么最值钱？

知道 localStorage 和 httpOnly cookie 区别的人

看到 AI 生成 var mu sync.Mutex 时知道为什么加了锁的人

理解 SQL 执行计划、不会被 AI 生成的 SELECT * 炸库的人

不是"会写代码"的人被替代了，是"只会照着模板写"的人被替代了。

怎么成为那个"能判断"的人？

不需要去啃《统计学习方法》。需要的是：把你每天在用的 AI 工具，从头到尾理解一遍。

你知道 AI 在猜 token——为什么它猜出的代码有时候能用，有时候不能？什么时候能？什么时候不能？

这些问题的答案不需要数学学位。需要的是一种工程直觉——理解你手上的工具，而不是跪拜它或妖魔化它。

我在「数解AI」做的事就是这个：不讲情怀文，不讲"程序员会不会失业"。只讲你每天用的 AI 到底怎么工作。用工程师能理解的方式。
