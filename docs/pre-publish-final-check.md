# 发布前最终检查

调用 `baoyu-post-to-wechat` 发布前的**最后一道门禁**，在 `docs/article-quality-check.md`（内容质量）和 `AGENTS.md` 发布前检查（流程）之后执行。逐项确认，全部通过才能点发布。

## 1. 标题与关键词 SEO

- 标题符合 `docs/article-title-seo.md` 最新标准：关键词前置 + 痛点驱动 + ≤22 字 + 含 1 个专业关键词 + **过 9 条自检清单（含感官冲击力第 9 条）**
- 摘要含 2-3 个搜索关键词
- 正文核心关键词在标题、摘要、首段中自然出现（不堆砌）
- **感官冲击力（2026-08-31 新增）**：① 标题一眼可读、有画面、有反差/情绪词（详见 article-title-seo.md 第 9 条）；② 封面缩成信息流卡片大小后仍单一主视觉、高对比、标题 ≤12 字且清晰可读（详见 image-generation.md「封面感官冲击力」节）——两项任一不满足，测试池期首日推荐可能为 0
- **封面文字脚本叠加（2026-10-28 新增，硬性）**：封面文字必须 `make_cover.py` 脚本叠（AI 只出无字底图），禁止 AI 生图直写中文（字形发虚拥挤）；`quality_check.py` 已自动核验（`check_cover.py` 比例/块高 + `cover_meta.json` ≤12 字 + `00-cover-base.png` 流水线证据），详见 image-generation.md「封面文字必须脚本叠加」节与 AGENTS.md 封面标题规格节

## 2. 正文开头无重复封面图 / 无重复标题

- 封面图 `00-cover.png` 由发布工具单独上传为封面，**正文开头不得再插入同一张图**
- 检查 `weixin.md` 第一张配图：如出现与封面相同的图片，删除正文中的引用
- **正文开头不得重复文章标题**：文章标题由发布工具单独作为标题，正文第一行不得再出现与 frontmatter `title` 相同的 H1 标题（`# 标题`），否则发布后正文开头会多出一个重复标题

## 3. 硬件数字事实核查

文中所有 **GPU 型号、显存容量、模型规模、上下文长度** 的组合必须能实际跑通。自检规则：

- 模型参数 × 量化位宽 + KV cache 估算值 **≤** 显卡总显存
- 消费级场景一律用消费级硬件（4090 / 5090 / Mac 统一内存），服务器级场景用 A100 / H100 / H200
- 同一个段落内，硬件上下文必须一致：不能前半句在讲 4090，后半句的数据却是 70B 模型才能产生的
- 数字给到具体的 GB 或 MB，不写"很大""很多""几百兆"等模糊量

**本次 MLA 篇的教训**：70B 模型即使 4-bit（~35GB）也装不进 24GB 的 4090；KV cache 31GB 应和 A100 80GB 比，不是和 4090 比。

## 4. 无「待发布」残留

- 全文搜索 `（待发布）`、`待发布` 字样，必须为零
- 系列中已发布的文章，全部替换为真实微信链接（`https://mp.weixin.qq.com/s/...`），链接来自各篇 frontmatter 的 `wechatUrl` 字段
- 确实未发布的后续篇目：不列链接（2026-11-07 起尾部也不再写合集导航，见第 6 项）

## 5. 文末话题标签

- 末尾含 3-5 个 `#标签`，格式与选取规则见 `docs/wechat-topic-tags.md`
- 放在全文最末尾，独占一行

## 6. 尾部不放合集导航（2026-11-07 废止）

- 尾部**不再写 `📖 合集链接 + 箭头链`**（作者 2026-11-07 口径）——合集聚合改由后台发布时**勾选合集**完成，正文不列篇目
- 已发布的历史文章保留原样，**不回去改**；新文、修订稿一律不再加
- 后台勾选合集仍为必须项（合集页与菜单「全部合集」靠它），只是不进正文

❌ 已废止写法（仅历史文章保留）：

## 6b. 尾部「热门文章」（如有）

- 用 `scripts/hot_articles.py --md --cited <本文weixin.md>` 生成：读 `docs/wechat-data-audit-log.json` 聚合历史最高阅读量 Top 6，自动过滤贴图（publish-data `item_show_type!=0` ∪ tietu-corpus-summary ∪ tietu-extra），再追加本文引用的相关公众号文章；禁止手写、禁止挑最近发布的文章
- 链接行之间**不留空行**（空行 = 独立 `<p margin:1.5em>` = 视觉空行）；榜单变更后跑 `--self-check`

## 7. 下一篇预告：不再硬性要求（想要才写）

- **不强制**：结尾可以没有「下一篇」，不要为了凑预告而硬编选题（作者 2026-11-07：「有空再写」）
- 真要写也只写**已经在排期里的篇目**，禁止空头预告（"下篇拆××"但下篇根本不存在）；无排期就不写
- 替代做法：结尾用**开放式问题 + 互动引导**收尾（见第 8、9 项），不靠预告撑

❌ 已废止的硬性文案：

```markdown
下一篇我们聊残差连接：为什么网络越深反而越训不动？
```

## 8. 互动引导

- 尾部必须引导读者**点赞、关注、收藏**，结合价值承诺，不要只写干巴巴的"欢迎关注"

```markdown
觉得有用就点个赞 👍、收藏 ⭐ 备用；关注「数解AI」，新文第一时间推给你。
```

## 9. 叙事闭环：开头 ↔ 结尾

- 开头驱动问题、正文论证、结尾（阶段结论 + 互动问题）必须形成**完整的逻辑链条**，不能各自独立
- 自检：读者看完结尾后，回头想起开头的驱动问题——两者是否在同一叙事弧线上？

### 闭环标准

| 环节 | 要求 |
|------|------|
| 开头 | 提一个具体的痛点/问题，让读者知道"这篇文章要解决什么" |
| 正文 | 逐层拆解、给出答案，结束时形成阶段性结论 |
| 结尾 | 用阶段性结论收口 + 一个读者能答的开放问题（不再用下一篇预告接钩） |

### 常见断裂（必须修正）

```markdown
❌ 开头：1M 上下文到底难在哪？
   正文：KDA 用线性注意力解决
   结尾：下一篇我们聊 MoE 如何挑专家（且 MoE 与该篇无关）
   → 断裂：结尾接的东西和开头痛点不是一条线，读者会困惑"为什么突然跳到这？"

✅ 开头：1M 上下文到底难在哪？
   正文：KDA 用线性注意力省掉"每次回看全部历史"
   结尾：阶段性结论（省了回看，但历史本身的 KV Cache 还是大）+ 开放问题
   → 闭环：开头问"难在哪"，正文答了其中一半，结尾把边界交回读者
```

### 尾部收口检查（取代旧「系列内预告串联检查」）

全文通读一遍：结尾是不是从**本篇结论的边界**自然收口？去掉所有「下一篇」字样后，结尾是否仍然成立？不成立就得重写——而不是补一句预告。

## 11. 发布入口：必须是 `weixin.md`（走 mdnice 管线）

- 发布必须把 **`weixin.md`** 交给 `baoyu-post-to-wechat`（它内部 spawn `md-to-wechat.ts` → mdnice `scienceBlue` + `compactWechatLayout` + `relaxWechatReadability`）。
- ⚠️ **禁止先把 md 预渲染成 HTML 再发布**。`baoyu-markdown-to-html` 是**另一条渲染器**（它自己的 grace 主题 ≈ 段落 `margin: 1.5em 8px; letter-spacing: 0.1em`），与 mdnice 的内联样式完全不同——用它生成的 HTML 会把 mdnice 整个绕过去，排版、字号、留白全部脱离项目标准。
- 事故记录（2026-10-09，Pi Durable 篇）：先渲染成 HTML 再发，草稿箱里的版本不是 mdnice 样式，已重发修正并删除旧稿。
- 手机可读性规则固化在 `md-to-wechat.ts`：正文 16px、行高 1.85、段间距 14px、`ol/ul` 左缩进归零（修参考文献左侧空白）、`li` 加 4px、代码块 `pre-wrap` 不横滚 + 13px。改主题后需复核这些正则是否仍匹配。
